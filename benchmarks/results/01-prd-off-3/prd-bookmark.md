## 2. 배경 및 문제 정의

사용자는 관심 있는 게시글을 나중에 다시 읽고 싶어도 서비스 안에서 이를 저장하거나 모아 볼 수 없다. 그 결과 게시글 URL을 별도로 보관하거나, 다시 검색해야 하는 불편이 발생한다.

로그인한 사용자가 게시글을 북마크하고 마이페이지에서 저장한 게시글을 다시 찾을 수 있게 하여 콘텐츠 재방문 경험을 개선한다.

## 3. 목표

- 로그인 사용자가 게시글 상세 또는 게시글 카드에서 북마크를 추가·해제할 수 있다.
- 사용자는 현재 북마크 상태를 버튼의 시각적 상태로 즉시 확인할 수 있다.
- 사용자는 마이페이지에서 자신이 북마크한 게시글을 최신 북마크순으로 조회할 수 있다.
- 사용자별 북마크 데이터가 안전하게 분리되고, 새로고침 및 재로그인 후에도 유지된다.

### 성공 지표

릴리스 후 4주를 기준으로 아래 지표를 관찰한다. 목표값은 기존 활성 사용자 및 게시글 조회 데이터를 바탕으로 릴리스 전에 확정한다.

- 주간 활성 로그인 사용자 중 북마크 기능 사용률
- 게시글 상세 조회 대비 북마크 추가 전환율
- 북마크 목록을 통한 게시글 재방문율
- 북마크 추가·해제 요청 성공률 99.5% 이상
- 북마크 목록 조회 요청 성공률 99.5% 이상

## 4. 비목표

MVP에서는 다음을 지원하지 않는다.

- 북마크 폴더, 태그, 메모 및 정렬 방식 사용자 설정
- 북마크 수의 작성자 또는 다른 사용자 대상 공개
- 북마크 추가 알림 및 리마인더
- 비로그인 사용자의 로컬 북마크 저장 또는 로그인 후 병합
- 게시글 본문 전체의 오프라인 저장
- 북마크 목록 공유 또는 내보내기

## 5. 대상 사용자 및 핵심 사용자 스토리

### 대상 사용자

- 서비스에 로그인한 상태로 게시글을 탐색하는 사용자
- 관심 게시글을 저장하고 나중에 다시 확인하려는 사용자

### 사용자 스토리

1. 로그인 사용자로서 관심 게시글을 북마크하여 나중에 다시 찾고 싶다.
2. 로그인 사용자로서 이미 북마크한 게시글인지 한눈에 알고 싶다.
3. 로그인 사용자로서 실수로 추가한 북마크를 같은 위치에서 바로 해제하고 싶다.
4. 로그인 사용자로서 내가 북마크한 게시글을 마이페이지에서 모아 보고 싶다.
5. 비로그인 사용자로서 북마크 버튼을 눌렀을 때 로그인이 필요하다는 안내를 받고 로그인 화면으로 이동하고 싶다.

## 6. 가정 및 정책

- 기존 서비스에 Supabase Auth 기반 로그인과 사용자 식별 체계가 존재한다.
- 기존 `posts` 테이블과 게시글 상세·목록 UI가 존재한다.
- 게시글 작성자는 자신의 게시글도 북마크할 수 있다.
- 북마크는 사용자와 게시글 사이에 하나만 존재하며 중복 저장할 수 없다.
- 북마크 목록의 기본 정렬은 북마크한 시각의 내림차순이다.
- 삭제된 게시글은 북마크 목록에 노출하지 않는다. 게시글이 물리 삭제되는 경우 연결된 북마크도 함께 삭제한다.
- 비공개·차단 등 게시글 접근 정책이 있다면 북마크 목록에도 동일하게 적용한다.
- 비로그인 사용자에게도 북마크 버튼을 노출하되, 클릭 시 인증 안내 후 로그인 화면으로 이동시킨다. 로그인 완료 후 원래 게시글로 돌아올 수 있도록 복귀 URL을 전달한다. 로그인 전에 누른 북마크는 자동 저장하지 않는다.

## 7. 사용자 흐름

### 7.1 북마크 추가

1. 사용자가 게시글 상세 또는 게시글 카드에서 비활성 북마크 버튼을 누른다.
2. UI가 즉시 활성 상태로 바뀐다.
3. 서버에 현재 사용자와 게시글의 북마크 생성을 요청한다.
4. 성공하면 활성 상태를 유지하고 관련 북마크 목록 캐시를 무효화한다.
5. 실패하면 이전 상태로 복구하고 재시도 가능한 오류 메시지를 표시한다.

### 7.2 북마크 해제

1. 사용자가 활성 북마크 버튼을 누른다.
2. UI가 즉시 비활성 상태로 바뀐다.
3. 서버에 북마크 삭제를 요청한다.
4. 성공하면 비활성 상태를 유지하고 관련 북마크 목록 캐시를 무효화한다.
5. 실패하면 이전 상태로 복구하고 오류 메시지를 표시한다.

### 7.3 마이페이지 목록 조회

1. 사용자가 마이페이지의 `북마크` 메뉴로 이동한다.
2. 시스템이 해당 사용자의 북마크를 최신 북마크순으로 조회한다.
3. 사용자가 게시글 카드를 선택하면 게시글 상세로 이동한다.
4. 목록에서 북마크를 해제하면 해당 항목을 즉시 제거한다.

## 8. 기능 요구사항

### FR-1. 북마크 버튼 노출 및 상태

- 게시글 상세 화면의 주요 액션 영역에 북마크 버튼을 노출해야 한다.
- 게시글 카드에 기존 액션 영역이 있다면 동일 버튼을 노출해야 한다.
- 버튼은 `북마크 안 됨`, `북마크됨`, `처리 중` 상태를 구분해야 한다.
- 아이콘만 사용하는 경우에도 스크린 리더용 이름을 제공해야 한다.
- 활성 상태는 색상만이 아니라 채움 여부 등 추가 시각 요소로 구분해야 한다.
- 초기 상태 확인 중 잘못된 상태가 잠깐 표시되지 않도록 로딩 상태를 사용해야 한다.

### FR-2. 인증 처리

- 로그인 사용자만 북마크 데이터를 생성·삭제·조회할 수 있어야 한다.
- 비로그인 사용자가 버튼을 누르면 로그인 필요 안내를 표시해야 한다.
- 로그인 화면 이동 시 현재 페이지를 복귀 URL로 보존해야 한다.
- 인증 세션이 만료된 요청은 로그인 필요 상태로 처리하고 낙관적 UI를 원복해야 한다.

### FR-3. 북마크 추가

- 로그인 사용자가 북마크되지 않은 게시글의 버튼을 누르면 북마크를 생성해야 한다.
- 동일 사용자·동일 게시글 조합의 중복 데이터가 생성되지 않아야 한다.
- 중복 추가 요청은 최종적으로 북마크됨 상태를 보장하는 멱등 동작이어야 한다.
- 빠른 연속 클릭으로 상충하는 요청이 발생하지 않도록 처리 중에는 같은 버튼의 추가 입력을 막아야 한다.

### FR-4. 북마크 해제

- 로그인 사용자가 북마크된 게시글의 버튼을 누르면 북마크를 삭제해야 한다.
- 이미 삭제된 북마크의 해제 요청도 최종적으로 북마크 안 됨 상태를 보장해야 한다.
- 해제 성공 후 같은 게시글을 다시 북마크할 수 있어야 한다.

### FR-5. 상태 동기화

- 같은 게시글이 여러 화면 또는 컴포넌트에 표시될 때 React Query 캐시를 통해 상태가 일관되어야 한다.
- 추가·해제에는 낙관적 업데이트를 적용하고 실패 시 이전 캐시로 롤백해야 한다.
- mutation 완료 후 게시글별 상태와 북마크 목록 쿼리를 재검증해야 한다.
- 새로고침 및 다른 기기에서 재로그인한 뒤에도 서버 상태가 복원되어야 한다.

### FR-6. 마이페이지 북마크 목록

- 마이페이지에 `북마크` 메뉴 및 전용 경로를 제공해야 한다. 권장 경로는 `/mypage/bookmarks`이다.
- 현재 사용자가 북마크한 게시글만 노출해야 한다.
- 기본 정렬은 `bookmarks.created_at DESC`로 한다.
- 각 항목에는 최소한 게시글 제목, 요약 또는 본문 일부, 작성자, 게시일, 북마크 버튼을 표시해야 한다. 기존 게시글 카드가 있다면 재사용한다.
- 항목 선택 시 게시글 상세로 이동해야 한다.
- 북마크 해제 시 해당 항목을 목록에서 즉시 제거하고, 실패하면 원래 위치에 복원해야 한다.
- 최초 로딩, 다음 페이지 로딩, 빈 목록, 오류 상태를 각각 제공해야 한다.
- 빈 목록에는 `아직 북마크한 게시글이 없습니다` 안내와 게시글 탐색 화면으로 이동하는 동작을 제공해야 한다.
- 오류 상태에는 재시도 동작을 제공해야 한다.
- 페이지당 20개를 기본값으로 하며, 데이터 증가에 대응할 수 있도록 커서 기반 페이지네이션 또는 무한 스크롤을 사용해야 한다.

### FR-7. 게시글 삭제 및 접근 제한

- 삭제된 게시글에 연결된 북마크는 함께 삭제되어야 한다.
- 사용자가 더 이상 조회 권한이 없는 게시글은 북마크 목록 결과에 포함하지 않아야 한다.
- 목록 조회와 상세 조회의 게시글 접근 정책이 일치해야 한다.

### FR-8. 사용자 피드백

- 추가·해제 성공은 버튼 상태 변화만으로 명확한 경우 별도 토스트를 필수로 하지 않는다.
- 요청 실패 시 `북마크를 저장하지 못했습니다. 다시 시도해 주세요.` 또는 동등한 메시지를 표시해야 한다.
- 실패 메시지가 표시되어도 사용자의 게시글 탐색을 막지 않아야 한다.

## 9. 데이터 요구사항

### 9.1 제안 스키마

기존 테이블 명과 키 타입에 맞게 조정하되 다음 제약을 충족해야 한다.

```sql
create table public.bookmarks (
  user_id uuid not null references auth.users(id) on delete cascade,
  post_id uuid not null references public.posts(id) on delete cascade,
  created_at timestamptz not null default now(),
  primary key (user_id, post_id)
);

create index bookmarks_user_created_at_idx
  on public.bookmarks (user_id, created_at desc);
```

- 복합 기본 키 또는 동등한 unique 제약으로 중복 북마크를 차단한다.
- `created_at`은 서버에서 생성하고 최신 북마크순 정렬 및 페이지네이션에 사용한다.
- 전체 사용자 대상 게시글별 북마크 상태 일괄 조회가 필요하다면 실제 쿼리 패턴을 측정한 뒤 `post_id` 인덱스를 추가한다.

### 9.2 Row Level Security

`bookmarks`에 RLS를 활성화하고 다음 원칙을 적용한다.

- `SELECT`: `auth.uid() = user_id`인 행만 허용
- `INSERT`: `auth.uid() = user_id`인 행만 허용
- `DELETE`: `auth.uid() = user_id`인 행만 허용
- 클라이언트가 다른 사용자의 `user_id`로 생성·조회·삭제할 수 없어야 한다.
- service role key를 브라우저 번들 또는 공개 환경 변수에 포함하지 않는다.
- 게시글 접근 제한이 있다면 목록 join 또는 서버 조회 계층에서도 해당 정책을 적용한다.

## 10. 기술 및 인터페이스 요구사항

### 10.1 상태 관리

- 서버 상태는 React Query를 단일 기준으로 사용한다.
- 권장 query key는 다음과 같다.
  - 게시글별 상태: `['bookmark', postId]`
  - 마이페이지 목록: `['bookmarks', { cursor, limit }]`
- 북마크 추가·해제 mutation은 요청 전 캐시 취소 및 스냅샷, 낙관적 변경, 오류 시 롤백, 완료 후 invalidate 순서를 따른다.
- 초기 렌더링 시 사용자별 데이터가 다른 사용자에게 노출되지 않도록 로그아웃 또는 사용자 변경 시 사용자 전용 캐시를 제거하거나 query key에 사용자 식별자를 포함한다.

### 10.2 데이터 접근

- Supabase 클라이언트 직접 접근 또는 Next.js Route Handler/Server Action 중 기존 프로젝트 패턴과 일치하는 방식을 사용한다.
- 어떤 방식을 사용하더라도 최종 권한 검증은 Supabase RLS에서 수행해야 한다.
- 추가는 `upsert` 또는 중복 키를 정상 상태로 해석하는 방식으로 멱등성을 보장한다.
- 해제는 현재 로그인 사용자와 `post_id`를 모두 조건으로 사용한다.
- 목록 응답은 UI 렌더링에 필요한 게시글 필드만 조회하고, 다음 페이지용 커서를 포함해야 한다.
- 클라이언트가 전달한 `user_id`만 신뢰해서는 안 되며 인증 세션의 사용자와 일치해야 한다.

### 10.3 렌더링

- 북마크 버튼과 mutation 로직은 Client Component로 구현할 수 있다.
- 마이페이지의 초기 데이터는 기존 앱의 패턴에 따라 Server Component에서 prefetch/dehydrate하거나 클라이언트에서 조회할 수 있다.
- 어느 방식을 선택하든 hydration 전후의 북마크 상태가 뒤집혀 보이지 않아야 한다.

## 11. 비기능 요구사항

### 성능

- 북마크 추가·해제 요청의 p95 응답 시간 목표는 정상 네트워크 기준 500ms 이내로 한다.
- 북마크 목록 최초 조회의 p95 응답 시간 목표는 1초 이내로 한다.
- 목록은 필요한 컬럼만 선택하며 한 번에 최대 20개 게시글을 반환한다.
- 게시글 목록의 북마크 상태는 게시글마다 개별 네트워크 요청을 보내는 N+1 패턴을 피하고 일괄 조회한다.

### 보안 및 개인정보

- 사용자의 북마크 목록은 기본적으로 비공개다.
- 다른 사용자의 북마크 존재 여부나 목록을 API 응답으로 노출하지 않는다.
- 모든 변경 요청은 유효한 인증 세션과 RLS 정책을 통과해야 한다.
- 오류 응답에 내부 SQL, 키 또는 사용자 정보를 포함하지 않는다.

### 접근성

- 버튼은 키보드로 접근하고 Enter 또는 Space로 실행할 수 있어야 한다.
- 상태에 따라 `북마크 추가`와 `북마크 해제` 등 명확한 접근성 이름을 제공한다.
- 처리 중에는 `aria-busy` 또는 동등한 상태를 전달한다.
- 포커스 표시와 색상 대비는 서비스의 접근성 기준을 충족한다.

### 호환성

- 서비스가 공식 지원하는 데스크톱 및 모바일 브라우저에서 동일한 핵심 기능을 제공한다.
- 작은 화면에서도 버튼 터치 영역은 최소 44×44px을 권장한다.

## 12. 분석 이벤트

기존 분석 도구가 있는 경우 아래 이벤트를 기록한다. 이벤트에는 내부 사용자 식별 정책을 적용하고 게시글 본문 등 불필요한 개인정보는 담지 않는다.

| 이벤트 | 시점 | 필수 속성 |
| --- | --- | --- |
| `bookmark_add_succeeded` | 북마크 추가 성공 | `post_id`, `surface` |
| `bookmark_remove_succeeded` | 북마크 해제 성공 | `post_id`, `surface` |
| `bookmark_action_failed` | 추가 또는 해제 실패 | `post_id`, `action`, `surface`, `error_category` |
| `bookmark_list_viewed` | 마이페이지 목록 진입 | `item_count` |
| `bookmark_post_opened` | 북마크 목록에서 상세 진입 | `post_id`, `position` |

`surface` 값은 최소 `post_detail`, `post_list`, `mypage_bookmarks`를 구분한다.

## 13. 수용 기준

### AC-1. 추가 및 지속성

- Given 로그인 사용자가 북마크하지 않은 게시글을 보고 있을 때
- When 북마크 버튼을 누르면
- Then 버튼이 즉시 활성 상태가 되고 데이터베이스에 사용자·게시글 조합이 1개 저장된다.
- And 새로고침 후에도 활성 상태가 유지된다.

### AC-2. 중복 방지

- Given 동일 게시글에 대한 추가 요청이 중복 전송될 때
- When 모든 요청이 완료되면
- Then 데이터베이스에는 해당 사용자·게시글 조합이 1개만 존재한다.

### AC-3. 해제

- Given 로그인 사용자가 북마크한 게시글을 보고 있을 때
- When 활성 북마크 버튼을 누르면
- Then 버튼이 즉시 비활성 상태가 되고 해당 북마크가 삭제된다.

### AC-4. 실패 롤백

- Given 추가 또는 해제 요청이 실패할 때
- When 서버 오류가 반환되면
- Then 버튼 및 목록은 요청 전 상태로 복원되고 재시도 가능한 오류 안내가 표시된다.

### AC-5. 비로그인 사용자

- Given 비로그인 사용자가 게시글을 보고 있을 때
- When 북마크 버튼을 누르면
- Then 로그인 필요 안내가 표시되고 로그인 화면으로 이동할 수 있다.
- And 로그인 전에는 북마크 데이터가 생성되지 않는다.

### AC-6. 목록 조회

- Given 여러 게시글을 북마크한 로그인 사용자가 있을 때
- When `/mypage/bookmarks`에 진입하면
- Then 본인의 북마크만 최신 북마크순으로 표시된다.
- And 항목을 선택하면 해당 게시글 상세로 이동한다.

### AC-7. 목록 내 해제

- Given 마이페이지 북마크 목록이 표시된 상태에서
- When 사용자가 항목의 북마크를 해제하면
- Then 해당 항목이 즉시 목록에서 제거된다.
- And 실패 시 원래 위치에 복원된다.

### AC-8. 빈 목록 및 페이지네이션

- Given 북마크가 없는 사용자가 목록에 진입하면
- Then 빈 상태 안내와 게시글 탐색 동작이 표시된다.
- Given 북마크가 20개를 초과하면
- Then 사용자는 중복·누락 없이 다음 항목을 불러올 수 있다.

### AC-9. 권한 분리

- Given 사용자 A가 사용자 B의 북마크를 조회하거나 삭제하려 할 때
- When Supabase에 요청하면
- Then RLS에 의해 결과가 노출되지 않거나 요청이 거부된다.

### AC-10. 삭제 게시글

- Given 북마크된 게시글이 삭제될 때
- When 사용자가 북마크 목록을 다시 조회하면
- Then 해당 게시글이 표시되지 않고 연결 북마크도 남지 않는다.

## 14. 테스트 범위

- 단위 테스트
  - 북마크 버튼의 각 상태와 접근성 이름
  - 낙관적 업데이트, 실패 롤백, 캐시 무효화
  - 로그인 유도 및 복귀 URL 생성
- 통합 테스트
  - 중복 추가의 멱등성
  - 추가·해제 후 목록 및 상세 상태 동기화
  - 정렬, 커서 페이지네이션, 빈 상태, 오류 재시도
  - 게시글 삭제 시 cascade 동작
- 보안 테스트
  - 미인증 사용자의 select/insert/delete 차단
  - 다른 사용자 행의 조회·생성·삭제 차단
  - service role key의 클라이언트 번들 미포함 확인
- E2E 테스트
  - 로그인 → 게시글 북마크 → 마이페이지 확인 → 상세 진입 → 북마크 해제
  - 네트워크 실패 시 UI 롤백
  - 모바일 뷰포트와 키보드 조작

3. 내부 또는 스테이징 환경에서 기능·성능·접근성 테스트를 수행한다.
