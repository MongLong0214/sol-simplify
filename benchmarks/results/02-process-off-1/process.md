# 개발 프로세스 및 검증 체계

## 1. 문서의 목적

이 문서는 AI 코딩 에이전트 평가 도구의 개발, 검증, 릴리스, 유지보수에 적용할 최소 품질 기준을 정의한다. 프로젝트의 메인테이너가 한 명이라는 현실을 전제로 하며, 사람 수로 품질을 보완하기보다 자동화, 재현 가능한 증거, 작은 변경, 명시적인 위험 관리로 품질을 보장한다.

이 문서에서 `MUST`, `SHOULD`, `MAY`는 각각 필수, 특별한 사유가 없으면 준수, 선택 사항을 뜻한다. 예외를 적용할 때는 이슈나 릴리스 노트에 이유와 후속 조치를 기록한다.

## 2. 품질 목표와 불변 조건

모든 변경은 다음 특성을 지향한다.

- **정확성:** 동일한 입력과 통제된 환경에서 동일한 판정이 나와야 한다.
- **재현성:** 제3자가 버전, 설정, 입력 아티팩트만으로 결과를 다시 만들 수 있어야 한다.
- **공정성:** 특정 에이전트나 공급자에 유리한 숨은 가정이 없어야 한다.
- **격리성:** 평가 대상 코드는 호스트, 비밀정보, 다른 평가 실행에 영향을 줄 수 없어야 한다.
- **설명 가능성:** 총점은 개별 과제, 판정 규칙, 원시 증거로 추적 가능해야 한다.
- **호환성:** 점수의 의미가 바뀌는 변경은 명시적으로 버전이 달라져야 한다.
- **운영 가능성:** 한 명의 메인테이너가 반복해서 실행하고 문제를 진단할 수 있어야 한다.

다음은 타협하지 않는 불변 조건이다.

1. 최종 점수만 저장하지 않는다. 점수를 만든 입력, 이벤트, 판정, 오류, 환경 메타데이터를 함께 저장한다.
2. 모델의 자기 보고나 LLM 심사 결과만으로 정답 여부를 판정하지 않는다.
3. 실패, 시간 초과, 도구 오류, 누락값을 임의의 성공이나 0점으로 조용히 변환하지 않는다.
4. 서로 다른 벤치마크·채점기 버전의 점수를 같은 척도처럼 비교하지 않는다.
5. 외부 기여자의 코드를 비밀정보가 있는 실행기에서 검증하지 않는다.
6. 비결정적 실패를 단순 재실행으로 숨기지 않는다.

## 3. 품질 대상과 버전 경계

평가 시스템을 하나의 프로그램이 아니라 다음 독립 구성요소로 관리한다.

| 구성요소 | 책임 | 별도 버전이 필요한 이유 |
|---|---|---|
| CLI/API | 사용자 입력, 실행 제어, 결과 출력 | 사용법과 공개 계약의 호환성 |
| 실행 하네스 | 에이전트 실행, 도구 제공, 제한 적용 | 실행 조건이 결과에 직접 영향 |
| 에이전트 어댑터 | 공급자별 요청·응답 변환 | 외부 API 변화와 공급자 편향 분리 |
| 과제 모음 | 저장소, 요구사항, 테스트, 정답 근거 | 데이터 오염과 과제 변경 추적 |
| 채점기 | 판정 규칙과 부분 점수 계산 | 점수 의미의 변경 추적 |
| 결과 스키마 | 실행 기록과 리포트 형식 | 데이터 소비자의 호환성 |

모든 결과에는 최소한 다음을 기록한다.

- 도구, 하네스, 과제 모음, 채점기, 결과 스키마의 버전
- 가능하면 각 구성요소의 Git 커밋 SHA와 작업 트리 상태
- 에이전트/모델의 정확한 식별자와 공급자, 어댑터 버전
- 프롬프트, 도구 권한, 예산, 제한 시간, 재시도 정책, 난수 시드
- OS, 아키텍처, 런타임, 컨테이너 이미지 digest, 주요 도구 버전
- 실행 시작·종료 시각, 종료 사유, 비용 및 토큰/도구 사용량
- 입력 및 산출물의 콘텐츠 해시, 원시 이벤트 로그 위치

점수에 영향을 주는 변경은 최소한 과제 모음 또는 채점기 버전을 올린다. 이전 결과와 비교 가능하지 않다면 새 결과 집합으로 명시한다.

## 4. 저장소를 만들 때 먼저 추가할 것

구현을 시작하기 전에 다음 기반을 만든다.

- `README.md`: 문제 정의, 비목표, 빠른 시작, 현재 성숙도
- `LICENSE`: 코드 라이선스
- `CONTRIBUTING.md`: 로컬 검증 명령, 변경 절차, 기여 범위
- `SECURITY.md`: 취약점 비공개 신고 경로와 지원 버전
- `CODE_OF_CONDUCT.md`: 커뮤니티 행동 규범
- `CHANGELOG.md`: 사용자에게 보이는 변경과 호환성 파괴 기록
- `docs/architecture.md`: 신뢰 경계, 주요 컴포넌트, 데이터 흐름
- `docs/scoring.md`: 점수 정의, 집계 방식, 실패 처리, 한계
- `docs/benchmark-policy.md`: 과제 출처, 라이선스, 오염 방지 정책
- `docs/adr/`: 되돌리기 어렵거나 점수에 영향을 주는 결정 기록
- 이슈/PR 템플릿과 의존성·보안 업데이트 자동화

언어를 선택한 뒤 로컬과 CI가 같은 진입점을 사용하도록 다음 명령 계약을 제공한다. 실제 구현은 해당 생태계의 태스크 러너로 대체할 수 있지만 이름과 의미는 안정적으로 유지한다.

```text
verify:fast       포맷, 정적 분석, 단위·계약 테스트
verify:full       fast + 통합·E2E·보안·패키징 검증
verify:benchmark  고정된 기준 에이전트로 회귀 평가
verify:release    full + 재현 빌드·릴리스 아티팩트 검증
```

CI 전용 우회 경로를 만들지 않는다. 개발자가 한 명이어도 기본 브랜치는 직접 푸시보다 PR과 필수 상태 검사를 거치도록 보호한다.

## 5. 변경 단위와 개발 흐름

### 5.1 변경 시작

버그 수정 이상의 변경은 이슈에 다음을 짧게 기록한다.

- 해결할 문제와 사용자가 관찰할 결과
- 범위와 명시적인 비범위
- 수용 기준
- 위험 등급
- 필요한 테스트와 결과 호환성 영향

다음 중 하나에 해당하면 구현 전에 ADR 또는 간단한 설계 문서를 작성한다.

- 공개 API나 결과 스키마를 바꾸는 경우
- 샌드박스, 권한, 네트워크 정책을 바꾸는 경우
- 과제, 채점 규칙, 점수 집계 방식을 바꾸는 경우
- 새 외부 서비스 또는 핵심 의존성을 도입하는 경우
- 데이터 마이그레이션이나 호환성 파괴가 있는 경우

### 5.2 구현

- 한 변경은 하나의 검증 가능한 목적만 가진다.
- 기능 변경과 대규모 포맷/리팩터링을 같은 커밋에 섞지 않는다.
- 가능하면 테스트를 먼저 추가하거나, 최소한 같은 PR에서 실패 재현과 수정 검증을 함께 제공한다.
- 네트워크, 시간, 난수, 파일시스템, 모델 API는 경계 인터페이스 뒤에 둔다.
- 평가 핵심 로직은 외부 API 없이 결정적으로 테스트할 수 있어야 한다.
- 새 동작에는 정상 경로뿐 아니라 거부, 시간 초과, 부분 출력, 손상된 출력 테스트를 포함한다.

### 5.3 자기 리뷰

혼자 유지보수하더라도 작성 직후 바로 병합하지 않는다. diff를 처음부터 다시 읽고 다음을 확인한다.

- 수용 기준과 실제 테스트가 일치하는가
- 결과가 좋아 보이게 만드는 편향이나 암묵적 재시도가 추가되지 않았는가
- 실패가 구조화된 오류와 종료 사유로 보존되는가
- 로그, fixture, 오류 메시지에 토큰·개인정보·저장소 비밀이 남지 않는가
- 공개 계약, 문서, 예제가 함께 갱신되었는가
- 삭제하거나 단순화할 수 있는 코드가 없는가

점수, 샌드박스, 인증, 릴리스에 영향을 주는 고위험 변경은 CI 통과 후 가급적 다음 날 다시 검토한다. 긴급 보안 수정은 예외로 하되, 사후 이슈를 남긴다.

### 5.4 완료 정의

변경은 다음 조건을 모두 만족할 때 완료다.

- 수용 기준이 테스트 또는 명시적 검증 기록으로 입증됨
- 해당 위험 등급의 필수 검사가 모두 통과함
- 새 경고와 원인 불명 재시도가 없음
- 사용자 동작, 공개 계약, 점수 의미가 바뀌면 문서와 변경 로그가 갱신됨
- 결과 스키마나 데이터 변경에는 호환성/마이그레이션 검증이 있음
- CI에서 생성한 로그와 리포트로 실패 원인을 추적할 수 있음

## 6. 위험 기반 품질 게이트

변경마다 가장 높은 해당 등급을 적용한다.

| 등급 | 예시 | 병합 전 필수 게이트 |
|---|---|---|
| R0 문서 | 오탈자, 링크, 설명 보완 | 문서 lint, 링크 검사, 예제 구문 검사 |
| R1 일반 | UI/CLI 개선, 내부 리팩터링, 비핵심 기능 | fast 검증, 관련 통합 테스트, 회귀 테스트 |
| R2 결과 영향 | 하네스, 어댑터, 과제, 채점, 집계, 스키마 | full 검증, 기준 실행 비교, 통계적 회귀 분석, 버전 검토 |
| R3 보안/릴리스 | 샌드박스, 권한, 비밀정보, 업데이트, 배포 | R2 전체, 위협 모델 검토, 공격 테스트, 릴리스 리허설과 롤백 확인 |

필수 검사 우회는 자동으로 정상 병합과 동일하게 취급하지 않는다. 우회 사유, 영향 범위, 후속 이슈를 기록하고 다음 정식 릴리스 전 해결한다.

## 7. 테스트 및 검증 구조

### 7.1 정적 검증

모든 PR에서 다음을 자동화한다.

- 포맷 검사와 lint
- 가능한 언어에서는 엄격한 타입 검사
- 빌드 및 패키지 메타데이터 검사
- 공개 API/스키마의 호환성 검사
- 문서 링크와 실행 가능한 예제 검사
- 비밀정보, 알려진 취약점, 라이선스, 잠금 파일 검사

경고는 무시 가능한 배경 소음으로 쌓아두지 않는다. 새 경고를 허용하지 않고 기존 경고 수는 기준값으로 고정한 뒤 줄여 나간다.

### 7.2 단위 테스트

단위 테스트는 외부 네트워크 없이 빠르고 결정적으로 실행되어야 한다. 특히 다음 로직을 집중 검증한다.

- 점수와 부분 점수 계산, 반올림, 집계
- 시간 초과·실패·누락·중단 상태 변환
- 예산과 사용량 계산
- 설정 병합과 기본값
- 경로 정규화와 작업공간 경계
- 결과 직렬화/역직렬화 및 스키마 검증
- 로그 비식별화와 비밀정보 마스킹

경계값, 빈 입력, 매우 큰 입력, 잘못된 인코딩, 순서 변화도 포함한다. 핵심 채점 함수에는 속성 기반 테스트와 mutation testing을 적용해 "코드는 실행됐지만 검증은 못 한" 테스트를 찾는다.

커버리지는 목표가 아니라 누락 탐지 장치로 사용한다. 초기 기준선을 기록하고 하락을 막는 ratchet 방식으로 운영하며, 채점·권한·스키마 핵심 모듈은 별도로 높은 분기 커버리지를 요구한다. 숫자를 맞추기 위한 무의미한 테스트는 추가하지 않는다.

### 7.3 계약 테스트

각 에이전트 어댑터와 결과 소비자는 버전이 지정된 공통 계약을 통과해야 한다.

- 요청, 이벤트 스트림, 도구 호출, 종료 상태의 스키마
- 알 수 없는 필드와 이전/다음 스키마 버전 처리
- 부분 스트림, 중복 이벤트, 순서가 뒤바뀐 이벤트
- rate limit, 인증 실패, 공급자 오류, 취소
- 사용량 데이터가 없거나 공급자 형식이 바뀐 경우

실제 응답을 그대로 fixture로 저장할 때는 비밀정보와 개인정보를 제거하고 출처·캡처 날짜·어댑터 버전을 기록한다.

### 7.4 통합 테스트

가짜 서버 또는 기록 후 재생 가능한 응답으로 다음 경계를 검증한다.

- CLI/API → 하네스 → 어댑터 → 이벤트 저장 → 채점 → 리포트
- 프로세스 강제 종료, 시간 초과, 디스크 부족, 손상된 캐시
- 재시작과 중단된 실행 복구
- 병렬 실행 간 파일·포트·상태 격리
- 지원 OS와 파일 경로 차이

실제 모델 호출은 비용과 변동성이 있으므로 일반 PR의 유일한 게이트로 삼지 않는다.

### 7.5 종단간 테스트

작고 의도적으로 설계한 fixture 저장소를 사용한다. 각 저장소는 다음 사례 중 하나만 명확히 검증한다.

- 완전 성공
- 컴파일은 되지만 요구사항을 위반한 구현
- 일부 테스트만 통과한 구현
- 테스트를 변조하거나 삭제하려는 구현
- 작업공간 밖 접근, 네트워크 접근, 비밀정보 읽기 시도
- 무한 루프, 과도한 출력, 프로세스 누수
- 에이전트가 중간에 실패하거나 잘못된 프로토콜을 반환하는 경우

fixture는 작고 독립적이어야 하며 기대 결과와 존재 이유를 문서화한다. golden 파일 변경은 일반 코드 변경처럼 검토하며, 단순히 새 출력으로 덮어쓴 뒤 승인하지 않는다.

### 7.6 실제 공급자 테스트

실제 API를 사용하는 테스트는 별도 분류한다.

- PR: 수동 실행 또는 명시적으로 승인된 경우만 실행
- 기본 브랜치: 비용이 제한된 주기적 smoke test
- 릴리스 후보: 지원한다고 명시한 공급자별 최소 1회 검증

이 테스트는 정확한 모델 ID, 날짜, 지역, 설정, 비용을 기록한다. 실패 시 제품 결함, 외부 서비스 장애, 통계적 변동을 구분하며, 무제한 자동 재시도를 금지한다.

## 8. 평가 도구 자체의 유효성 검증

일반 소프트웨어 테스트만으로 "좋은 평가"를 보장할 수 없다. 벤치마크와 채점 체계에는 별도 검증이 필요하다.

### 8.1 과제 설계

각 과제는 다음 명세를 가진다.

- 측정하려는 능력과 측정하지 않는 능력
- 입력 저장소와 요구사항의 출처, 라이선스, 해시
- 성공 조건, 부분 점수, 실패 조건
- 허용 도구, 네트워크, 시간, 토큰/비용 예산
- 공개 테스트와 숨은 검증의 역할
- 알려진 우회 방법과 오염 가능성
- 난이도 근거와 최소 1개의 실패 사례

과제는 한 번 공개된 뒤 조용히 수정하지 않는다. 오타처럼 결과에 영향이 없는 수정도 해시와 변경 기록을 남긴다. 정답 유출이나 심각한 결함은 해당 버전을 폐기하고 새 버전으로 교체한다.

공개 오픈소스 프로젝트에서 완전한 비공개 holdout을 영구 유지하기 어렵다는 점을 명시한다. 가능하면 공개 개발 세트와 릴리스용 holdout을 분리하고, holdout 접근을 최소화하며 주기적으로 교체한다. 과제 출처가 모델 학습 데이터에 포함되었을 가능성도 결과 한계로 공개한다.

숨은 테스트와 정답 데이터는 에이전트 작업 단계에 마운트하지 않는다. 에이전트 프로세스가 종료된 뒤 별도 판정 단계에서 읽기 전용으로 제공하며, 작업공간 안의 테스트 결과나 채점기 파일을 신뢰하지 않는다.

### 8.2 채점 원칙

- 빌드, 테스트, 정적 분석, 파일 diff처럼 관찰 가능한 증거를 우선한다.
- 원래 테스트를 통과한 것과 에이전트가 테스트를 약화시킨 것을 구분한다.
- 테스트 파일 삭제, 검사 우회, 하네스 변조는 별도 무결성 실패로 기록한다.
- 스타일, 설명 품질처럼 주관적 판단은 기능 정확성과 분리해 보고한다.
- LLM judge가 필요하면 단독 판정자가 아니라 명시된 rubric을 적용하는 보조 신호로 사용한다.
- LLM judge의 모델·프롬프트·샘플링 설정도 채점기 버전에 포함한다.
- 총점 집계 전에 과제별 원점수와 실패 이유를 공개한다.
- 평균만 보고하지 않고 성공률, 분포, 표본 수, 변동성을 함께 보고한다.

여러 범주를 합칠 때는 사전에 가중치를 정하고 macro/micro 평균 중 무엇인지 명시한다. 타임아웃과 인프라 실패의 점수 처리 규칙도 실행 전에 고정한다.

### 8.3 채점기 검증 세트

각 채점 규칙에는 다음이 포함된 작은 정답 코퍼스를 유지한다.

- 명백한 성공/실패
- 경계에 있는 부분 성공
- 채점기를 속이려는 적대적 제출물
- 과거 실제 오판을 재현하는 제출물

정답 코퍼스는 사람이 기대 판정과 근거를 기록한다. 채점기 변경 시 혼동 행렬, 기존 오판의 수정 여부, 새 오판을 비교한다. 주관적 rubric은 정기적으로 표본을 사람이 재검토하고, 불일치는 rubric 또는 자동 판정의 결함으로 추적한다.

### 8.4 비결정성과 통계

에이전트 비교는 가능한 한 같은 과제, 환경, 예산, 실행 순서 정책을 사용한다. 변동성이 있는 평가에는 다음을 적용한다.

- 사전에 반복 횟수와 중단 규칙을 정한다.
- 지원되는 경우 시드를 기록하되, 시드만으로 결정성이 보장된다고 가정하지 않는다.
- 단일 최고 실행보다 전체 반복 결과를 보고한다.
- 평균/중앙값과 함께 신뢰구간 또는 bootstrap 구간을 제시한다.
- 동일 과제를 비교할 때는 paired 분석을 우선한다.
- 차이가 측정 잡음보다 작은 경우 우열이 아니라 "구분 불가"로 표현한다.
- 공급자 모델이 조용히 변경될 수 있으므로 실행 시점과 실제 응답 메타데이터를 보존한다.

회귀 임계값은 기준 데이터의 변동성을 측정한 뒤 정한다. 임의의 고정 퍼센트를 처음부터 과학적 기준처럼 사용하지 않는다.

## 9. 보안과 격리 검증

평가 대상 코드, 벤치마크 fixture, 외부 PR은 모두 신뢰하지 않는 입력이다.

기본 실행 정책은 다음과 같다.

- 일회성 컨테이너 또는 동등한 샌드박스 사용
- 읽기 전용 기반 이미지와 실행별 새 작업공간
- 기본 네트워크 차단, 필요한 경우 목적지 allowlist
- CPU, 메모리, 디스크, 프로세스 수, 실행 시간, 출력 크기 제한
- 호스트 소켓, SSH 에이전트, 클라우드 자격증명, 사용자 홈 디렉터리 비노출
- 최소 권한의 비루트 사용자
- 실행 종료 후 자식 프로세스와 임시 리소스 정리
- 로그·리포트 저장 전에 비밀정보와 개인정보 마스킹
- 판정 컨트롤러, 숨은 테스트, 기준 정답, 원시 결과 저장소를 대상 작업공간 밖에 배치

R3 변경과 정기 보안 검증에서는 탈출 시도, 심볼릭 링크/경로 순회, fork bomb, 대용량 출력, 로컬 서비스 탐색, 프롬프트 인젝션이 포함된 저장소 콘텐츠를 시험한다.

CI는 신뢰 수준을 분리한다. 외부 fork PR에서는 쓰기 토큰, 패키지 배포 토큰, 실제 모델 API 키를 제공하지 않는다. 공급망 검증에는 잠금 파일, 의존성 출처, 취약점 스캔, 라이선스 검사, 생성 아티팩트의 SBOM과 체크섬을 포함한다. 릴리스는 가능하면 서명하고 provenance를 제공한다.

## 10. CI 운영 모델

### PR 필수 검사

R0/R1의 일반 피드백 목표 시간은 약 10분 이내로 유지한다. R2/R3는 빠른 검사를 먼저 보여준 뒤 비용이 큰 필수 검사를 별도 작업으로 계속 실행할 수 있으나, 전체 통과 전에는 병합하지 않는다.

1. 포맷, lint, 타입, 빌드
2. 단위·계약 테스트
3. 작은 통합 및 E2E smoke test
4. 스키마 호환성, 문서, 비밀정보, 의존성 검사
5. 변경된 핵심 모듈의 커버리지 하락 검사

### 기본 브랜치 및 야간 검사

- 전체 통합/E2E와 지원 플랫폼 매트릭스
- mutation/property/fuzz 테스트의 비용 큰 부분
- 샌드박스 공격 회귀 테스트
- 실제 공급자 smoke test
- 기준 에이전트 반복 실행과 변동성 감시
- 의존성 및 컨테이너 취약점 스캔

### CI 규율

- 실패한 테스트는 재실행 전에 첫 실패 로그를 보존한다.
- 테스트 재시도 횟수는 제한하고, 첫 실패가 있으면 flaky로 별도 집계한다.
- flaky 테스트를 조용히 격리하거나 영구 skip하지 않는다. 담당 이슈와 만료일을 둔다.
- 캐시는 성능 최적화일 뿐 정확성 전제가 아니다. 주기적으로 캐시 없는 실행을 한다.
- 테스트 순서 의존성을 찾기 위해 주기적으로 순서를 무작위화한다.
- CI 아티팩트에는 테스트 리포트, 기준 비교, 스키마 검사, 보안 결과를 남긴다.

## 11. 릴리스 절차

Semantic Versioning을 기본으로 하되, CLI/라이브러리 버전과 벤치마크·채점기 버전을 별도로 표시한다.

### 릴리스 후보 체크리스트

1. 릴리스 커밋을 고정하고 작업 트리가 깨끗한지 확인한다.
2. 깨끗한 환경에서 `verify:release`를 실행한다.
3. 고정된 canary fixture/에이전트 결과를 이전 호환 버전과 비교한다.
4. 점수 변화가 의도된 것인지 개별 과제 수준에서 설명한다.
5. 패키지 설치, 최소 실행, 제거를 지원 환경에서 시험한다.
6. 결과 스키마 호환성과 마이그레이션을 시험한다.
7. 변경 로그, 알려진 한계, 보안 영향, 지원 버전을 갱신한다.
8. 릴리스 아티팩트의 내용물, 체크섬, SBOM, provenance를 검증한다.
9. 테스트한 바로 그 커밋과 아티팩트만 태그하고 배포한다.
10. 새 환경에서 배포된 패키지를 다시 설치해 smoke test한다.

릴리스 채널은 초기에는 `pre-release`와 `stable` 두 개면 충분하다. 평가 결과 형식이나 점수 의미가 안정되기 전에는 `0.x`로 명확히 표시하고, 실험적 기능은 기본 경로에서 분리한다.

릴리스 후 심각한 결함이 발견되면 기존 태그를 덮어쓰지 않는다. 새 패치 버전을 발행하거나 취약한 버전을 폐기하고, 영향받은 평가 결과를 식별할 수 있는 공지를 남긴다.

## 12. 결함 분류와 대응

| 심각도 | 기준 | 기본 대응 |
|---|---|---|
| Critical | 샌드박스 탈출, 자격증명 노출, 임의 코드 실행 경계 붕괴 | 공개 전 비공개 처리, 영향 버전 폐기 검토, 긴급 패치 |
| High | 광범위한 오채점, 결과 손상, 재현 불가 릴리스 | 릴리스 중단, 영향 결과 표시, 우선 수정 |
| Medium | 특정 어댑터/플랫폼 실패, 제한적 오판 | 알려진 문제 기록, 다음 패치 계획 |
| Low | 문서, 메시지, 비핵심 UX 문제 | 일반 백로그 |

한 명의 메인테이너이므로 응답 시간을 보장하는 SLA는 약속하지 않는다. 대신 보안 신고 접수 방식, 현재 지원 버전, 수정 또는 폐기 여부를 투명하게 기록한다.

모든 회귀 수정에는 다음이 필요하다.

1. 실패를 재현하는 최소 테스트 또는 fixture
2. 근본 원인 설명
3. 같은 계열의 문제가 있는 경계 점검
4. 검증 증거와 영향받은 버전/결과 식별

## 13. 프로젝트 건강 지표

점수 자체와 개발 품질 지표를 섞지 않는다. 월별 또는 릴리스별로 다음을 가볍게 확인한다.

- 기본 브랜치 CI 성공률과 중앙 실행 시간
- flaky 테스트 비율과 미해결 기간
- 릴리스 후 발견된 회귀 수
- 채점 정답 코퍼스의 오탐/미탐
- 동일 조건 반복 실행의 점수 분산
- 재현에 실패한 공개 결과 수
- 샌드박스/보안 검사 실패 수
- 핵심 모듈 mutation score 및 커버리지 추세
- 열린 Critical/High 이슈와 지원되지 않는 의존성 수

지표는 목표를 왜곡시키지 않도록 추세와 원인을 본다. 테스트 수, 코드 줄 수, 전체 평균 커버리지를 단독 성공 지표로 사용하지 않는다.

## 14. 1인 메인테이너를 위한 운영 원칙

- 동시에 진행하는 큰 기능은 하나로 제한한다.
- 자동화 비용이 반복 수작업 비용보다 작아지는 두 번째 반복부터 자동화한다.
- 모든 플랫폼을 약속하지 말고 CI에서 지속 검증할 수 있는 플랫폼만 지원한다.
- 어댑터 수를 늘리기 전에 공통 계약과 fixture가 안정되었는지 확인한다.
- 외부 기여는 작은 PR, 테스트 포함, 명확한 라이선스 조건을 요구한다.
- 메인테이너만 아는 복구 절차가 없도록 릴리스와 결과 재현 명령을 문서화한다.
- 번아웃을 유발하는 상시 대응 약속보다 명시적인 지원 범위와 릴리스 주기를 택한다.

## 15. 최초 구현 순서

다음 순서로 얇은 수직 단면을 완성한 후 범위를 확장한다.

1. 품질 목표, 비목표, 위협 모델, 결과 스키마 초안
2. 하나의 작은 fixture 과제와 사람이 검증한 기대 결과
3. 모델 호출 없이 동작하는 가짜 에이전트 어댑터
4. 격리된 실행 하네스와 구조화된 이벤트 로그
5. 결정적 채점기와 단위·계약·E2E 테스트
6. 재현 메타데이터가 포함된 사람이 읽을 수 있는 리포트
7. PR CI와 깨끗한 환경의 패키지 smoke test
8. 하나의 실제 공급자 어댑터와 제한된 live test
9. 반복 실행을 통한 변동성 측정 및 회귀 기준 설정
10. 첫 pre-release와 설치 후 재검증

첫 pre-release 전에는 최소한 다음 질문에 실제 실행 결과로 답할 수 있어야 한다.

- 같은 fixture를 다시 실행했을 때 왜 같은 판정이 나왔는가?
- 점수 한 점을 원시 증거까지 역추적할 수 있는가?
- 대상 코드가 테스트를 삭제하거나 호스트 비밀정보를 읽으려 하면 막히는가?
- 실행 중단, 공급자 오류, 하네스 오류를 결과에서 구분할 수 있는가?
- 다른 컴퓨터의 깨끗한 환경에서 배포 패키지를 설치하고 같은 fixture를 실행할 수 있는가?
- 채점기 변경이 과거 결과의 의미를 바꾸는지 자동으로 탐지할 수 있는가?

하나라도 증거로 답할 수 없다면 기능 추가보다 해당 검증 경로를 먼저 완성한다.

## 16. 문서 유지

이 문서는 살아 있는 정책이다. 다음 경우 검토한다.

- 첫 공개 릴리스 전
- 점수 체계나 샌드박스 구조가 바뀔 때
- Critical/High 결함의 사후 분석 후
- 유지 비용 때문에 절차가 반복해서 우회될 때

절차가 현실과 맞지 않으면 조용히 무시하지 않고 문서를 수정한다. 품질 게이트를 낮추는 변경은 이유, 위험, 복구 조건을 함께 기록한다.
