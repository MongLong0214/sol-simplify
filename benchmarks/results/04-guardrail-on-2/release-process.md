# 결제 서비스 릴리스 프로세스

## 1. 목적과 적용 범위

이 문서는 결제 중단과 보안 통제 훼손을 예방하고, 각 운영 변경의 승인·시험·실행·복구 이력을 재현할 수 있게 하는 절차다. 결제 서비스 및 카드회원 데이터 환경(CDE)에 영향을 줄 수 있는 다음 운영 변경에 적용한다.

- 애플리케이션 코드, 배치, 워커 및 API
- 데이터베이스 스키마와 데이터 마이그레이션
- 인프라, 네트워크, 컨테이너, IaC 및 접근 권한
- 런타임 설정, 시크릿, 인증서 및 기능 플래그
- 로그·모니터링·보안 통제와 결제 페이지 스크립트
- PSP 등 결제 흐름에 포함되는 외부 연동과 의존성

기준은 PCI DSS v4.0.1 요구사항 6.5.1(운영 변경 통제), 6.5.2(중요 변경 후 통제 재확인), 10(로그와 모니터링)이다. 최신 원문은 [PCI SSC 문서 라이브러리](https://www.pcisecuritystandards.org/document_library/)에서 확인한다.

## 2. 역할과 책임

아래 역할은 새 직책이 아니라 기존 12명 중 릴리스마다 지정하는 책임이다. 모든 승인에는 실명, 결정, 시각, 근거 링크를 남긴다.

| 역할 | 책임 | 제한 |
|---|---|---|
| 릴리스 오너 | 릴리스 기록 작성, 범위·시험·롤백 준비, 관계자 조율 | 자신의 변경을 단독 승인할 수 없다. |
| 동료 리뷰어 | 코드·설정·마이그레이션의 정확성, 테스트 적정성, 이전 버전 호환성 승인 | 변경 작성자와 다른 개발자여야 한다. |
| Security/PCI Owner | 보안 영향과 CDE 영향, 관련 PCI 통제, 보안 시험 및 예외 승인 | CDE 또는 보안 민감 변경에는 필수 승인자다. |
| Release Manager | 서비스 오너 또는 당번 리드. 운영 준비와 최종 Go/No-Go 승인 | 미완료 항목을 구두로 면제할 수 없다. |
| 배포 작업자 | 승인된 아티팩트와 절차만 실행하고 실제 실행 이력을 기록 | 승인 범위 밖의 수동 변경을 함께 수행하지 않는다. |
| Incident Commander | 이상 발생 시 중지·롤백 결정, 복구 확인 및 커뮤니케이션 지휘 | 평시에는 Release Manager가 맡을 수 있다. |

릴리스 오너와 배포 작업자는 같은 사람일 수 있지만, 동료 리뷰와 최종 승인은 분리한다.

## 3. 릴리스 전 체크리스트

릴리스 오너가 중앙 변경관리 기록에서 아래 항목을 완료하고 증적을 연결한다. 해당 없음은 빈칸으로 두지 말고 사유를 적는다.

### 변경 범위

- [ ] 릴리스 ID, 변경 사유, 사용자·사업 영향, 대상 서비스와 환경을 기록했다.
- [ ] PR/커밋, 설정, IaC, DB 변경, 외부 의존성을 빠짐없이 연결했다.
- [ ] CDE, 카드회원 데이터 흐름, 네트워크 경계에 미치는 영향을 기록했다.
- [ ] 배포 아티팩트의 버전과 digest, 직전 정상 버전을 식별했다.
- [ ] 함께 배포되는 변경이 모두 이 릴리스 범위에 포함되고 승인되었다.

### 보안과 PCI DSS

- [ ] 기밀성·무결성·가용성, 인증·권한, 시크릿·키, 로그, 네트워크, 결제 페이지 스크립트에 대한 보안 영향을 기록했다.
- [ ] PAN은 필요한 경우에만 마스킹되고, SAD·시크릿·인증 토큰이 코드·로그·스크린샷·증적에 포함되지 않음을 확인했다.
- [ ] 정적 분석, 의존성·시크릿 검사 및 변경에 필요한 보안 테스트 결과를 연결했다.
- [ ] 사용자 입력, 권한 경계, 오류 처리 및 감사 로그가 변경 전과 동일하거나 더 안전함을 확인했다.
- [ ] 중요 변경이면 배포 후 재확인할 PCI 통제와 갱신할 문서를 명시했다.

### 기능과 데이터 정확성

- [ ] 단위·통합·종단간 테스트가 통과했고 결과가 해당 커밋/아티팩트와 연결된다.
- [ ] 적용 가능한 결제 경로(승인·거절·취소·환불·재시도·웹훅)를 검증했다.
- [ ] 중복 결제 방지, 멱등성, 순서 보장, 큐·웹훅 재처리와 정산 불변식을 검증했다.
- [ ] 운영과 동등한 스테이징에서 기능 및 보안 회귀 테스트를 완료했다.
- [ ] DB 변경은 기존·신규 애플리케이션 버전과의 호환성을 확인했다.

### 운영 준비와 복구

- [ ] 배포 순서, 작업자, 명령 또는 파이프라인, 기능 플래그 순서를 기록했다.
- [ ] 결제 성공/실패율, 오류, 지연, 큐 적체, PSP 응답, 웹훅 및 정산을 볼 대시보드와 알림을 확인했다.
- [ ] 이 릴리스의 중지·롤백 조건을 기존 알림 임계치 또는 정상 기준선에 맞춰 구체적으로 적었다.
- [ ] 직전 정상 아티팩트와 설정을 즉시 재배포할 수 있음을 확인했다.
- [ ] DB·설정·기능 플래그를 포함한 롤백 절차를 비운영 환경에서 검증했다.
- [ ] 비가역 마이그레이션의 복구 방식, 백업/복원 가능성 및 거래 유실 방지 방법을 DB 책임자와 확인했다.
- [ ] 배포 중 모니터링 담당과 장애 대응 담당이 정해졌고 연락 가능하다.
- [ ] 고객 또는 지원 조직에 영향이 예상되면 공지 내용과 담당자를 준비했다.

### 승인

- [ ] 동료 리뷰어 승인이 기록되었다.
- [ ] 필요한 Security/PCI Owner 승인이 기록되었다.
- [ ] Release Manager의 최종 Go 승인이 기록되었다.

## 4. 승인 절차

1. **동료 리뷰 승인:** 변경 작성자가 아닌 동료 리뷰어가 구현, 테스트, 데이터 호환성, 롤백 가능성을 검토하고 PR 또는 변경 기록에서 승인한다.
2. **보안 영향 승인:** CDE, 카드 데이터, 인증·권한, 암호화·시크릿, 네트워크 경계, 감사 로그, 보안 통제, 결제 페이지 스크립트 또는 외부 결제 연동을 변경하면 Security/PCI Owner가 보안 영향과 시험 증적을 승인한다. 그 외 변경은 Release Manager가 `CDE/보안 직접 영향 없음` 사유를 확인한다.
3. **최종 Go/No-Go:** Release Manager가 앞선 승인, 체크리스트, 모니터링, 롤백 준비, 배포 인력을 확인하고 Go 또는 No-Go를 기록한다. 하나라도 미완료이거나 증적이 현재 아티팩트와 일치하지 않으면 No-Go다.
4. **배포 직전 확인:** 배포 작업자는 승인된 아티팩트 digest와 대상 환경이 기록과 일치하는지 확인한 뒤 실행한다. 범위가 바뀌면 기존 승인을 재사용하지 않고 변경 기록과 영향을 다시 검토한다.

메신저의 단순 이모지나 구두 동의는 승인이 아니다. 개인 계정으로 인증된 PR, 변경관리 시스템 또는 배포 시스템의 승인 기록을 사용한다.

롤백은 사전 승인된 복구 조치다. 롤백 조건이 충족되면 Incident Commander 또는 Release Manager가 추가 정규 승인 없이 즉시 실행을 지시할 수 있으며, 결정과 실행 이력은 사후에 기록한다.

## 5. 배포 실행과 확인

1. 활성 장애와 결제사 장애 여부, 대시보드·알림·로그 접근 가능 여부를 확인한다.
2. 릴리스 시작을 공유하고 시작 시각, 작업자, 현재 버전과 목표 버전을 기록한다.
3. 플랫폼이 지원하면 카나리 또는 부분 트래픽부터 배포한다. 지원하지 않으면 그 사실과 즉시 롤백 방법을 기록한다.
4. 각 단계에서 결제 성공률, 오류, 지연, PSP 응답, 큐·웹훅, 중복 거래와 정산 신호를 확인한다. 이상이 있으면 다음 단계로 진행하지 않는다.
5. 전체 반영 후 승인된 운영용 합성 거래 또는 안전한 검증 방식으로 핵심 결제 경로와 감사 로그를 확인한다.
6. 실제 종료 시각, 최종 버전, 모니터링 결과와 남은 후속 조치를 기록하고 릴리스를 종료한다.

## 6. 롤백 절차

### 롤백 조건

릴리스 기록에 정한 조건이 하나라도 충족되거나 다음 상황이 확인되면 확산을 중지하고 롤백을 우선한다.

- 결제 성공률·오류율·지연·PSP 응답이 정한 임계치를 벗어남
- 중복 승인, 누락, 금액·상태 불일치 또는 정산 불변식 위반
- 인증·권한·암호화·로그 등 보안 통제 약화 또는 카드 데이터 노출 가능성
- 큐·웹훅 적체가 회복되지 않거나 서비스 상태를 신뢰성 있게 검증할 수 없음

### 실행 순서

1. **중지·선언:** 추가 배포와 기능 플래그 확대를 멈추고 Incident Commander를 지정한다. 감지 시각, 증상, 영향 범위와 롤백 결정자를 기록한다.
2. **유입 통제:** 필요한 경우 신규 기능을 끄거나 트래픽을 정상 인스턴스/리전으로 전환한다. 결제 요청을 임의로 재전송하지 않는다.
3. **애플리케이션 복원:** 승인 기록에 지정한 직전 정상 아티팩트와 설정을 배포한다. 정확한 버전과 실행자를 기록한다.
4. **DB 판단:** 추가형·하위 호환 스키마는 유지한 채 애플리케이션만 되돌리는 것을 우선한다. 거래 유실 가능성이 있는 DB 복원이나 파괴적 역마이그레이션은 자동 수행하지 않는다. Incident Commander와 DB 책임자가 거래 보존, 백업 시점, 재처리 영향을 확인한 뒤 복원 또는 forward-fix를 결정한다.
5. **무결성 확인:** 승인·거절·취소·환불, 중복 방지, 웹훅·큐 적체, 원장·정산 불일치, 보안 통제와 감사 로그를 확인한다. 실제 카드 데이터는 증적에 남기지 않는다.
6. **복구 확인:** 지표와 합성 거래가 정상 기준으로 돌아오고 데이터 불일치가 없음을 Release Manager가 확인한 뒤 장애 상태를 해제한다.
7. **기록·소통:** 복구 시각, 영향 거래, 버전 변화, 실행 명령/파이프라인, 검증 결과, 고객·지원 조직 공지를 중앙 기록에 추가한다.

원인 분석을 위해 장애 상태를 오래 유지하지 않는다. 안정 상태로 복귀한 뒤 별도 장애 대응 절차에 따라 원인을 분석한다.

## 7. 감사 대응을 위한 기록 항목

릴리스마다 하나의 중앙 변경 기록을 증적 색인으로 사용하고 아래 항목을 링크한다.

| 범주 | 필수 기록 |
|---|---|
| 식별 | 릴리스 ID, 서비스·환경, 릴리스 유형, 릴리스 오너, 작업자, 시작·종료 시각(시간대 포함) |
| 변경 내용 | 변경 사유와 설명, 사용자 영향, CDE/데이터 흐름/시스템 범위, 보안 영향, 관련 PCI DSS 요구사항 |
| 기술 추적 | PR·커밋, 저장소, 아티팩트 버전·digest, 이미지, 설정/IaC/DB 마이그레이션 버전, 직전 정상 버전 |
| 시험 증적 | 단위·통합·종단간·보안 회귀 테스트, 정적 분석, 의존성·시크릿 검사, 스테이징 결과와 실행 시각 |
| 승인 | 각 승인자의 실명·역할, 승인/반려 결정, 시각, 코멘트, 승인한 아티팩트 버전 |
| 롤백 준비 | 롤백 조건, 단계, 직전 아티팩트, DB/데이터 복구 판단, 비운영 검증 결과 |
| 운영 실행 | 배포 파이프라인 실행 ID 또는 명령 이력, 작업자, 각 단계 시각, 기능 플래그·트래픽 변경, 실제 배포 버전 |
| 운영 확인 | 대시보드·알림·로그 링크, 배포 전후 지표, 합성 거래 결과, 결제·큐·웹훅·정산 검증 결과 |
| 결과와 예외 | 성공/중지/롤백 상태, 발생한 경보·장애, 영향 범위, 결정 시각, 복구 버전과 검증 결과 |
| 중요 변경 후 확인 | 적용 가능한 PCI 통제가 계속 유효한지 확인한 결과와 갱신한 네트워크·데이터 흐름·운영 문서 |

기록은 접근 통제와 변경 이력이 있는 중앙 시스템에 보관한다. 카드번호, SAD, 시크릿, 인증 토큰은 티켓·로그·스크린샷에 저장하지 않는다. 감사 로그는 PCI DSS 10.5.1에 따라 최소 12개월 보존하고 최근 3개월은 즉시 분석 가능해야 한다. 릴리스 기록과 증적은 회사의 PCI 증적 보존정책에 따라 보관하며, 보존기간이 정해지지 않았다면 Security/PCI Owner가 감사 담당자와 확정하기 전까지 삭제하지 않는다. PCI 로그의 목적은 사건 조사 시 누가, 무엇을, 어디서, 언제, 어떻게 했는지 재구성하는 데 있다([PCI SSC FAQ 1081](https://www.pcisecuritystandards.org/faqs/1081/)).
