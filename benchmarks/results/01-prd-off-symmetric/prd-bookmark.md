# 게시글 북마크 기능 PRD

## 1. 문서 개요

| 항목 | 내용 |
| --- | --- |
| 기능명 | 게시글 북마크 및 마이페이지 북마크 목록 |
| 상태 | Draft |
| 대상 서비스 | Next.js 15 App Router + Supabase + React Query 웹서비스 |
| 주요 사용자 | 로그인 사용자 |

## 2. 배경과 문제

사용자는 관심 있는 게시글을 나중에 다시 읽고 싶어도 서비스 안에서 이를 보관하고 찾아볼 방법이 없다. 이로 인해 게시글 URL을 별도로 저장하거나 검색을 반복해야 한다.

로그인 사용자가 게시글을 간단히 북마크하고, 마이페이지에서 저장한 게시글을 한곳에서 다시 확인할 수 있도록 한다.

## 3. 목표

- 로그인 사용자가 게시글에서 북마크를 추가하거나 해제할 수 있다.
- 사용자는 새로고침하거나 다른 기기에서 접속해도 자신의 북마크 상태를 확인할 수 있다.
- 사용자는 마이페이지에서 최근 북마크한 순서로 게시글 목록을 조회할 수 있다.
- 중복 요청과 네트워크 오류에도 사용자별 북마크 데이터가 일관되게 유지된다.

## 4. 비목표

이번 범위에는 다음 항목을 포함하지 않는다.

- 북마크 폴더, 태그 또는 메모
- 북마크 목록의 검색, 필터 및 사용자 지정 정렬
- 북마크 수 공개 또는 인기 게시글 랭킹 반영
- 다른 사용자와 북마크 목록 공유
- 비로그인 사용자의 로컬 북마크 저장 및 로그인 후 병합
- 북마크 추가 알림 또는 리마인더

## 5. 전제 조건

- Supabase Auth로 로그인 사용자를 식별할 수 있다.
- 게시글은 고유 ID와 목록 표시에 필요한 제목, 요약, 작성자, 작성일 등의 정보를 가진다.
- 삭제되었거나 현재 사용자가 열람할 수 없는 게시글은 북마크 목록에 노출하지 않는다.
- 마이페이지는 로그인 사용자만 접근할 수 있다.

## 6. 핵심 사용자 스토리

1. 로그인 사용자로서 관심 있는 게시글을 나중에 다시 보기 위해 북마크하고 싶다.
2. 로그인 사용자로서 실수로 저장한 게시글을 북마크에서 해제하고 싶다.
3. 로그인 사용자로서 내가 북마크한 게시글을 마이페이지에서 최신 저장순으로 보고 싶다.
4. 비로그인 사용자로서 북마크를 누르면 로그인해야 사용할 수 있는 기능임을 안내받고 싶다.

## 7. 사용자 흐름

### 7.1 게시글에서 북마크 추가

1. 사용자가 게시글 상세 화면에 진입한다.
2. 시스템은 현재 사용자의 해당 게시글 북마크 여부를 표시한다.
3. 사용자가 비활성 상태의 북마크 버튼을 누른다.
4. UI는 버튼을 즉시 활성 상태로 변경하고 저장 요청을 보낸다.
5. 성공 시 활성 상태를 유지한다.
6. 실패 시 이전 상태로 되돌리고 재시도 가능한 오류 메시지를 표시한다.

### 7.2 북마크 해제

1. 사용자가 활성 상태의 북마크 버튼을 누른다.
2. UI는 버튼을 즉시 비활성 상태로 변경하고 삭제 요청을 보낸다.
3. 성공 시 비활성 상태를 유지한다.
4. 실패 시 이전 상태로 되돌리고 오류 메시지를 표시한다.

마이페이지 목록에서 해제한 경우 해당 항목은 즉시 목록에서 제거한다. 실패하면 원래 위치에 복원한다. 별도의 확인 대화상자는 표시하지 않는다.

### 7.3 북마크 목록 조회

1. 사용자가 마이페이지의 `북마크` 메뉴에 진입한다.
2. 시스템은 최근 북마크한 순서로 게시글을 조회한다.
3. 사용자가 게시글 항목을 누르면 해당 게시글 상세 화면으로 이동한다.
4. 다음 페이지가 있으면 사용자가 추가 항목을 불러올 수 있다.

### 7.4 비로그인 사용자

1. 비로그인 사용자가 북마크 버튼을 누른다.
2. 시스템은 로그인이 필요한 기능임을 알리고 로그인 화면으로 이동시킨다.
3. 로그인 완료 후 사용자가 보고 있던 게시글로 돌아온다.
4. 로그인만으로 북마크가 자동 추가되지는 않으며, 사용자가 다시 버튼을 눌러 저장한다.

## 8. 기능 요구사항

### FR-1. 북마크 버튼 표시

- 게시글 상세 화면에 북마크 버튼을 표시한다.
- 버튼은 `북마크 안 됨`, `북마크됨`, `처리 중` 상태를 시각적으로 구분한다.
- 아이콘만 사용하는 경우 접근성 이름을 제공한다.
  - 비활성: `북마크 추가`
  - 활성: `북마크 해제`
- 요청 처리 중에는 같은 사용자의 연속 클릭으로 요청이 중복되지 않도록 제어한다.

### FR-2. 북마크 상태 조회

- 로그인 사용자에게만 서버에 저장된 북마크 상태를 조회한다.
- 새로고침, 재로그인, 다른 기기 접속 후에도 동일한 상태가 표시되어야 한다.
- 비로그인 사용자의 초기 상태는 비활성으로 표시한다.

### FR-3. 북마크 추가

- 인증된 사용자는 열람 가능한 게시글을 북마크할 수 있다.
- 동일 사용자가 동일 게시글을 두 번 이상 북마크해도 레코드는 하나만 존재해야 한다.
- 같은 추가 요청이 반복되어도 성공 상태를 반환하는 멱등 동작이어야 한다.
- 성공 시 마이페이지 북마크 목록 캐시에도 변경이 반영되어야 한다.

### FR-4. 북마크 해제

- 인증된 사용자는 자신이 만든 북마크만 해제할 수 있다.
- 이미 해제된 북마크에 삭제 요청을 반복해도 성공 상태를 반환하는 멱등 동작이어야 한다.
- 성공 시 게시글의 북마크 상태와 마이페이지 목록 캐시가 함께 갱신되어야 한다.

### FR-5. 마이페이지 북마크 목록

- 마이페이지에 `북마크` 메뉴 또는 섹션을 제공한다.
- 기본 정렬은 `북마크한 시각 내림차순`이다.
- 각 항목은 최소한 제목과 게시글 상세 링크를 제공한다. 서비스의 기존 게시글 카드가 있으면 같은 UI와 메타데이터를 재사용한다.
- 최초 페이지 크기는 20개로 하며, 커서 기반으로 다음 페이지를 조회한다.
- 목록에서 북마크를 해제할 수 있다.
- 결과가 없으면 `북마크한 게시글이 없습니다.`와 게시글 탐색 경로를 표시한다.
- 삭제되었거나 사용 권한이 사라진 게시글은 결과에서 제외한다.

### FR-6. 인증과 권한

- 북마크 추가, 해제, 목록 조회는 모두 서버에서 현재 세션을 검증한다.
- 클라이언트가 전달한 사용자 ID를 권한 판단에 사용하지 않는다.
- 사용자는 다른 사용자의 북마크를 조회, 생성 또는 삭제할 수 없다.
- 인증되지 않은 API 요청에는 `401 Unauthorized`, 권한이 없는 게시글 요청에는 서비스 정책에 따라 `403 Forbidden` 또는 리소스 존재를 감추기 위한 `404 Not Found`를 반환한다.

### FR-7. 오류 처리

- 네트워크 또는 서버 오류가 발생하면 낙관적으로 변경한 UI를 이전 상태로 되돌린다.
- 오류 메시지는 `북마크를 저장하지 못했습니다. 다시 시도해 주세요.` 또는 `북마크를 해제하지 못했습니다. 다시 시도해 주세요.`처럼 수행한 동작을 명시한다.
- 목록 조회 실패 시 오류 상태와 `다시 시도` 동작을 제공한다.
- 만료된 세션은 로그인 갱신 또는 재로그인 흐름으로 연결한다.

## 9. UX 상태 정의

| 화면/컴포넌트 | 상태 | 요구 동작 |
| --- | --- | --- |
| 북마크 버튼 | 비활성 | 외곽선 아이콘과 `북마크 추가` 접근성 이름 표시 |
| 북마크 버튼 | 활성 | 채워진 아이콘과 `북마크 해제` 접근성 이름 표시 |
| 북마크 버튼 | 처리 중 | 현재 낙관적 상태를 표시하고 중복 입력 방지 |
| 북마크 목록 | 로딩 | 기존 디자인 시스템의 스켈레톤 표시 |
| 북마크 목록 | 빈 상태 | 안내 문구와 게시글 탐색 CTA 표시 |
| 북마크 목록 | 오류 | 오류 문구와 재시도 버튼 표시 |
| 북마크 목록 | 다음 페이지 로딩 | 기존 항목을 유지하면서 하단 로딩 상태 표시 |

북마크 상태는 색상만으로 구분하지 않으며 아이콘 형태, 레이블 또는 보조 텍스트를 함께 사용한다. 버튼은 키보드로 조작 가능해야 하고 포커스 표시를 제공해야 한다.

## 10. 데이터 모델

Supabase Postgres에 다음 테이블을 추가한다. 실제 게시글 및 사용자 테이블 이름은 기존 스키마에 맞춘다.

### `bookmarks`

| 컬럼 | 타입 | 제약 조건 | 설명 |
| --- | --- | --- | --- |
| `id` | `uuid` | PK, 기본값 `gen_random_uuid()` | 북마크 식별자 |
| `user_id` | `uuid` | NOT NULL, FK → `auth.users(id)`, ON DELETE CASCADE | 사용자 식별자 |
| `post_id` | 게시글 PK와 동일 | NOT NULL, FK → `posts(id)`, ON DELETE CASCADE | 게시글 식별자 |
| `created_at` | `timestamptz` | NOT NULL, 기본값 `now()` | 북마크한 시각 |

필수 제약 및 인덱스:

- `UNIQUE (user_id, post_id)`: 사용자별 중복 북마크 방지
- `(user_id, created_at DESC, id DESC)`: 마이페이지 목록 정렬 및 커서 페이지네이션 지원
- 게시글 삭제 시 관련 북마크도 함께 삭제

### RLS 정책

`bookmarks` 테이블에서 RLS를 활성화하고 다음 원칙을 적용한다.

- `SELECT`: `auth.uid() = user_id`
- `INSERT`: `auth.uid() = user_id`
- `DELETE`: `auth.uid() = user_id`
- 사용자 ID는 서버에서 세션 기준으로 설정한다.
- 서비스 역할 키는 브라우저에 노출하지 않는다.

게시글 가시성 정책이 존재하면 목록 조회 시 해당 정책도 함께 만족해야 한다.

## 11. API 계약

기존 프로젝트의 API 규칙이 없다면 Next.js App Router의 Route Handler를 사용한다. 아래 경로는 권장안이며 같은 의미의 Server Action으로 구현해도 된다.

### 북마크 상태 조회

`GET /api/posts/{postId}/bookmark`

성공 응답:

```json
{
  "bookmarked": true
}
```

### 북마크 추가

`PUT /api/posts/{postId}/bookmark`

성공 응답: `200 OK`

```json
{
  "bookmarked": true
}
```

`UNIQUE (user_id, post_id)` 충돌은 오류가 아니라 이미 저장된 상태로 처리한다.

### 북마크 해제

`DELETE /api/posts/{postId}/bookmark`

성공 응답: `200 OK`

```json
{
  "bookmarked": false
}
```

대상 레코드가 없어도 동일한 성공 응답을 반환한다.

### 내 북마크 목록 조회

`GET /api/me/bookmarks?limit=20&cursor={cursor}`

성공 응답 예시:

```json
{
  "items": [
    {
      "bookmarkedAt": "2026-08-25T10:00:00Z",
      "post": {
        "id": "post-id",
        "title": "게시글 제목",
        "excerpt": "게시글 요약"
      }
    }
  ],
  "nextCursor": null
}
```

- `limit` 기본값은 20이며 과도한 조회를 막기 위한 최대값을 둔다.
- 커서는 `created_at`과 안정적인 보조 정렬 키 `id`를 기반으로 생성하며, 클라이언트가 내부 값을 수정할 수 없도록 불투명한 문자열로 전달한다.
- `nextCursor`가 `null`이면 마지막 페이지다.

## 12. 클라이언트 상태 및 캐시 정책

React Query의 권장 쿼리 키는 다음과 같다.

- 게시글별 상태: `['posts', postId, 'bookmark']`
- 내 북마크 목록: `['me', 'bookmarks']`

추가 및 해제 mutation은 다음 순서를 따른다.

1. 관련 쿼리를 취소한다.
2. 이전 캐시를 보관한다.
3. 상세 상태와 목록을 낙관적으로 갱신한다.
4. 실패 시 보관한 캐시로 롤백한다.
5. 완료 후 관련 쿼리를 무효화해 서버 상태와 재동기화한다.

마이페이지 목록은 `useInfiniteQuery`를 사용한 커서 페이지네이션을 기본안으로 한다. 인증 사용자 변경 또는 로그아웃 시 이전 사용자의 북마크 캐시가 노출되지 않도록 사용자 종속 캐시를 제거하거나 쿼리 클라이언트를 초기화한다.

## 13. 비기능 요구사항

### 성능

- 북마크 추가 및 해제 API의 목표 응답 시간은 정상 부하에서 p95 500ms 이하로 한다. 단, 배포 환경과 Supabase 리전에 따라 기준을 조정할 수 있다.
- 북마크 목록 최초 응답의 목표 서버 처리 시간은 정상 부하에서 p95 800ms 이하로 한다.
- 목록은 게시글별 추가 요청을 발생시키는 N+1 조회 없이 가져온다.

### 보안 및 개인정보

- 북마크 목록은 기본적으로 비공개다.
- 모든 쓰기 요청은 세션과 RLS 양쪽에서 소유권을 검증한다.
- 로그와 분석 이벤트에 인증 토큰 또는 게시글 본문을 기록하지 않는다.

### 접근성

- 버튼은 키보드 및 스크린 리더로 현재 상태와 수행할 동작을 이해할 수 있어야 한다.
- 처리 결과를 토스트로만 전달하는 경우 적절한 live region을 사용한다.

### 호환성

- 서비스가 지원하는 최신 주요 데스크톱 및 모바일 브라우저에서 동일한 핵심 동작을 제공한다.
- 모바일 터치 영역은 서비스 디자인 시스템의 최소 크기를 따른다.

## 14. 분석 이벤트 및 성공 지표

### 권장 이벤트

| 이벤트 | 발생 시점 | 주요 속성 |
| --- | --- | --- |
| `bookmark_added` | 북마크 추가 서버 성공 | `post_id`, `source` (`post_detail`/`mypage`) |
| `bookmark_removed` | 북마크 해제 서버 성공 | `post_id`, `source` |
| `bookmark_list_viewed` | 마이페이지 목록 조회 성공 | `item_count` |
| `bookmark_action_failed` | 추가 또는 해제 실패 | `action`, `error_code`, `source` |

분석 이벤트는 낙관적 UI 변경 시점이 아니라 서버 성공이 확인된 시점에 한 번만 기록한다.

### 출시 후 관찰 지표

- 북마크 기능을 한 번 이상 사용한 로그인 사용자 비율
- 사용자당 평균 북마크 수
- 북마크 목록에서 게시글 상세로 이동한 비율
- 북마크 추가 및 해제 API 오류율

초기 목표치는 기존 활성 사용자 및 트래픽 기준선을 확인한 뒤 별도로 확정한다.

## 15. 수용 기준

### AC-1. 추가와 상태 유지

- Given 로그인 사용자가 북마크하지 않은 게시글을 보고 있을 때
- When 북마크 추가 버튼을 누르면
- Then 버튼이 활성 상태로 바뀌고, 새로고침 후에도 활성 상태가 유지된다.

### AC-2. 중복 방지

- Given 로그인 사용자가 같은 게시글에 추가 요청을 여러 번 보냈을 때
- When 모든 요청 처리가 끝나면
- Then 해당 사용자와 게시글 조합의 북마크 레코드는 하나만 존재한다.

### AC-3. 해제

- Given 로그인 사용자가 북마크한 게시글을 보고 있을 때
- When 북마크 해제 버튼을 누르면
- Then 버튼이 비활성 상태로 바뀌고 마이페이지 목록에서도 해당 게시글이 제거된다.

### AC-4. 비로그인 처리

- Given 비로그인 사용자가 게시글을 보고 있을 때
- When 북마크 버튼을 누르면
- Then 로그인 필요 안내 후 로그인 화면으로 이동하며, 로그인 완료 후 원래 게시글로 돌아올 수 있다.

### AC-5. 목록 조회와 순서

- Given 로그인 사용자가 여러 게시글을 서로 다른 시각에 북마크했을 때
- When 마이페이지 북마크 목록을 열면
- Then 열람 가능한 게시글이 최근 북마크한 순서로 표시된다.

### AC-6. 빈 상태

- Given 로그인 사용자의 유효한 북마크가 없을 때
- When 마이페이지 북마크 목록을 열면
- Then 빈 상태 안내와 게시글 탐색 경로가 표시된다.

### AC-7. 오류 롤백

- Given 북마크 추가 또는 해제 요청이 실패하도록 설정했을 때
- When 사용자가 버튼을 누르면
- Then 낙관적으로 변경된 UI가 이전 상태로 복원되고 재시도 가능한 오류 메시지가 표시된다.

### AC-8. 사용자 간 격리

- Given 사용자 A와 사용자 B가 서로 다른 북마크를 가지고 있을 때
- When 사용자 A가 상태 또는 목록 API를 호출하면
- Then 사용자 B의 북마크는 조회되거나 변경되지 않는다.

### AC-9. 페이지네이션

- Given 사용자가 페이지 크기보다 많은 게시글을 북마크했을 때
- When 다음 페이지를 순차적으로 불러오면
- Then 항목이 누락되거나 중복되지 않고 마지막 페이지에서 `nextCursor`가 `null`이 된다.

### AC-10. 삭제 또는 비공개 게시글

- Given 북마크한 게시글이 삭제되었거나 사용자에게 열람 불가 상태가 되었을 때
- When 북마크 목록을 조회하면
- Then 해당 게시글은 목록에 노출되지 않는다.

## 16. 테스트 범위

- 데이터베이스: 고유 제약, 외래 키 삭제 동작, RLS 사용자 격리
- API: 인증 여부, 멱등 추가/해제, 존재하지 않거나 열람 불가한 게시글, 커서 경계값
- 클라이언트: 버튼 상태, 빠른 연속 입력, 낙관적 업데이트, 실패 롤백, 캐시 동기화
- 목록: 로딩, 빈 상태, 오류, 다중 페이지, 항목 해제
- E2E: 로그인 → 게시글 북마크 → 마이페이지 확인 → 해제 → 새로고침 후 상태 확인
- 접근성: 키보드 조작, 접근성 이름, 포커스 표시, 상태 변경 안내

## 17. 출시 계획

1. 데이터베이스 마이그레이션과 RLS 정책을 먼저 배포한다.
2. API 및 자동화 테스트를 배포한다.
3. 게시글 상세 북마크 버튼과 마이페이지 목록을 기능 플래그 뒤에 배포한다.
4. 내부 또는 제한된 사용자에게 활성화해 오류율과 데이터 정합성을 확인한다.
5. 전체 로그인 사용자에게 활성화하고 주요 지표를 모니터링한다.

롤백 시 UI와 API 노출을 기능 플래그로 중단할 수 있어야 한다. 데이터 테이블은 즉시 삭제하지 않아 재배포 시 기존 북마크가 유지되도록 한다.

## 18. 결정 필요 사항

- 기존 게시글 카드에서 어떤 메타데이터를 북마크 목록에 노출할지
- 비로그인 북마크 클릭 시 로그인 모달과 전용 로그인 페이지 중 어느 흐름을 사용할지
- 게시글 삭제 외에 비공개, 차단, 신고 처리된 게시글의 노출 정책
- 분석 도구와 이벤트 속성의 최종 명명 규칙
- 실제 트래픽 기준의 성능 목표 및 알림 임계치
