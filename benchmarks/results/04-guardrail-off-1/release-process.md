# 결제 서비스 릴리스 프로세스

## 1. 문서 정보

| 항목 | 내용 |
|---|---|
| 문서 버전/상태 | v1.0 / 초안(내부 승인 후 시행) |
| 시행일 | 내부 승인일 |
| 문서 승인자 | Engineering Lead, Security Owner |
| 문서 소유자 | Engineering Lead |
| 통제 소유자 | Security Owner(PCI 담당자) |
| 적용 대상 | 운영 환경 및 카드회원데이터 환경(CDE)에 영향을 줄 수 있는 애플리케이션, 인프라, 네트워크, 데이터베이스, 설정, 결제 페이지 스크립트, 서드파티 연동 변경 |
| 기준 | PCI DSS v4.0.1, 회사의 보안·장애대응 정책 |
| 검토 주기 | 반기 1회, 그리고 중대 장애·감사 지적·중대한 시스템 변경 후 5영업일 이내 |
| 기록 시스템 | 변경 티켓, Git 저장소, CI/CD, 중앙 로그 및 증적 저장소 |

이 문서의 목적은 안전하고 추적 가능한 릴리스를 보장하고, 카드 결제 중단 시간을 최소화하며, PCI DSS 감사에 필요한 변경·승인·시험·배포 증적을 일관되게 남기는 것이다. 지난 릴리스의 40분 결제 중단을 재발 방지하기 위해 운영 배포의 **5분 이내 중단/롤백 결정, 15분 이내 이전 정상 버전 복구**를 목표로 한다.

> 이 문서는 운영 절차이며 PCI DSS 준수 여부에 대한 법률 또는 심사 판단을 대체하지 않는다. 실제 적용 범위와 증적은 담당 QSA/인수사와 확인한다.

## 2. 기본 원칙

1. 모든 운영 변경은 하나의 변경 티켓과 연결한다. 티켓 없는 운영 변경은 금지한다.
2. 변경 작성자는 자신의 변경을 단독 승인하거나 최종 배포 승인할 수 없다. 최소 2인이 변경에 관여한다.
3. 운영 배포는 승인 게이트가 설정된 CI/CD 서비스 계정으로 수행한다. 개인 계정의 직접 배포는 금지하며, 불가피한 경우 비상 변경 절차와 break-glass 기록을 적용한다.
4. 빌드한 동일 아티팩트를 환경별로 승격하며 운영에서 다시 빌드하지 않는다. 아티팩트는 버전, Git SHA, digest 및 서명으로 식별한다.
5. 데이터베이스와 API 변경은 기본적으로 하위 호환 가능해야 하며 expand-migrate-contract 방식을 사용한다.
6. 로그, 화면 캡처, 테스트 데이터와 변경 티켓에 PAN 전체값, CVV/CVC, PIN, 트랙 데이터, 비밀키, 토큰 원문 등 민감정보를 남기지 않는다.
7. 배포 중에는 한 명의 Release Manager만 진행/중단 결정을 지휘한다. 이상 징후가 불명확하면 진행보다 롤백을 기본값으로 한다.

## 3. 역할과 책임

실제 담당자는 분기별 온콜/릴리스 역할표에 이름과 대리자를 지정한다. 한 사람이 여러 역할을 맡을 수 있으나 **Change Owner는 Peer Reviewer 또는 최종 Release Manager를 겸할 수 없다.**

| 역할 | 주요 책임 | 승인 대상 |
|---|---|---|
| Change Owner | 변경 구현, 영향·위험 분석, 시험 및 롤백 계획 작성, 증적 취합 | 승인자가 아니며 릴리스 완료 확인을 요청 |
| Peer Reviewer | 코드, IaC, 설정, 마이그레이션 및 테스트 검토 | 코드/설계의 정확성, 테스트 충분성, 롤백 가능성 |
| QA/Verifier | 스테이징과 릴리스 후보 검증 | 기능·회귀·결제 핵심 흐름 시험 결과 |
| Service Owner/Tech Lead | 서비스 구조와 데이터 무결성 책임 | 기술 위험, 용량, 호환성, DB 변경, 롤아웃·롤백 계획 |
| Security Owner(PCI 담당자) | CDE 범위와 보안 통제 책임 | CDE/인증·권한/암호화/로깅/결제 페이지/취약점 예외의 보안 영향 |
| Release Manager(순번제) | 체크리스트 확인, go/no-go 지휘, 타임라인 기록 | 모든 필수 승인과 운영 준비를 확인한 최종 배포 승인 |
| On-call Operator | 모니터링, 배포 실행 또는 감독, 장애 대응 | 대시보드·알람·인력·복구 수단의 운영 준비 확인 |
| Incident Commander(IC) | 장애 시 단일 지휘, 복구와 커뮤니케이션 조정 | 비상 변경 및 데이터 복구 결정 |

## 4. 변경 등급

| 등급 | 기준 | 예시 | 필수 승인 |
|---|---|---|---|
| 일반 변경 | 계획된 운영 변경 | 애플리케이션 릴리스, 의존성 업데이트, 안전한 설정 변경 | Peer Reviewer, QA/Verifier, Service Owner, Release Manager |
| CDE/고위험 변경 | CDE, 결제 성공률, 데이터 무결성 또는 보안 통제에 영향을 줄 수 있음 | 결제 승인/매입/취소, DB 스키마, IAM, 암호화, 방화벽, 감사로그, 결제 페이지 스크립트, 결제사 연동 | 일반 변경 승인 전부 + Security Owner |
| 비상 변경 | 진행 중인 장애·취약점 악용·긴급 규제 대응을 위해 정규 대기시간을 지킬 수 없음 | 장애 완화 설정, 긴급 패치, 이전 버전 복구 | IC + Service Owner(동일인/작성자 겸임 시 독립된 선임 엔지니어 추가); 보안 통제 변경은 가능한 즉시 Security Owner 포함 |

문서 변경, 개발환경 전용 변경처럼 운영/CDE에 영향을 줄 수 없다고 분류한 경우에도 티켓에 근거를 기록한다. 영향 여부가 불명확하면 상위 등급을 적용한다.

## 5. 릴리스 전 체크리스트

Change Owner가 체크하고 각 승인자가 담당 영역을 검증한다. `N/A`는 허용하지만 반드시 사유를 적는다. 필수 항목이 충족되지 않으면 Release Manager는 배포를 승인하지 않는다.

### 5.1 변경 정의와 범위

- [ ] 변경 티켓에 목적, 고객 영향, 변경 내용, 대상 환경·서비스·컴포넌트를 기록했다.
- [ ] CDE, 카드회원데이터 흐름, 네트워크 세분화 및 PCI DSS 통제에 미치는 영향을 기록했다.
- [ ] 위험 등급(낮음/중간/높음), 실패 양상, blast radius, 외부 결제사·의존 서비스 영향을 분석했다.
- [ ] 관련 PR, 이슈, 설계 문서, 아티팩트 버전/Git SHA가 티켓에 연결되어 있다.
- [ ] 운영 문서, 자산 목록, 데이터 흐름도, 네트워크도 및 CDE 범위 문서의 갱신 필요 여부를 확인했다.
- [ ] 고객 공지, 고객지원 안내 또는 상태 페이지 공지가 필요한지 결정했다.

### 5.2 코드와 보안

- [ ] Change Owner가 아닌 Peer Reviewer가 코드/IaC/설정을 승인했다.
- [ ] 단위·통합·회귀 테스트가 통과했고 결과 링크가 있다.
- [ ] SAST, SCA/의존성, 비밀정보, IaC 및 컨테이너 이미지 검사가 통과했다.
- [ ] 미해결 Critical/High 취약점이 없다. 예외가 있으면 Security Owner가 만료일·보완통제·책임자를 승인했다.
- [ ] 인증, 인가, 세션, 암호화, 키/인증서, 로깅 변경을 Security Owner가 검토했다.
- [ ] 로그와 오류 응답에 PAN, SAD 또는 비밀정보가 노출되지 않는지 시험했다.
- [ ] 결제 페이지 스크립트 변경은 승인 여부, 무결성 확인 수단, 사용 목적 및 인벤토리를 갱신했다.
- [ ] 결제 페이지와 보안 관련 HTTP 헤더의 비인가 변경 탐지·알림이 배포 후에도 작동하는지 확인했다.
- [ ] 새 계정·권한·방화벽 규칙은 최소권한과 만료/회수 계획을 갖췄다.
- [ ] 중대한 인프라/애플리케이션 변경이면 Security Owner가 변경 후 내부·외부 침투시험 및 세분화 통제 검증의 적용 여부, 범위와 완료 기한을 기록했다.

### 5.3 결제 기능과 데이터

- [ ] 스테이징에서 토큰화된 테스트 데이터로 승인, 실패, 타임아웃, 재시도, 취소/환불 등 영향받는 핵심 경로를 검증했다.
- [ ] 사전 운영환경에서 실제 PAN을 사용하지 않았고, 운영 승격 전 테스트 데이터·계정·디버그 기능을 제거했다. 사전 운영환경 자체가 CDE이면 적용되는 모든 PCI DSS 통제를 확인했다.
- [ ] 멱등키와 재시도 동작을 검증해 중복 승인·중복 청구가 발생하지 않음을 확인했다.
- [ ] 결제사 응답 코드 매핑, 타임아웃, 서킷브레이커 및 대체 경로를 검증했다.
- [ ] DB 마이그레이션은 하위 호환, 실행시간, 잠금, 복제 지연, 저장공간 영향을 검토했다.
- [ ] 파괴적 스키마 변경은 별도 릴리스로 분리했고 이전 코드가 더 이상 사용되지 않음을 확인했다.
- [ ] 데이터 변경이 있으면 백업 상태와 복구 시험 결과를 확인하고 사후 정합성 점검 쿼리를 준비했다.

### 5.4 운영 준비와 롤백

- [ ] 변경에 특화된 성공 지표, 대시보드, 로그 검색 및 알람 링크가 준비되어 있다.
- [ ] 아래 기본 중단/롤백 기준을 서비스 특성에 맞게 티켓에 확정했다.
- [ ] 단계적 배포 또는 canary 대상·단계·관찰시간을 정했다. 불가능하면 사유와 blast radius 완화책을 승인받았다.
- [ ] 직전 정상 아티팩트와 설정을 즉시 배포할 수 있고, 최근 롤백 또는 복구 리허설 결과가 유효하다.
- [ ] 기능 플래그의 기본값, 소유자, 비활성화 방법 및 전파시간을 확인했다.
- [ ] 롤백 명령/파이프라인, 필요한 권한, 예상 복구시간 및 검증 절차를 문서화했다.
- [ ] 비가역 데이터 변경의 roll-forward 또는 보상 계획과 결제 대사 절차가 있다.
- [ ] Release Manager, On-call Operator, Change Owner가 배포 및 최소 30분의 안정화 관찰 시간 동안 참여 가능하다.
- [ ] 같은 결제 경로의 동시 변경, 진행 중인 Sev-1/Sev-2, 결제사 점검 및 트래픽 피크가 없음을 확인했다.

### 5.5 최종 준비

- [ ] 모든 필수 승인에 승인자 ID, 시각, 대상 릴리스 버전이 기록되어 있다.
- [ ] CI/CD가 승인된 불변 아티팩트와 예상 환경을 가리킨다.
- [ ] 운영 합성 결제는 실제 카드정보가 아닌 승인된 테스트 토큰/계정만 사용한다.
- [ ] 배포 채널, 상태 페이지, 고객지원 및 경영진의 장애 연락 경로를 확인했다.
- [ ] Release Manager가 체크리스트를 잠그고 최종 go/no-go를 기록했다.

## 6. 승인 절차

### 6.1 일반 및 CDE/고위험 변경

승인은 다음 순서로 진행한다. 승인은 구두, 메신저 이모지 또는 회의 참석만으로 대체할 수 없으며 변경 티켓이나 CI/CD 승인 게이트에 인증된 사용자 ID와 시각으로 남겨야 한다.

1. **Change Owner 제출:** 변경 설명, 보안 영향, 시험 증적, 롤아웃 및 롤백 계획을 완성한다.
2. **Peer Reviewer 승인:** 코드/설정의 정확성, 안전한 개발 기준, 테스트와 롤백 가능성을 검토한다.
3. **QA/Verifier 승인:** 승인된 릴리스 후보에 대한 기능·회귀·결제 핵심 경로 결과를 승인한다.
4. **Service Owner 승인:** 기술 위험, 용량, 호환성, DB/데이터 무결성 및 롤백 계획을 승인한다.
5. **Security Owner 승인:** CDE/고위험 변경이면 보안 영향, 취약점 결과, PCI 범위·통제 및 예외를 승인한다. 범위 밖으로 판단하면 그 근거를 티켓에 남긴다.
6. **On-call Operator 확인:** 모니터링, 알람, 배포 창, 인력, 이전 정상 버전 및 권한의 준비 상태를 확인한다.
7. **Release Manager 최종 승인:** 동일 버전의 필수 승인과 체크리스트가 모두 있는지 확인하고 go/no-go를 기록한다.
8. **CI/CD 배포:** 최종 승인 후에만 운영 배포 게이트가 열린다. 승인 후 코드·설정·아티팩트가 바뀌면 기존 승인은 무효이며 변경 범위에 맞게 재승인한다.

### 6.2 배포 보류 조건

다음 중 하나라도 해당하면 no-go다.

- 필수 승인 또는 시험 증적이 없음
- 롤백 가능한 직전 정상 버전이 없음
- Critical/High 취약점 또는 보안 통제 실패에 승인된 예외가 없음
- 결제 핵심 경로 테스트, 중앙 감사로그 또는 모니터링이 실패함
- 진행 중인 중대 장애나 동일 경로의 다른 운영 변경이 있음
- 배포·관찰·복구에 필요한 담당자가 없음

### 6.3 비상 변경 승인

1. IC가 비상 변경을 선언하고 장애/보안 사건 ID, 긴급 사유, 변경 범위와 예상 위험을 기록한다.
2. IC와 Service Owner가 변경을 승인한다. 두 역할이 동일인이거나 둘 중 한 명이 Change Owner라면 독립된 선임 엔지니어를 추가해 Change Owner 외의 검토자를 확보한다.
3. 보안 통제나 CDE 범위를 바꾸는 경우 Security Owner 승인을 우선 확보한다. 서비스 복구가 지연될 정도로 연락이 되지 않으면 IC와 두 번째 선임 엔지니어가 최소 변경을 승인하고 그 사유를 기록한다.
4. 가능한 자동 시험, 현재 백업, 롤백 수단, 모니터링을 확인한 후 제한된 범위로 배포한다.
5. 다음 영업일 안에 정규 승인과 증적을 보완하고, 3영업일 안에 사후검토를 완료한다. 사후승인은 사전 통제 생략을 정당화하지 않는다.

## 7. 배포 및 관찰 절차

1. Release Manager가 배포 채널에 릴리스 ID, 대상 버전, 범위, 시작 시각, 담당자, 대시보드와 롤백 기준을 공지한다.
2. On-call Operator가 배포 직전 15분 기준선(트래픽, 내부 오류/타임아웃, 결제 승인 성공률, p95/p99 지연, 큐 적체, DB 상태)을 기록한다.
3. CI/CD로 승인된 불변 아티팩트를 canary에 배포한다. 기본 단계는 `5% → 25% → 100%`이며 각 단계에서 최소 10분과 서비스가 정한 최소 결제 건수를 모두 충족할 때까지 관찰한다.
4. 각 단계에서 헬스체크, 합성 결제, 실제 결제 지표, 데이터 정합성, 보안 알람과 로그 수집 상태를 검증한다.
5. 중단 기준이 없을 때만 Release Manager가 다음 단계를 승인한다. 관찰시간 단축은 금지하며 연장은 가능하다.
6. 100% 배포 뒤 최소 30분간 집중 관찰한다. 일일/주간 주기가 있는 변경은 다음 주요 배치 또는 대사 완료까지 티켓을 관찰 상태로 둔다.
7. QA/Verifier와 On-call Operator가 사후 검증을 기록한 뒤 Release Manager가 릴리스를 종료한다.

### 7.1 기본 중단 및 롤백 기준

서비스별 정상 범위가 더 엄격하면 그 기준을 사용한다. 다음 중 하나가 발생하면 rollout을 즉시 멈춘다.

- 합성 결제 또는 핵심 readiness check가 2회 연속 실패
- 결제 API의 내부 5xx/타임아웃 비율이 3분 연속 1% 초과 또는 평시의 2배 초과
- 결제 승인 성공률이 비교 기준선 대비 3%p 이상 하락한 상태가 5분 지속되고 내부 오류와 연관됨
- p95 지연이 기준선의 2배를 5분간 초과하거나 결제사 타임아웃 한계에 접근
- 중복 승인/청구, 원장 불일치, 메시지 유실 등 데이터 무결성 이상이 1건이라도 확인됨
- CDE 보안 알람, 권한 우회, 민감정보 노출 또는 감사로그 중단이 확인됨
- 원인을 5분 안에 확인할 수 없거나 안전성을 입증할 수 없음

Release Manager와 On-call Operator는 각각 단독으로 롤백을 시작할 권한이 있으며, 보안/데이터 무결성 신호는 Security Owner도 즉시 중단시킬 수 있다. **롤백 시작에는 추가 승인이나 원인 규명을 기다리지 않는다.** 실행자는 배포 채널에 즉시 선언하고 Release Manager가 타임라인을 관리한다.

## 8. 롤백 절차

### 8.1 즉시 조치(목표: 이상 감지 후 5분 이내)

1. 이상을 발견한 사람은 배포 채널에 `ROLLBACK`을 선언하고 Release Manager에게 알린다.
2. Release Manager는 rollout과 관련 배치/마이그레이션을 중지하고, 중대 고객 영향이면 IC를 지정해 장애 절차를 시작한다.
3. 배포 시작 시각, 최초 이상 시각, 영향 범위, 현재 버전과 직전 정상 버전을 기록한다.
4. 다른 운영 변경을 동결하고 고객지원/상태 페이지 담당자에게 영향을 알린다.

### 8.2 복구 실행(목표: 15분 이내)

영향을 가장 빨리 줄이는 다음 수단을 순서에 얽매이지 않고 선택한다.

1. 문제 기능을 기능 플래그 또는 kill switch로 비활성화한다.
2. 트래픽을 정상 인스턴스/리전으로 전환하거나 canary를 제거한다.
3. CI/CD의 승인된 rollback job으로 직전 정상 아티팩트 digest와 설정 버전을 재배포한다.
4. 큐 소비자나 배치를 안전하게 중지한다. 처리 중 메시지는 삭제하지 않고 격리한다.
5. DB 변경은 아래 원칙을 따른다.
   - 하위 호환 스키마는 유지하고 애플리케이션만 이전 버전으로 되돌린다.
   - 파괴적 migration을 성급히 역실행하지 않는다. 준비된 roll-forward/보상 migration을 사용한다.
   - 데이터 손상 확산 가능성이 있으면 쓰기를 중단하고 IC와 Service Owner가 복구 시점을 결정한다.
   - 백업 복원처럼 정상 거래가 유실될 수 있는 조치는 영향 범위와 결제사 대사 계획을 확인한 후 IC와 Service Owner가 공동 승인한다.

### 8.3 복구 검증

- [ ] 배포된 버전/digest와 설정이 목표한 정상 버전인지 확인했다.
- [ ] 헬스체크와 합성 승인·취소 흐름이 연속 2회 성공했다.
- [ ] 내부 오류, 승인 성공률, 지연, 큐, DB, 외부 결제사 지표가 기준선으로 회복됐다.
- [ ] 중복/누락/미확정 거래를 조회하고 결제사·원장·주문 간 대사 목록을 만들었다.
- [ ] 감사로그와 보안 모니터링이 정상 수집되고 민감정보 노출이 없다.
- [ ] 최소 30분의 안정화 관찰 후 IC가 서비스 복구를 선언했다.

복구 후 실패한 릴리스의 재배포는 새 변경 티켓/버전과 정규 승인 절차를 거친다. 현장에서 수정한 아티팩트를 그대로 재배포하지 않는다.

### 8.4 사후 조치

- 1영업일 안에 실제 영향 시간, 실패 원인, 탐지·결정·복구 타임라인과 결제 대사 상태를 기록한다.
- Sev-1/Sev-2 또는 결제 중단은 3영업일 안에 비난 없는 사후분석을 열고 재발방지 과제에 소유자와 기한을 지정한다.
- 미확정·중복 가능 거래는 결제사 응답과 내부 원장을 대사하고, 자동 재시도 전 멱등성을 확인한다.
- 롤백이 15분을 넘으면 지연 원인을 별도 개선 과제로 만든다.
- 필요하면 CDE 범위, 런북, 알람, 체크리스트 및 이 문서를 갱신한다.

### 9.1 기록 품질과 보존

- 승인과 배포 기록은 인증된 개인/서비스 계정으로 자동 타임스탬프를 남기며 모든 관련 시스템의 시간을 동기화한다.
- 증적은 변경 후 덮어쓸 수 없는 append-only 또는 변경 이력이 보존되는 저장소에 저장한다.
- 증적과 감사로그 접근은 업무상 필요한 사람으로 제한하고 열람·수정·삭제 행위도 감사로그로 남긴다.
- 릴리스 증적과 관련 감사로그는 **최소 12개월** 보존하고, 최근 **3개월**은 즉시 검색 가능하게 유지한다. 법률·계약·회사 정책이 더 길면 더 긴 기간을 적용한다.
- 비밀정보와 카드 데이터는 증적에서 마스킹한다. PAN 기록이 업무상 불가피하면 승인된 저장소에서 최소 표시 원칙과 접근통제를 적용하며, SAD는 결제 승인 완료 후 어떤 경우에도 저장하지 않는다.
- Release Manager는 릴리스 종료 전에 증적 패키지의 누락을 확인하고, Security Owner는 분기별 표본 점검으로 승인 분리·증적 완전성·보존 여부를 검토한다.

## 10. 정기 검증과 지표

- 분기마다 운영과 유사한 환경에서 애플리케이션 롤백 및 DB 복구 훈련을 실시하고 실제 소요시간과 실패 항목을 기록한다.
- 매월 다음 지표를 Engineering Lead와 Security Owner가 검토한다.
  - 변경 실패율과 롤백률
  - 배포로 인한 결제 영향 시간
  - 이상 감지부터 롤백 결정까지의 시간
  - 롤백 시작부터 서비스 복구까지의 시간
  - 승인/증적 누락률과 비상 변경 비율
  - 취약점 예외의 수, 연령 및 만료 초과 건수
- 두 번 연속 15분 복구 목표를 충족하지 못하면 고위험 변경의 배포를 제한하고 복구 자동화 개선을 우선한다.
