# 개발 프로세스와 검증 체계

## 목표

이 프로젝트의 품질은 문서나 승인 절차의 양이 아니라 다음 특성으로 판단한다.

- 같은 입력과 평가 조건을 재현할 수 있다.
- 점수의 근거를 원시 결과까지 추적할 수 있다.
- 에이전트 실패, 실행 환경 실패, 평가기 버그를 구분한다.
- 신뢰할 수 없는 에이전트 코드가 호스트와 비밀정보를 침해하지 못한다.
- 설치부터 결과 생성까지 사용자가 실제로 밟는 경로가 동작한다.

기술 스택은 아직 정해지지 않았으므로 명령 이름은 예시다. 스택을 선택한 뒤 로컬과 CI가 함께 호출하는 단일 명령(`check`)으로 고정한다.

## 최소 개발 흐름

1. 변경하려는 사용자 동작과 실패 조건을 이슈 본문이나 커밋 설명에 짧게 적는다. 별도 설계 문서는 판단이 오래 남아야 할 때만 만든다.
2. 버그는 먼저 실패를 재현하는 테스트를 추가한다. 새 기능은 공개 동작을 나타내는 테스트와 함께 구현한다.
3. 작은 단위로 구현하고 `check`를 실행한다.
4. 커밋 전 diff에서 디버그 코드, 임시 우회, 비밀정보, 불필요한 의존성 변경을 확인한다.
5. 기본 브랜치에는 필수 CI가 통과한 변경만 합친다. 1인 프로젝트이므로 타인 승인이나 형식적인 사인오프는 요구하지 않는다.

AI가 작성한 코드도 같은 흐름을 따른다. 생성 주체나 그럴듯한 설명은 품질 증거가 아니며, 테스트 결과와 diff가 증거다.

## `check`: 로컬과 CI의 공통 검증 경로

`check`는 현재 스택에 해당하는 아래 작업을 한 번에 실행하고, 하나라도 실패하면 실패 코드로 종료한다.

- 포맷 검사
- 린트와 정적 분석 또는 타입 검사
- 단위 테스트
- 결정론적 통합 테스트
- 빌드 또는 패키지 생성
- 생성한 패키지를 깨끗한 임시 환경에 설치해 예제 평가를 실행하는 스모크 테스트

CI도 별도 로직을 복제하지 않고 이 명령을 호출한다. 의존성은 잠금 파일로 설치하고, 테스트에는 배포용 비밀정보를 주지 않는다. 기본 브랜치에는 이 CI만 필수 상태 검사로 둔다. 지원 운영체제나 런타임이 실제로 늘어날 때에만 매트릭스를 늘린다.

외부 모델 API를 호출하는 테스트는 비용과 비결정성 때문에 기본 `check`에 넣지 않는다. 대신 어댑터 계약 테스트는 가짜 서버로 항상 실행하고, 특정 공급자 지원을 릴리스하기 전에는 실제 자격증명으로 별도 스모크 테스트를 수행한다. 실행하지 못했다면 그 공급자를 검증했다고 표시하지 않는다.

## 테스트 구조

### 단위 테스트

점수 계산, 출력 파싱, 예산 계산, 시간 제한, 오류 분류, 결과 직렬화를 외부 API 없이 검증한다. 경계값과 잘못된 입력을 우선한다.

### 통합 테스트

결정론적 가짜 에이전트로 준비, 실행, 중단, 결과 수집, 정리의 전체 수명주기를 검증한다. 정상 종료뿐 아니라 시간 초과, 비정상 종료, 손상된 출력, 부분 결과도 포함한다.

### 평가 적합성 테스트

버전이 지정된 작은 기준 사례 세트를 둔다. 명백히 성공한 결과, 명백히 실패한 결과, 채점 불가능한 결과가 각각 기대한 판정과 근거를 내는지 확인한다. 점수 공식을 바꾸면 이 사례의 차이를 사람이 읽을 수 있게 확인하고 평가 프로토콜 버전을 올린다.

다음 불변 조건은 속성 테스트나 여러 고정 fixture로 검증한다.

- 같은 원시 결과와 같은 프로토콜 버전은 같은 점수를 낸다.
- 결과의 순서나 표시 형식처럼 의미 없는 차이는 점수를 바꾸지 않는다.
- 실행 환경 오류는 에이전트 실패 점수로 변환되지 않는다.
- 유효하지 않은 결과는 조용히 일부 점수로 흡수되지 않는다.

### 종단간 테스트

릴리스 후보 패키지를 새 환경에 설치한 뒤, 공개 예제를 실행하고 결과 파일을 다시 읽어 검증한다. 소스 트리에서만 가능한 import나 누락된 패키지 파일을 여기서 잡는다.

## 평가의 공정성과 재현성

각 평가 실행은 결과와 함께 최소한 다음 정보를 기록한다.

- 도구와 평가 프로토콜 버전
- 과제 세트 ID와 버전 또는 콘텐츠 해시
- 에이전트, 모델, 공급자, 공개 가능한 설정
- 프롬프트와 허용된 도구·네트워크 정책
- 시간·토큰·비용 등 적용한 예산과 종료 사유
- 난수 시드, 실행 환경, 의존성 잠금 정보
- 원시 로그의 위치 또는 해시, 구조화된 결과, 점수 근거

비밀정보와 개인정보는 저장 전에 제거한다. 원시 관찰값과 정규화된 점수를 분리해 보존하며, 집계 결과만으로 원인을 숨기지 않는다.

공개된 과제나 채점 규칙을 수정해 과거 결과의 의미가 달라지면 기존 버전을 덮어쓰지 않고 새 프로토콜 버전을 만든다. 확률적인 에이전트의 단일 실행을 일반 성능처럼 표현하지 않으며, 반복 횟수와 분산을 결과에 함께 남긴다. 필요한 반복 횟수는 실제 변동성을 보고 정한다.

## 실행 격리와 보안

에이전트가 실행하거나 생성한 코드는 신뢰하지 않는다. 기본 실행기는 다음 경계를 보장해야 한다.

- 임시 작업공간 밖의 파일 접근 차단
- 호스트 자격증명과 환경 변수 비공개
- 네트워크 기본 차단 또는 명시적 허용 목록
- 실행 시간, 프로세스, 메모리, 디스크, 출력 크기 제한
- 중단 시 자식 프로세스까지 종료하고 임시 자원 정리
- 경로 탈출, 심볼릭 링크 탈출, 과대 출력, 손상된 인코딩을 안전하게 처리

이 경계를 강제하지 못하는 로컬 실행 모드는 `sandbox`라고 부르지 않고 위험을 명시한다. 격리 검증은 통제된 환경에서 악성 fixture를 실행해 실제로 경계를 넘지 못하는지 확인한다.

## 변경 종류별 필수 증거

| 변경 | 합치기 전에 필요한 증거 |
|---|---|
| 일반 코드 | `check` 통과 |
| 버그 수정 | 기존 실패를 재현하고 수정 후 통과하는 회귀 테스트 |
| 채점 규칙·과제 | 평가 적합성 테스트, 결과 차이 검토, 프로토콜 버전 변경 |
| 실행기·격리 | 통합 테스트와 해당 보안 경계 테스트 |
| 공급자 어댑터 | 가짜 서버 계약 테스트, 지원 표기 전 실제 스모크 테스트 |
| 릴리스 | 깨끗한 환경의 설치·종단간 테스트, 태그와 소스 커밋 일치 확인 |

릴리스 산출물에는 도구 버전과 소스 커밋을 포함한다. 게시 후 사용자가 보는 설치 명령으로 다시 설치하고 예제 평가를 실행해야 릴리스가 끝난다.

## 실패 처리와 프로세스 유지 원칙

CI가 간헐적으로 실패하면 재시도를 규칙으로 만들지 않는다. 원인을 고치거나 신뢰할 수 없는 검사를 제거한다. 운영 중 발견된 결함은 재현 테스트를 남기되, 그 결함과 무관한 승인 단계나 새 관리 문서는 추가하지 않는다.

커버리지 수치, 테스트 개수, 파일 개수는 품질 게이트로 고정하지 않는다. 커버리지는 누락된 위험을 찾는 참고 자료일 뿐이며, 테스트는 실제 사용자 동작이나 신뢰 경계를 보호해야 한다.

새 필수 검사는 실제로 빠져나간 결함을 잡거나 새 지원 범위를 검증할 때만 추가한다. 추가할 때는 코드 주석이나 CI 설명에 다음을 남긴다.

`sol-simplify: <이 검사가 막는 실제 실패>, remove when <더 이상 해당 실패를 만들 수 없는 조건>`

제품이 정상인데도 반복해서 개발을 막는 검사는 예외 절차를 덧붙이지 말고 수정하거나 삭제한다.
