# 검증 기계 해체 계획

## 판정

현재 게이트는 고쳐서 유지할 대상이 아니라 제거할 대상이다. 제품 소스보다 큰 검증 기계가 제품 결함이 아닌 레포 상태를 검사하며, 이미 정상적인 구현 착수를 전부 막았다. 우회 규칙이나 pin 자동 갱신기를 더 만들지 않는다.

가정: 제시된 수치가 현재 상태를 정확히 나타내며, 실제 파일명과 CI 작업명은 구현 시 레포에서 찾아 대응한다.

## 실행 순서

1. **착수 차단부터 없앤다.**
   - 리졸버를 티켓 착수의 필수 조건과 required CI에서 제거한다.
   - 어제 막힌 4개 티켓은 일반 코드 리뷰와 기존 제품 테스트만으로 진행한다.
   - 전부 거부한 규칙에 예외·override·수동 승인 절차를 붙이지 말고 그 규칙을 삭제한다.

2. **`census pin`을 완전히 삭제한다.**
   - 파일 수·티켓 수의 고정값, 이를 비교하는 검사, 재측정 명령, 생성 파일, CI 호출을 함께 제거한다.
   - 정확한 개수가 제품 동작에 쓰이지 않는다면 대체하지 않는다. 현황 표시가 꼭 필요해도 커밋된 기준값 없이 실행 시 계산하는 비차단 정보로만 둔다.

3. **리졸버와 계약 테스트를 해체한다.**
   - 각 규칙에 “이 규칙이 없으면 사용자가 겪는 구체적인 제품 실패가 무엇인가?”를 묻는다.
   - 티켓 형식, 레포 census, 문서 간 정합, 작업 순서처럼 절차만 검사하는 규칙과 테스트는 삭제한다.
   - 실제 제품 실패를 잡는 규칙만 해당 제품 모듈의 단위·통합 테스트로 옮긴다. 8,683줄 계약 테스트를 새 구조에 그대로 이식하지 않는다.
   - 남은 제품 테스트가 통과하면 5,745줄 리졸버와 진입점·설정·문서 참조를 삭제한다.

4. **CI를 제품 검증으로 축소한다.**
   - 필수 검사는 빌드, 타입/정적 검사, 실제 동작 테스트, 보안 경계, 데이터 마이그레이션처럼 실패가 제품 결함을 뜻하는 것만 남긴다.
   - 레포 전체 파일 수, 티켓 총수, 브랜치 합류 순서, 생성된 절차 상태에 의존하는 검사는 두지 않는다.

## 완료 확인

- 리졸버와 census 검사를 호출하는 required 경로가 없다.
- 커밋된 file/ticket count pin과 이를 갱신하는 코드가 없다.
- 두 브랜치가 각각 파일이나 티켓을 추가해도 검증 기준값 충돌이 생기지 않는다.
- 막혔던 4개 티켓이 별도 예외 없이 착수 가능하다.
- 기존 제품 빌드와 실제 동작 테스트는 통과하며, 삭제 후 남은 실패는 제품 결함과 직접 연결된다.
- 최종 변경은 새 검증 계층을 추가하지 않고 순삭제가 중심이다.
