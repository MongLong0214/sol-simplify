# PR 리뷰 프로세스

목표는 모든 변경을 작성자 외 한 명이 이해하고, 병합 전에 중요한 문제를 발견하는 것이다.

## 1. PR 올리기

- PR 설명에 **무엇을**, **왜** 바꿨는지와 확인 방법을 적는다.
- 작성자는 리뷰를 요청하기 전에 변경 내용을 스스로 다시 읽고 관련 테스트를 실행한다.
- 아직 작업 중이면 Draft PR로 올리고, 병합 가능한 상태가 되면 리뷰를 요청한다.
- 가능하면 PR 하나에는 한 가지 목적만 담는다.

## 2. 리뷰하기

- 작성자를 제외한 팀원 한 명의 승인이면 충분하다. 관련 맥락을 가장 잘 아는 사람에게 먼저 요청한다.
- 리뷰어는 다음 순서로 본다: 동작의 정확성, 보안·데이터 손실 위험, 테스트, 이해하기 쉬운 코드인지 여부.
- 반드시 고쳐야 하는 의견과 선택적인 제안을 분명히 구분한다. 취향 차이만으로 병합을 막지 않는다.
- 리뷰어는 승인하거나, 수정이 필요한 이유를 구체적으로 남긴다.

## 3. 수정과 병합

- 작성자는 모든 필수 의견에 반영 내용이나 반대 이유를 답한다.
- 큰 수정이 생기면 다시 리뷰를 요청한다. 오탈자처럼 결과에 영향이 없는 수정은 재승인이 필요 없다.
- 필수 의견이 해결되고 테스트가 통과했으며 한 명이 승인하면 작성자가 병합한다.
- 병합 후 문제가 발견되면 해당 변경의 작성자가 우선 대응하되, 필요하면 팀이 함께 해결한다.

## 의견이 합의되지 않을 때

작성자와 리뷰어가 근거를 확인해도 합의하지 못하면 세 번째 팀원이 논의에 참여한다. 세 사람이 현재 PR의 안전성과 범위만 기준으로 결론을 내리고, 별도 규칙은 반복되는 문제가 생길 때만 추가한다.

> sol-simplify: 리뷰 누락과 장기 논쟁을 줄이기 위해 이 절차를 둔다. 절차 때문에 작업이 반복해서 불필요하게 막히면 원인이 된 규칙을 제거하거나 완화한다.
