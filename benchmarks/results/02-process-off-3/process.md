# 개발 프로세스와 검증 체계

## 1. 문서의 목적

이 문서는 AI 코딩 에이전트 평가 도구를 신뢰할 수 있게 개발하고 배포하기 위한 기본 운영 규칙이다. 현재 전제는 다음과 같다.

- 프로젝트는 코드가 없는 초기 상태다.
- 메인테이너는 한 명이다.
- 코드는 공개되며 외부 기여를 받을 수 있다.
- 기술 스택, CI 서비스, 패키지 형식은 아직 정하지 않았다.
- 평가 대상이 생성한 코드는 신뢰할 수 없는 입력으로 간주한다.

목표는 절차의 양을 늘리는 것이 아니라, 적은 유지 비용으로 다음 질문에 항상 답할 수 있게 하는 것이다.

1. 이 변경은 의도대로 동작하는가?
2. 평가 결과는 재현 가능하고 비교 가능한가?
3. 실패가 에이전트, 평가 도구, 외부 서비스 중 어디에서 발생했는가?
4. 비신뢰 코드를 실행해도 호스트와 비밀 정보가 안전한가?
5. 문제가 생겼을 때 잘못된 결과를 식별하고 철회할 수 있는가?

## 2. 품질 원칙

1. **평가 결과보다 평가 근거를 먼저 보존한다.** 점수뿐 아니라 입력, 환경, 로그, 산출물, 채점 근거와 버전을 남긴다.
2. **제어 영역은 결정적으로 만든다.** 오케스트레이션, 파싱, 채점, 집계는 같은 입력에 같은 결과를 내야 한다. 모델이나 네트워크의 비결정성은 별도로 표시한다.
3. **실패 원인을 분리한다.** 과제 실패, 에이전트 실패, 인프라 실패, 채점 실패를 하나의 `failed` 상태로 합치지 않는다.
4. **비교 가능성을 버전으로 보장한다.** 과제, 실행 환경, 어댑터, 채점 규칙 중 하나라도 의미 있게 바뀌면 평가 버전을 바꾼다.
5. **보안은 기능 요구사항이다.** 샌드박스가 없는 실행기는 완료된 기능이 아니다.
6. **자동화된 증거가 없는 예외는 만료되어야 한다.** 품질 게이트 우회에는 사유, 영향 범위, 담당자, 만료일이 필요하다.
7. **1인 유지보수에 맞게 설계한다.** 형식적인 승인 대신 작은 변경, 자동 검사, 시간차 자기 검토, 재현 가능한 릴리스로 실수를 줄인다.

## 3. 품질 모델과 우선순위

| 영역 | 확인할 속성 | 대표 검증 |
| --- | --- | --- |
| 정확성 | 실행·채점·집계가 명세와 일치 | 단위, 계약, 속성 기반, 골든 테스트 |
| 평가 타당성 | 점수가 실제 코딩 성능을 반영 | 기준 에이전트, 수동 표본 검토, 채점기 보정 |
| 재현성 | 동일 조건에서 결과와 판정이 재현 | 환경 잠금, 리플레이, provenance 비교 |
| 격리와 보안 | 대상 코드가 호스트·비밀에 접근 불가 | 위협 모델, 침투 픽스처, 제한 검증 |
| 신뢰성 | 중단·재시도·부분 실패를 올바르게 처리 | 장애 주입, 복구, 멱등성 테스트 |
| 호환성 | 스키마와 플러그인 변화가 통제됨 | 소비자 계약, 마이그레이션 테스트 |
| 유지보수성 | 혼자서 변경과 장애를 감당 가능 | 정적 검사, 문서, 복잡도·의존성 점검 |
| 사용성 | 설치부터 결과 해석까지 명확 | 깨끗한 환경의 설치·튜토리얼 테스트 |

우선순위는 `잘못된 결과 방지 > 보안 > 결과 재현 > 기능 수 > 성능 최적화` 순서로 둔다. 공개 순위나 비교 수치를 제공하기 전에는 정확성, 타당성, 재현성 기준을 모두 만족해야 한다.

## 4. 아키텍처 경계와 필수 산출물

구현 전에 다음 구성요소를 분리한다. 분리는 장애 귀속과 독립 테스트를 위한 것이다.

- **Task spec:** 저장소, 시작 상태, 지시문, 제한, 기대 결과, 라이선스
- **Environment:** OS·런타임·도구·의존성과 네트워크 정책
- **Agent adapter:** 공통 입력을 각 에이전트 호출 규약으로 변환
- **Runner:** 시간·자원·프로세스 수 제한 아래 작업을 실행
- **Recorder:** 이벤트, 명령, 종료 상태, 비용, 산출물과 로그를 수집
- **Scorer:** 테스트 및 판정 규칙을 실행하고 근거가 있는 점수를 생성
- **Aggregator:** 여러 과제·시드의 결과와 불확실성을 집계
- **Reporter:** 원시 결과를 수정하지 않고 사람이 읽는 보고서를 생성

각 실행은 최소한 다음 실행 출처 정보(provenance)를 기계 판독 가능한 형태로 보존한다.

- 실행 ID와 결과 스키마 버전
- 도구 커밋과 배포 버전
- 과제 ID·버전·콘텐츠 해시
- 환경 이미지의 불변 digest와 툴체인 버전
- 에이전트·모델·제공자 식별자 및 알려진 설정값
- 시스템/사용자 프롬프트 또는 그 해시와 공개 가능 여부
- 난수 시드, 시간 제한, 자원 제한, 네트워크 정책
- 시작·종료 시각, 단계별 종료 코드와 실패 분류
- 토큰·비용·지연 시간(제공자가 반환하는 범위)
- 생성된 패치, 테스트 결과, 채점 근거, 원시 로그의 해시

비밀 정보와 민감한 모델 내부 데이터는 provenance에 직접 기록하지 않는다. 비공개 값은 안정적인 식별자나 해시로 대체하고, 로그 저장 전 별도 마스킹(redaction) 단계를 거친다.

## 5. 변경 프로세스

### 5.1 작업 시작 조건

모든 변경은 이슈 또는 짧은 변경 메모에서 시작한다. 다음 내용이 있으면 개발 준비가 된 것으로 본다.

- 해결할 문제와 사용자가 관찰할 결과
- 포함 범위와 제외 범위
- 검증 가능한 수용 조건
- 실패 시 영향: `low`, `medium`, `high`, `critical`
- 필요한 테스트 수준과 문서 변경

다음 변경에는 구현 전에 간단한 ADR(Architecture Decision Record)을 작성한다.

- 공개 결과 스키마 또는 플러그인 계약 변경
- 채점 방식, 통계 방식, 평가 과제 변경
- 샌드박스·권한·비밀·네트워크 경계 변경
- 새 외부 서비스 또는 런타임 의존성 추가
- 기존 평가 결과의 비교 가능성을 깨는 변경

ADR에는 맥락, 결정, 대안, 장단점, 되돌리는 방법을 한 페이지 이내로 기록한다.

### 5.2 구현 규칙

- 한 변경은 한 가지 관찰 가능한 목적만 갖도록 작게 나눈다.
- 새 동작은 테스트와 함께 작성한다. 버그 수정은 먼저 실패를 재현하는 회귀 테스트를 추가한다.
- 오류를 삼키지 않는다. 사용자 오류, 대상 에이전트 오류, 인프라 오류, 내부 오류를 서로 다른 타입과 종료 코드로 표현한다.
- 시간, 난수, 파일시스템, 네트워크, 모델 API는 경계 뒤에 두어 테스트에서 대체 가능하게 한다.
- 기본 경로는 오프라인에서 테스트할 수 있어야 한다. 실제 모델 호출은 핵심 CI 통과 조건으로 사용하지 않는다.
- 로그는 구조화하고 실행 ID를 포함한다. 비밀, 인증 헤더, 전체 환경 변수는 기록하지 않는다.

### 5.3 자기 리뷰와 병합

메인테이너도 `main`에 직접 커밋하지 않고 PR을 사용한다. PR에는 다음을 포함한다.

- 무엇을 왜 바꿨는지
- 위험도와 실패·롤백 방식
- 수용 조건별 검증 증거
- 사용자 문서, 스키마, 보안 영향
- 평가 결과의 과거 버전과 비교 가능 여부

`high` 또는 `critical` 변경은 CI 성공 후 즉시 병합하지 않고 한 번의 시간차 자기 리뷰를 한다. diff를 처음부터 다시 읽고, 실패 경로와 권한 확대를 별도로 확인한다. 외부 리뷰어가 없다는 이유로 자동 검사를 우회하지 않는다.

### 5.4 완료의 정의

변경은 다음 조건을 모두 만족할 때 완료다.

- 수용 조건이 자동 테스트 또는 명시된 수동 증거로 확인됨
- 필수 CI가 모두 성공하고 비결정적 재실행에 의존하지 않음
- 새 오류 경로와 경계 조건이 테스트됨
- 사용자 동작 변경에 문서와 예제가 동반됨
- 스키마·CLI 변경에 호환성 판단과 마이그레이션 경로가 있음
- 보안·개인정보·라이선스 영향이 검토됨
- 필요한 changelog와 ADR이 갱신됨
- 릴리스 후 관찰할 지표와 롤백 방법이 분명함

## 6. 테스트 전략

### 6.1 테스트 계층

1. **단위 테스트:** 파서, 상태 전이, 제한 계산, 점수 계산, 오류 분류를 외부 I/O 없이 검증한다.
2. **계약 테스트:** Task spec, 결과 스키마, 어댑터, 이벤트 로그의 생산자와 소비자가 같은 계약을 따르는지 검증한다.
3. **속성 기반·퍼즈 테스트:** 경로, 아카이브, 로그 파서, 점수 집계, 잘린 출력, 잘못된 Unicode와 큰 입력을 검증한다.
4. **변이·장애 주입 테스트:** scorer 조건, 종료 코드, 타임아웃, 손상된 산출물을 의도적으로 바꾸어 기존 테스트가 오류를 실제로 잡는지 확인한다.
5. **통합 테스트:** 임시 저장소와 로컬 샌드박스에서 runner–recorder–scorer 흐름을 검증한다.
6. **종단 간 테스트:** 실제 모델 대신 행동이 고정된 가짜 에이전트로 설치부터 보고서 생성까지 실행한다.
7. **라이브 테스트:** 실제 제공자 API와 모델의 연결 상태를 확인한다. 비용·가용성·비결정성 때문에 PR의 필수 게이트가 아니라 예약 실행으로 둔다.

테스트 픽스처에는 최소한 다음 에이전트를 둔다.

- 정상 패치를 만드는 에이전트
- 아무 작업도 하지 않는 에이전트
- 잘못된 출력 형식을 만드는 에이전트
- 시간 초과, 비정상 종료, 과도한 출력을 만드는 에이전트
- 네트워크·호스트 파일·비밀 접근을 시도하는 적대적 에이전트
- 정답은 맞지만 예상과 다른 구현을 만드는 에이전트

### 6.2 커버리지 정책

커버리지는 목표가 아니라 누락 탐지 신호로 사용한다.

- 보안 경계, 점수 계산, 결과 집계, 상태 전이: 명세의 모든 분기와 오류 경로를 테스트한다.
- 전체 라인 커버리지: 초기 기준선을 만든 뒤 감소를 허용하지 않는다.
- 변경된 코드: 최소 90% 라인 커버리지를 기본값으로 둔다.
- 생성 코드, 단순 선언, 플랫폼상 실행 불가능한 방어 코드는 근거를 남기고 제외할 수 있다.
- 커버리지가 높아도 경계값, 실패 경로, 속성 검증이 없으면 완료로 보지 않는다.

### 6.3 비결정적 테스트 정책

- 테스트는 고정 시드와 제어된 시계를 사용하고, 실패 시 시드를 출력한다.
- `재실행하면 통과`를 수정으로 인정하지 않는다.
- 새 flaky test는 격리만 하고 잊지 않는다. 담당 이슈와 최대 14일의 만료일을 지정한다.
- 필수 테스트의 최근 100회 flake 비율이 1%를 넘으면 기능 개발보다 먼저 안정화한다.
- 외부 API 실패는 제품 실패와 분리하여 기록한다.

## 7. CI 품질 게이트

개발자는 기술 스택을 정한 뒤 아래 동작을 하나의 표준 명령(예: `./scripts/verify`)으로 제공해야 한다. 로컬과 CI는 같은 명령을 사용한다.

| 단계 | 실행 시점 | 필수 검사 | 목표 시간 | 실패 처리 |
| --- | --- | --- | --- | --- |
| Fast | 커밋 전/모든 PR | 포맷, 린트, 타입, 단위, 스키마 | 2분 이내 | 병합 차단 |
| Full | 모든 PR | 계약, 통합, E2E, 커버리지, 문서 예제, 의존성·라이선스 검사 | 15분 이내 | 병합 차단 |
| Adversarial | `main`/매일 | 퍼즈, 장애 주입, 샌드박스 탈출 회귀, 반복 실행 | 시간 제한 내 | 릴리스 차단, 이슈 생성 |
| Live | 예약/수동 | 실제 제공자 smoke, 비용·지연·응답 계약 | 예산 제한 | 추세 경고; 핵심 로직 병합과 분리 |
| Release | 태그 후보 | 깨끗한 설치, 전체 회귀, 호환성, 재현성, 패키지 검증 | 제한 없음 | 배포 차단 |

추가 규칙:

- `main`은 보호하고 필수 검사가 없거나 실패한 병합을 금지한다.
- 외부 fork의 CI에서는 배포 키나 모델 API 키를 전달하지 않는다.
- 비밀을 다루는 이벤트와 코드가 실행되는 이벤트를 분리한다. 특히 비신뢰 PR 코드를 높은 권한 컨텍스트에서 실행하지 않는다.
- 의존성은 lockfile로 고정하고 자동 업데이트 PR도 전체 검증을 통과시킨다.
- 정적 보안 분석, 비밀 탐지, 알려진 취약점, 라이선스 호환성 검사를 자동화한다.
- CI 이미지와 액션은 변경 가능한 태그가 아니라 불변 버전 또는 digest에 고정한다.

## 8. 평가 시스템 자체의 검증

이 도구의 핵심 제품은 점수가 아니라 **점수를 믿을 근거**다. 일반 소프트웨어 테스트와 별도로 다음 meta-evaluation을 수행한다.

### 8.1 기준 과제와 골든 결과

- 작고 명확한 기준 과제 모음을 버전 관리한다.
- 각 과제에는 성공, 부분 성공, 실패 예시와 기대 채점 근거를 둔다.
- scorer 변경 시 모든 골든 결과를 재실행하고 diff를 검토한다.
- 골든 파일 갱신은 테스트 통과를 위한 기계적 작업으로 취급하지 않는다. 변경 사유와 영향받는 과제·점수를 PR에 적는다.
- 과제의 테스트가 구현 형태를 과도하게 고정하지 않는지, 의도와 다른 유효한 해법을 허용하는지 확인한다.

### 8.2 채점기 보정

가능하면 빌드, 테스트, 정적 속성과 같은 객관적 신호를 우선한다. 모델 기반 judge가 필요한 경우 다음을 지킨다.

- judge 모델, 프롬프트, temperature, 출력 스키마를 고정하고 버전 기록
- 정답·오답·경계 사례로 구성한 보정 세트 유지
- 릴리스마다 무작위 표본을 눈가림 수동 판정한 뒤 judge와 비교
- 합의율뿐 아니라 false pass와 false fail을 따로 계산
- 불일치가 사전 정의한 허용치를 넘으면 공개 비교를 중단하고 원인을 조사
- judge가 자신 또는 같은 계열 모델에 유리할 수 있음을 결과의 한계에 명시
- judge의 설명을 사실로 간주하지 않고, 검증 가능한 근거와 연결

초기 목표는 보정 세트에서 false pass 1% 미만, false fail 5% 미만으로 둔다. 다만 표본이 작을 때 이 비율을 성능 보장처럼 표현하지 않는다. 원자료 수, 사례, 신뢰구간을 함께 공개하고 충분한 근거가 쌓이기 전의 모델 기반 판정은 `experimental`로 표시한다. 릴리스 차단 임계값과 최소 표본 수는 파일럿 결과를 본 뒤, 공개 비교를 시작하기 전에 ADR로 확정한다.

### 8.3 통계와 비교 규칙

- 비교 대상은 같은 과제 버전, 환경 digest, 예산, 제한, 채점기 버전을 사용한다.
- 순서 효과가 있으면 실행 순서를 무작위화하거나 교차 배치한다.
- 모델의 비결정성이 결과에 영향을 주면 여러 시드 또는 반복 실행을 사용한다.
- 평균 하나만 공개하지 않고 표본 수, 분산 또는 신뢰구간, 실패·무효 실행 수를 함께 제공한다.
- 과제별 짝지은 결과를 우선하고, 가능한 경우 bootstrap 신뢰구간을 제공한다.
- 제외 조건과 중단 규칙은 실행 전에 정한다. 결과를 본 뒤 유리한 실행만 제외하지 않는다.
- `pass@k`, 비용, 지연 시간은 별도 지표로 보고한다. 하나의 종합 점수로 정보 손실을 숨기지 않는다.
- 통계적으로 불확실한 차이를 순위의 확정적 우열로 표현하지 않는다.

### 8.4 결과 상태와 오류 귀속

모든 실행은 다음 중 하나의 최종 상태를 가져야 한다.

- `completed`: 실행과 채점이 유효하게 완료됨
- `agent_failed`: 대상 에이전트의 오류, 잘못된 동작 또는 제한 초과
- `task_invalid`: 과제 또는 기준 정답의 결함
- `infra_failed`: runner, 저장소, 네트워크, 제공자 장애
- `scoring_failed`: 채점기가 유효한 판정을 만들지 못함
- `cancelled`: 사용자 또는 정책에 따라 중단됨

`completed`가 아닌 실행을 자동으로 0점 처리하지 않는다. 0점은 유효한 평가에서 실패한 경우에만 사용한다. 무효 실행의 재시도 정책과 최대 횟수는 사전에 고정한다.

### 8.5 오염과 데이터 누출

- 과제마다 출처, 라이선스, 생성·수정 이력과 공개 시점을 기록한다.
- 공개 개발 세트와 릴리스 검증 세트를 구분한다.
- 공개 과제로 평가한 결과에는 학습 데이터 오염 가능성을 명시한다.
- 비공개 holdout을 운영한다면 접근을 최소화하고 주기적으로 교체하되, 방법론과 집계 규칙은 공개한다.
- 과제나 채점 테스트가 agent 컨텍스트로 유출되지 않는지 canary와 접근 로그로 확인한다.
- 개인정보, 실제 비밀, 라이선스가 불명확한 코드는 평가 데이터에 넣지 않는다.

## 9. 재현성 검증

재현성에는 두 수준이 있다.

1. **판정 재현:** 보존된 에이전트 산출물을 같은 scorer로 다시 채점하면 같은 결과가 나와야 한다. 모든 PR의 필수 게이트다.
2. **실행 재현:** 같은 입력으로 에이전트를 다시 호출했을 때 통계적으로 일관된 결과가 나와야 한다. 모델 비결정성 때문에 완전 동일성을 요구하지 않고 예약 검증으로 추세를 본다.

릴리스 전 대표 결과를 깨끗한 환경에서 리플레이해 다음을 확인한다.

- 입력·환경·산출물 해시가 기록과 일치
- 네트워크가 없어도 보존된 실행의 재채점 가능
- 같은 scorer가 같은 세부 점수와 최종 점수를 생성
- 보고서가 원시 결과를 변경하지 않음
- 실패 단계와 원인이 동일하게 분류됨

서로 다른 평가 버전의 점수는 기본 UI와 보고서에서 직접 비교하지 않는다. 비교를 지원하려면 변환 근거와 검증된 연결 실험이 필요하다.

## 10. 보안 검증

첫 runner 구현 전에 위협 모델을 작성하고 다음 공격자를 포함한다.

- 악의적 과제 저장소와 빌드 스크립트
- 악의적이거나 오작동하는 에이전트 출력
- prompt injection이 포함된 코드·이슈·로그
- 취약하거나 탈취된 의존성 및 CI 작업
- 결과 파일을 여는 사용자에 대한 HTML/터미널 주입

기본 실행 정책은 다음과 같다.

- 일회성 컨테이너 또는 VM, 비루트 사용자, 읽기 전용 기반 이미지 사용
- 호스트의 Docker socket, 홈 디렉터리, SSH agent, 클라우드 metadata 차단
- 작업 디렉터리 외 쓰기 금지, 과제 원본은 읽기 전용 제공
- 네트워크 기본 차단; 필요한 경우 목적지와 프로토콜 allowlist 적용
- CPU, 메모리, 디스크, PID, 실행 시간, 로그 크기 제한
- 하위 프로세스까지 종료하고 실행 후 환경 폐기
- 비밀은 최소 범위·최단 수명의 broker를 통해 제공하고 대상 코드에 직접 노출하지 않음
- 경로 traversal, symlink, archive bomb, ANSI/HTML 주입을 입력 경계에서 검증
- 원시 산출물을 호스트에서 자동 실행하거나 신뢰 영역의 웹 페이지로 그대로 렌더링하지 않음

보안 회귀 세트는 `/etc`·호스트 작업공간·환경 변수 읽기, 외부 통신, fork bomb, 디스크 고갈, 시간 초과, symlink 탈출, 악성 아카이브와 로그 주입 시도를 포함한다. 하나라도 경계를 넘으면 릴리스를 차단한다.

취약점 신고를 위한 `SECURITY.md`와 비공개 연락 경로를 첫 공개 릴리스 전에 준비한다. 보안 경계 변경은 `critical`로 분류하고 별도 ADR과 시간차 자기 리뷰를 요구한다.

## 11. 버전과 릴리스

다음 버전을 독립적으로 관리한다.

- 제품/CLI 버전: 사용자 기능과 API에 SemVer 적용
- 결과 스키마 버전: 파서 호환성과 마이그레이션 관리
- 벤치마크 버전: 과제 집합·환경·채점 의미의 묶음
- 어댑터 버전: 에이전트 호출 방식과 기본 설정

점수, 통과 조건, 과제 테스트, 기본 예산, 환경이 결과 의미를 바꾸면 벤치마크 버전을 올린다. 기존 결과를 새 규칙으로 조용히 덮어쓰지 않는다.

릴리스 후보는 다음 절차를 통과한다.

1. 버전과 changelog를 확정하고 비교 가능성 변경을 명시한다.
2. 깨끗한 지원 플랫폼에서 소스와 배포 패키지를 각각 설치한다.
3. Full·Adversarial 게이트와 기준 과제 전체를 실행한다.
4. 이전 안정 버전의 결과를 재채점해 호환성 또는 의도된 차이를 확인한다.
5. SBOM, 의존성·라이선스·비밀 탐지 결과를 확인한다.
6. 패키지 내용에 테스트 비밀, 로컬 경로, 불필요한 데이터가 없는지 검사한다.
7. 태그와 릴리스 산출물을 자동 생성하고 checksum을 게시한다.
8. 최소 한 번의 실제 설치 smoke test 후 안정 릴리스로 승격한다.

초기에는 사람이 실행하는 release checklist를 사용하되, 같은 실수가 두 번 발견되면 해당 항목을 자동화한다. 릴리스는 되돌릴 수 있어야 하며 최근 안정 버전 설치 방법과 잘못된 평가 결과의 철회 방법을 문서화한다.

## 12. 장애와 잘못된 결과 처리

다음은 품질 사고로 취급한다.

- 샌드박스 또는 비밀 경계 침해
- 점수 계산 오류나 잘못된 순위 공개
- 재현에 필요한 데이터 손실
- 과제 정답·테스트 결함으로 인한 광범위한 오판
- 결과 스키마를 조용히 깨뜨리는 변경

대응 순서는 다음과 같다.

1. 영향받는 릴리스와 결과 게시를 중단한다.
2. 원시 증거를 보존하고 영향 범위를 실행 ID와 버전으로 식별한다.
3. 공개 결과에 `withdrawn` 또는 `invalidated` 표시를 하며 삭제로 흔적을 없애지 않는다.
4. 원인을 수정하고 반드시 회귀 테스트를 추가한다.
5. 영향, 발견 경로, 수정, 재발 방지를 짧은 postmortem으로 공개한다.
6. 수정 버전과 재평가 필요 여부를 알린다.

보안 사고는 공개 전에 신고자 보호와 사용자 완화책을 우선하며, 자세한 공개 시점은 실제 위험을 고려한다.

## 13. 운영 지표와 정기 점검

매월 다음 지표를 짧게 검토한다.

- 필수 CI 성공률, p50/p95 시간, flaky test 비율
- 릴리스 후 발견된 결함과 회귀 테스트 누락 수
- `infra_failed`와 `scoring_failed` 비율 및 주요 원인
- 판정 리플레이 성공률(목표 100%)
- 채점기 수동 판정 불일치율과 false pass/false fail
- 대표 과제의 결과 분산과 성능·비용 회귀
- 취약 의존성 해결 시간과 미해결 예외 수
- 오래된 과제, 격리 테스트, 만료된 waiver 수

지표는 메인테이너를 평가하기 위한 것이 아니라 자동화와 설계가 약한 지점을 찾는 데 사용한다. 수치가 악화되면 새 기능보다 원인 제거를 우선한다.

## 14. 예외(waiver) 정책

품질 게이트를 일시적으로 우회해야 할 때는 저장소에 다음을 기록한다.

- 우회하는 검사와 구체적인 실패
- 사용자·보안·평가 신뢰성에 미치는 영향
- 임시 완화책
- 연결된 수정 이슈
- 만료일(기본 14일, 보안 경계는 최대 7일)

`critical` 보안 검사, 점수 계산 정확성, 판정 재현성은 공개 릴리스에서 우회할 수 없다. 만료된 waiver가 있으면 새 릴리스를 차단한다.

## 16. PR 체크리스트

```text
[ ] 문제, 범위, 수용 조건이 명확하다.
[ ] 실패를 재현하거나 새 동작을 증명하는 테스트가 있다.
[ ] 오류 귀속(agent/task/infra/scoring)이 유지된다.
[ ] 결과·과제·스키마의 비교 가능성 영향을 확인했다.
[ ] 비신뢰 입력, 권한, 네트워크, 비밀 노출을 확인했다.
[ ] 로그와 산출물에 민감 정보가 남지 않는다.
[ ] 문서, 예제, changelog 또는 ADR을 필요한 만큼 갱신했다.
[ ] 로컬 표준 검증과 필수 CI가 통과했다.
[ ] 롤백 또는 비활성화 방법이 있다.
```

이 문서는 초기 기본값이다. 절차를 바꿀 때는 단순히 느슨하게 만들지 말고, 기존 위험을 어떤 자동화나 검증 증거로 대체하는지 함께 기록한다.
