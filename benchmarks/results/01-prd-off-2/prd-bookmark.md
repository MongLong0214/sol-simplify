# 게시글 북마크 기능 PRD

## 1. 문서 정보

| 항목 | 내용 |
| --- | --- |
| 기능명 | 게시글 북마크 및 내 북마크 목록 |
| 상태 | Draft |
| 우선순위 | P1 |
| 대상 스택 | Next.js 15 App Router, Supabase, React Query |
| 대상 사용자 | 로그인 사용자 |

## 2. 배경과 문제

사용자는 다시 보고 싶은 게시글을 서비스 안에 저장할 방법이 없다. 그 결과 브라우저 북마크나 외부 메모에 의존하거나, 이전에 본 게시글을 다시 검색해야 한다.

로그인 사용자가 게시글을 한 번의 조작으로 저장·해제하고, 마이페이지에서 저장한 게시글을 다시 찾을 수 있는 개인 북마크 기능을 제공한다.

## 3. 목표

- 로그인 사용자가 게시글 상세 화면에서 북마크 상태를 확인하고 추가·해제할 수 있다.
- 북마크 상태가 세션과 기기를 넘어 계정 단위로 유지된다.
- 사용자가 마이페이지에서 북마크한 게시글을 최신 북마크순으로 조회할 수 있다.
- 각 사용자의 북마크 데이터가 다른 사용자에게 노출되거나 수정되지 않는다.
- 네트워크 지연 중에도 즉각적인 피드백을 제공하고, 실패 시 UI를 실제 서버 상태로 복구한다.

## 4. 비목표

MVP에서 다음 항목은 제외한다.

- 북마크 폴더, 태그, 메모 및 정렬 방식 선택
- 북마크 목록 공개 및 공유
- 게시글별 북마크 수 표시와 인기 순위 반영
- 비로그인 사용자의 로컬 북마크 및 로그인 후 병합
- 북마크 알림, 추천, 내보내기
- 게시글 목록 카드의 북마크 버튼(상세 화면만 MVP 범위)

## 5. 주요 사용자 시나리오

### 5.1 북마크 추가

1. 로그인 사용자가 게시글 상세 페이지에 진입한다.
2. 시스템은 해당 사용자의 북마크 여부를 조회한다.
3. 사용자가 비활성 상태의 `북마크` 버튼을 누른다.
4. 버튼이 즉시 활성 상태로 바뀌고 북마크가 서버에 저장된다.
5. 새로고침하거나 다른 기기에서 접속해도 활성 상태가 유지된다.

### 5.2 북마크 해제

1. 사용자가 활성 상태의 `북마크 해제` 버튼을 누른다.
2. 버튼이 즉시 비활성 상태로 바뀌고 북마크가 서버에서 제거된다.
3. 마이페이지 목록에서도 해당 게시글이 제거된다.

### 5.3 내 북마크 조회

1. 로그인 사용자가 `마이페이지 > 북마크`로 이동한다.
2. 북마크한 게시글을 북마크한 시각의 내림차순으로 확인한다.
3. 항목을 누르면 게시글 상세 페이지로 이동한다.
4. 목록에서 북마크를 해제하면 해당 항목이 즉시 사라진다.

### 5.4 비로그인 사용자

1. 비로그인 사용자가 게시글의 북마크 버튼을 누른다.
2. 시스템은 로그인 화면 또는 로그인 모달로 안내한다.
3. 로그인 완료 후 원래 게시글로 돌아온다. 의도하지 않은 저장을 막기 위해 북마크를 자동 추가하지는 않는다.

## 7. UX/UI 요구사항

### 7.1 게시글 상세 버튼

- 위치: 게시글의 기존 주요 액션 영역(공유, 좋아요 등이 있다면 같은 그룹).
- 비활성 상태: 윤곽선 북마크 아이콘과 `북마크` 레이블.
- 활성 상태: 채워진 북마크 아이콘과 `북마크 해제` 레이블.
- 요청 진행 중 연속 클릭을 방지하되, 낙관적 상태 변경은 즉시 보여준다.
- 성공 토스트는 필수가 아니며 시각적 상태 변경으로 성공을 알린다. 실패 시에는 오류 토스트 또는 인라인 메시지를 표시한다.
- 아이콘만 표시되는 화면 폭에서도 접근 가능한 이름을 유지한다.

### 7.2 마이페이지 목록

- 경로 예시: `/mypage/bookmarks` (기존 라우팅 규칙이 있으면 그 규칙을 우선한다).
- 기존 게시글 카드 컴포넌트가 있으면 재사용한다.
- 최초 로딩은 스켈레톤, 추가 페이지 로딩은 목록 하단 진행 상태를 사용한다.
- 빈 상태 예시: `아직 북마크한 게시글이 없습니다.`와 `게시글 둘러보기` 링크.
- 항목 내 해제 버튼은 게시글 상세로 이동하는 링크와 별도의 클릭 영역을 가진다.

### 7.3 접근성

- 버튼은 실제 `<button>` 요소를 사용한다.
- `aria-pressed`로 북마크 상태를 전달한다.
- 접근 가능한 이름은 상태에 따라 `북마크 추가`, `북마크 해제`로 제공한다.
- 키보드 조작과 명확한 포커스 표시를 지원한다.
- 상태를 색상만으로 구분하지 않고 아이콘 형태 또는 레이블을 함께 변경한다.

## 8. 데이터 모델

`posts.id`가 UUID이고 게시글 테이블이 `public.posts`에 있다는 가정이다. 실제 스키마가 다르면 외래 키 타입과 테이블명만 기존 모델에 맞춘다.

```sql
create table public.bookmarks (
  user_id uuid not null references auth.users(id) on delete cascade,
  post_id uuid not null references public.posts(id) on delete cascade,
  created_at timestamptz not null default now(),
  primary key (user_id, post_id)
);

create index bookmarks_user_created_post_idx
  on public.bookmarks (user_id, created_at desc, post_id desc);
```

- 복합 기본 키로 사용자·게시글 조합의 중복을 방지한다.
- `created_at`은 목록 정렬과 커서 페이지네이션에 사용하며 클라이언트 입력을 받지 않는다.
- 게시글이 소프트 삭제되는 구조라면 목록 조회 시 기존 게시글 공개 조건(예: `deleted_at is null`, 게시 상태)을 함께 적용한다.

### 8.1 Supabase RLS

북마크는 기본적으로 비공개 데이터이며, 클라이언트 요청은 사용자의 세션을 전달하는 Supabase 클라이언트를 사용한다. 서비스 역할 키를 브라우저에 노출하지 않는다.

```sql
alter table public.bookmarks enable row level security;

create policy "users can read own bookmarks"
on public.bookmarks for select
to authenticated
using ((select auth.uid()) = user_id);

create policy "users can create own bookmarks"
on public.bookmarks for insert
to authenticated
with check (
  (select auth.uid()) = user_id
  and exists (
    select 1
    from public.posts
    where posts.id = bookmarks.post_id
  )
);

create policy "users can delete own bookmarks"
on public.bookmarks for delete
to authenticated
using ((select auth.uid()) = user_id);
```

- `UPDATE` 정책은 만들지 않는다. 북마크는 추가 또는 삭제만 가능하다.
- 추가 정책의 `posts` 조회에도 기존 `posts` RLS 정책이 적용되므로, 사용자가 조회할 수 있는 게시글만 북마크할 수 있어야 한다. 실제 게시글 공개 조건이 RLS 밖에 구현되어 있다면 같은 조건을 정책 또는 서버 검증에 추가한다.
- API에서 받은 `user_id`를 신뢰하지 않고 인증 세션의 `auth.uid()`만 사용한다.

## 9. API 계약

Next.js App Router의 Route Handler를 서버 경계로 사용한다. 기존 프로젝트가 인증된 Supabase 직접 호출 패턴을 표준으로 사용한다면 동일한 응답·권한·멱등성 규칙을 유지한 채 대체할 수 있다.

### 9.1 북마크 상태 조회

`GET /api/posts/{postId}/bookmark`

```json
{ "isBookmarked": true }
```

- 인증 사용자: `200 OK`
- 비로그인 사용자: `200 OK`, `{ "isBookmarked": false }`를 반환할 수 있으나 버튼 클릭 시 로그인을 요구한다.
- 존재하지 않거나 조회할 수 없는 게시글: `404 Not Found`
- 기존 게시글 상세 응답에 사용자별 `isBookmarked`를 안전하게 포함할 수 있다면 별도 요청을 생략한다.

### 9.2 북마크 추가

`PUT /api/posts/{postId}/bookmark`

```json
{
  "isBookmarked": true,
  "bookmarkedAt": "2026-08-25T00:00:00.000Z"
}
```

- 새로 생성: `201 Created`
- 이미 존재: 기존 행을 반환하며 `200 OK`
- 비로그인: `401 Unauthorized`
- 존재하지 않거나 조회할 수 없는 게시글: `404 Not Found`

### 9.3 북마크 해제

`DELETE /api/posts/{postId}/bookmark`

- 삭제 여부와 관계없이 최종 상태가 동일하도록 `204 No Content`
- 비로그인: `401 Unauthorized`

### 9.4 내 북마크 목록

`GET /api/me/bookmarks?cursor={opaqueCursor}&limit=20`

```json
{
  "items": [
    {
      "post": {
        "id": "post-uuid",
        "title": "게시글 제목"
      },
      "bookmarkedAt": "2026-08-25T00:00:00.000Z"
    }
  ],
  "nextCursor": null
}
```

- 커서는 `created_at`과 `post_id`를 서버에서 불투명 문자열로 인코딩해 동일 시각 데이터에서도 누락·중복을 방지한다.
- 응답의 게시글 필드는 기존 게시글 카드 DTO를 따른다.
- 비로그인: `401 Unauthorized`
- 오류 응답은 공통 형식 `{ "error": { "code": "...", "message": "..." } }`을 따른다.

## 10. 프런트엔드 및 캐시 정책

### 10.1 컴포넌트 책임

- 게시글 상세 페이지(Server Component): 게시글과 인증 상태를 조회하고 가능한 경우 북마크 초기값을 함께 전달한다.
- `BookmarkButton`(Client Component): 상태 표시, 추가·해제 mutation, 낙관적 업데이트와 오류 복구를 담당한다.
- 북마크 목록 페이지: 서버에서 첫 페이지를 prefetch하고 `HydrationBoundary`로 전달할 수 있다.
- 목록 컴포넌트(Client Component): `useInfiniteQuery`로 다음 커서를 조회한다.

### 10.2 React Query

- 상태 키: `['bookmark-status', userId ?? 'anonymous', postId]`
- 목록 키: `['my-bookmarks', userId]`
- 추가·해제 전 관련 쿼리를 취소하고 이전 값을 저장한 뒤 낙관적으로 상태를 바꾼다.
- 실패 시 저장한 값으로 롤백하고 사용자에게 오류를 알린다.
- 완료 시 상태 쿼리와 목록 쿼리를 무효화해 서버 상태와 재동기화한다.
- 목록에서 해제할 때도 해당 항목을 낙관적으로 제거하고 실패하면 복원한다.
- 사용자별 데이터에는 공유 가능한 Next.js 정적 캐시를 사용하지 않는다. 서버 조회는 요청의 인증 쿠키를 사용하고 필요 시 `no-store` 또는 동등한 비공개 캐시 정책을 적용한다.
- 로그아웃 및 계정 전환 시 QueryClient의 사용자 전용 데이터를 제거해 이전 계정의 목록이 순간적으로 노출되지 않게 한다.

## 11. 비기능 요구사항

### 11.1 보안 및 개인정보

- RLS 검증 없이 클라이언트 입력만으로 소유권을 판단하지 않는다.
- 인증되지 않은 추가·삭제 요청은 거부한다.
- 다른 사용자의 북마크 조회·추가·삭제 시도가 DB 정책과 API 양쪽에서 실패해야 한다.
- 서버 로그와 분석 이벤트에 게시글 본문이나 사용자 토큰을 기록하지 않는다.

### 11.2 성능 및 안정성

- 정상 부하에서 북마크 상태/변경 API의 서버 응답 p95 목표는 500ms 이하, 목록 첫 페이지는 800ms 이하로 한다(클라이언트 네트워크 시간 제외).
- 목록 조회는 페이지 크기를 제한하고 인덱스를 사용하는 커서 기반 페이지네이션으로 처리한다.
- 상세 목록 화면에서 게시글마다 개별 상태 요청을 발생시키는 N+1 패턴을 만들지 않는다.
- 중복 클릭, 재시도 및 동시에 열린 여러 탭에서도 유일성 제약으로 중복 행이 생성되지 않아야 한다.

### 11.3 반응형 및 호환성

- 서비스가 지원하는 모바일·데스크톱 화면에서 버튼과 목록을 사용할 수 있어야 한다.
- 기존 프로젝트의 브라우저 지원 범위와 디자인 시스템을 따른다.

## 12. 분석 이벤트 및 운영 지표

| 이벤트 | 발생 시점 | 주요 속성 |
| --- | --- | --- |
| `bookmark_added` | 서버에서 추가 성공 | `post_id`, `source` (`post_detail`) |
| `bookmark_removed` | 서버에서 해제 성공 | `post_id`, `source` (`post_detail`, `mypage`) |
| `bookmark_list_viewed` | 마이페이지 북마크 목록 진입 | 첫 페이지 항목 수 |
| `bookmark_action_failed` | 추가·해제 실패 | 동작, 오류 코드, source |

개인 식별 정보와 게시글 본문은 이벤트 속성에서 제외한다.

출시 후 다음을 관찰한다.

- 주간 활성 로그인 사용자 중 북마크 기능 사용 비율
- 북마크 추가 후 7일 이내 해당 게시글 재방문 비율
- 추가·해제 API 성공률(목표 99.9% 이상)
- API p95 응답 시간과 클라이언트 롤백 발생률

## 13. 예외 및 오류 처리

| 상황 | 기대 동작 |
| --- | --- |
| 추가 직전에 게시글이 삭제됨 | UI를 롤백하고 `게시글을 찾을 수 없습니다.` 안내 |
| 네트워크 또는 서버 오류 | UI를 이전 상태로 복구하고 재시도 가능한 메시지 표시 |
| 인증 세션 만료 | 캐시를 정리하고 재로그인 안내 후 현재 URL을 복귀 경로로 보존 |
| 중복 추가 요청 | 유일성 오류를 사용자 오류로 노출하지 않고 활성 상태 반환 |
| 이미 삭제된 북마크 해제 | 성공으로 처리하고 비활성 상태 유지 |
| 북마크 후 게시글 비공개 전환 | 목록에서 제외하고 직접 접근 시 기존 게시글 권한 정책 적용 |
| 여러 탭에서 상태 변경 | 다음 포커스, 재조회 또는 mutation 완료 시 서버 상태로 수렴 |

## 14. 수용 기준

1. **추가 및 유지**  
   로그인 사용자가 북마크하지 않은 게시글에서 버튼을 누르면 즉시 활성화되고, 새로고침 후에도 활성 상태가 유지된다.

2. **해제**  
   활성화된 버튼을 누르면 북마크가 해제되며, 새로고침 후에도 비활성 상태다.

3. **내 목록**  
   마이페이지에는 해당 사용자가 북마크한 조회 가능한 게시글만 최신 북마크순으로 표시되고, 항목을 누르면 상세로 이동한다.

4. **빈 상태와 페이지네이션**  
   북마크가 없으면 지정된 빈 상태가 보이며, 20개를 초과하면 다음 페이지를 중복이나 누락 없이 조회할 수 있다.

5. **로그인 요구**  
   비로그인 사용자가 버튼을 누르면 로그인으로 안내되고, 인증되지 않은 API 변경 요청은 `401`을 반환한다.

6. **사용자 격리**  
   사용자 A는 UI, API 또는 Supabase 클라이언트를 통해 사용자 B의 북마크를 조회·변경할 수 없다.

7. **중복 방지와 멱등성**  
   동일 게시글에 추가 요청을 반복하거나 빠르게 클릭해도 북마크 행은 최대 하나이며 최종 UI와 DB 상태가 일치한다.

8. **실패 복구**  
   추가·해제 요청이 실패하면 낙관적으로 변경된 UI가 이전 상태로 복구되고 오류 안내가 표시된다.

9. **게시글 상태 반영**  
   삭제되었거나 조회 권한이 사라진 게시글은 북마크 목록과 상세 응답에 노출되지 않는다.

10. **접근성**  
    키보드만으로 버튼을 조작할 수 있고, 스크린 리더가 현재 상태와 가능한 동작을 식별할 수 있다.

## 15. 테스트 계획

- 단위 테스트: 버튼 상태, 낙관적 업데이트, 실패 롤백, 쿼리 키 및 커서 처리.
- API 통합 테스트: 인증 여부, 추가/중복 추가/해제, 없는 게시글, 세션 만료, 페이지네이션.
- DB/RLS 테스트: 자기 데이터 허용, 타 사용자 데이터 거부, 외래 키 삭제 전파, 유일성 보장.
- E2E 테스트: 상세에서 추가 → 마이페이지 확인 → 목록에서 해제, 새로고침 유지, 비로그인 로그인 유도.
- 접근성 테스트: 키보드 탐색, `aria-pressed`, 접근 가능한 이름, 포커스 표시.
- 반응형 테스트: 지원하는 모바일 및 데스크톱 주요 뷰포트.
