# 개발 프로세스와 검증 체계

## 1. 목표

이 프로젝트의 품질은 단순히 프로그램이 실행되는지가 아니라, **같은 입력과 환경에서 같은 평가 결과를 내고 그 결과를 설명할 수 있는지**로 판단한다.

우선순위는 다음과 같다.

1. 평가 정확성: 성공·실패와 점수를 명세대로 판정한다.
2. 재현성: 입력, 코드, 의존성, 실행 환경이 같으면 결과도 같다.
3. 격리와 안전: 평가 대상 에이전트가 호스트, 비밀 정보, 정답 데이터에 접근하지 못한다.
4. 추적 가능성: 모든 결과에서 사용한 버전, 설정, 태스크, 로그를 확인할 수 있다.
5. 유지 가능성: 한 명의 메인테이너가 반복해서 수행할 수 있을 만큼 단순하고 자동화되어 있다.

성능 최적화와 기능 확장은 위 항목을 만족한 뒤에 진행한다.

## 2. 작업 단위

모든 변경은 하나의 이슈로 시작한다. 이슈에는 다음만 기록한다.

- 해결할 문제와 범위
- 사용자 관점의 완료 조건
- 검증 방법
- 재현성, 점수 산정, 격리, 호환성에 미치는 영향

한 변경은 한 목적만 가진다. 기능 변경과 무관한 리팩터링은 분리한다. 큰 기능은 독립적으로 검증 가능한 가장 작은 단위로 나눈다.

다음 조건을 만족해야 구현을 시작한다.

- 입력, 출력, 오류 동작이 설명되어 있다.
- 점수나 합격 판정이 바뀐다면 예시와 기대 결과가 있다.
- 외부 API, 모델, 시간, 네트워크처럼 비결정적인 요소가 식별되어 있다.

## 3. 개발 흐름

1. 기본 브랜치에서 짧은 작업 브랜치를 만든다.
2. 실패하는 테스트 또는 재현 사례로 기대 동작을 먼저 고정한다.
3. 완료 조건을 만족하는 최소 구현을 작성한다.
4. 로컬에서 전체 검증 명령을 실행한다.
5. 변경 내용을 스스로 리뷰한 뒤 PR을 연다. 혼자 작업하더라도 PR을 변경 기록과 자동 검증의 단위로 사용한다.
6. 필수 CI가 모두 통과한 경우에만 squash merge한다. 기본 브랜치 직접 푸시는 금지한다.

PR 설명에는 다음을 포함한다.

- 무엇을 왜 바꿨는가
- 어떻게 검증했는가
- 평가 결과나 공개 인터페이스의 변화가 있는가
- 남은 위험이나 의도적으로 제외한 범위가 있는가

자체 리뷰에서는 diff만 다시 읽고 다음을 확인한다.

- 완료 조건 밖의 변경이 섞이지 않았는가
- 실패 경로와 경계값을 테스트했는가
- 로그나 산출물에 토큰, 자격 증명, 사용자 코드가 불필요하게 노출되지 않는가
- 평가 대상이 정답, 숨겨진 테스트, 호스트 파일에 접근할 수 없는가
- 결과를 재현하는 데 필요한 메타데이터가 남는가

## 4. 하나의 검증 진입점

기술 스택을 정할 때 `verify`라는 단일 로컬 명령을 제공한다. 이 명령은 CI와 같은 순서로 아래 검사를 실행하며, 하나라도 실패하면 0이 아닌 종료 코드를 반환해야 한다.

1. 포맷 검사
2. 린트와 정적 타입 검사(해당하는 경우)
3. 단위 테스트
4. 통합 테스트
5. 작은 고정 평가 세트를 이용한 종단 테스트

CI 전용으로만 존재하는 검증은 두지 않는다. 개발자는 커밋 전에 같은 검증을 로컬에서 실행할 수 있어야 한다.

## 5. 테스트 체계

### 단위 테스트

파서, 설정 병합, 점수 계산, 제한 시간과 종료 상태 판정처럼 순수하고 중요한 로직을 빠르게 검사한다. 다음 경우를 반드시 포함한다.

- 정상 입력
- 빈 입력과 경계값
- 잘못된 형식
- 부분 성공, 시간 초과, 비정상 종료
- 여러 하위 점수의 반올림과 집계

### 통합 테스트

프로세스 실행, 작업 공간 준비, 패치 수집, 테스트 러너, 결과 저장처럼 구성 요소 사이의 계약을 검사한다. 외부 모델 API는 기본 CI에서 호출하지 않고 기록된 응답이나 제어 가능한 가짜 구현을 사용한다. 실제 API 검사는 비용과 변동성을 고려해 수동 또는 정기 검사로 분리한다.

### 종단 테스트

몇 초 안에 끝나는 소형 저장소와 결정적인 가짜 에이전트를 fixture로 둔다. 최소한 다음 시나리오를 검증한다.

- 올바른 수정은 합격한다.
- 틀린 수정은 불합격한다.
- 아무 변경도 하지 않으면 불합격한다.
- 에이전트 오류와 시간 초과가 올바르게 기록된다.
- 허용되지 않은 파일 접근이나 네트워크 사용이 차단된다.

### 회귀 테스트

버그 수정에는 그 버그를 재현하는 테스트를 반드시 추가한다. 점수 판정 버그라면 기존 결과와 수정된 기대 결과를 함께 남겨 변경 이유를 알 수 있게 한다.

테스트는 서로 실행 순서나 이전 실행의 파일에 의존하지 않아야 한다. 시간, 난수, 경로가 결과에 영향을 주면 테스트에서 고정하거나 명시적으로 주입한다.

## 6. 평가 결과 검증

평가 태스크는 코드와 함께 버전 관리하며 각 태스크에 다음 정보를 둔다.

- 고유 ID와 버전
- 목적과 난이도
- 시작 저장소의 정확한 리비전
- 실행 환경과 의존성 버전
- 시간·CPU·메모리·네트워크 제한
- 채점 명령, 합격 조건, 점수 가중치

채점기는 에이전트의 설명이 아니라 생성된 작업 결과와 독립된 테스트 결과만 사용한다. 테스트와 정답 패치는 에이전트 실행 환경에 노출하지 않는다.

새 태스크나 채점 변경은 다음 절차로 검증한다.

1. 변경하지 않은 기준 상태가 예상대로 실패하는지 확인한다.
2. 알려진 정답 수정이 예상대로 합격하는지 확인한다.
3. 대표적인 잘못된 수정이 합격하지 않는지 확인한다.
4. 깨끗한 환경에서 동일 실행을 최소 3회 반복해 판정과 점수가 같은지 확인한다.
5. 태스크 자체 테스트가 원래 프로젝트의 관련 테스트도 훼손하지 않는지 확인한다.

세 번의 결과가 다르면 태스크나 러너를 flaky로 간주한다. 원인을 고치기 전에는 점수 집계와 릴리스 기준 세트에서 제외하며, 단순 재시도로 성공을 만들지 않는다.

모든 평가 결과에는 최소한 다음을 저장한다.

- 도구 버전과 커밋 SHA
- 태스크 ID와 버전
- 설정과 난수 시드
- 실행 환경 이미지 또는 의존성 잠금 파일의 식별자
- 시작·종료 시각, 종료 상태, 사용 자원
- 에이전트 출력, 적용된 diff, 채점 로그

비밀 정보는 저장 전에 제거한다. 결과 산출물만으로 동일 실행 명령을 구성할 수 있어야 한다.

## 7. CI 품질 게이트

모든 PR에서 다음을 필수 검사로 설정한다.

| 검사 | 실패 조건 |
| --- | --- |
| 소스 검증 | 포맷, 린트 또는 타입 검사 실패 |
| 테스트 | 단위·통합·소형 종단 테스트 실패 |
| 재현성 | 고정 fixture의 판정 또는 점수가 반복 실행에서 달라짐 |
| 보안 | 의존성 취약점 또는 비밀 정보 검사에서 허용되지 않은 항목 발견 |
| 호환성 | 지원한다고 명시한 실행 환경 중 하나라도 실패 |

CI는 잠금 파일을 사용해 깨끗한 환경에서 실행한다. 테스트를 건너뛰거나 필수 검사를 관리자 권한으로 우회해 병합하지 않는다. 불가피한 예외는 이유와 만료 조건을 이슈에 기록한다.

기본 브랜치에서는 전체 검증과 더 큰 고정 평가 세트를 실행한다. 정기 CI에서는 실제 지원 환경, 장시간 평가, 최신 의존성 호환성을 확인하되, 그 변동성 때문에 PR의 결정적 검증을 대체하지는 않는다.

## 8. 릴리스

초기 개발 단계에서는 시맨틱 버저닝을 사용하고, 공개 CLI·설정 형식·결과 스키마·점수 의미의 변경을 사용자 인터페이스 변경으로 취급한다.

릴리스 전에는 다음을 확인한다.

- 기본 브랜치의 모든 필수 검사가 통과했다.
- 깨끗한 환경에서 패키지 설치와 대표 실행을 확인했다.
- 고정 평가 세트의 결과를 이전 릴리스와 비교했고, 차이를 설명할 수 있다.
- 사용자에게 영향을 주는 변경과 마이그레이션 방법을 변경 기록에 적었다.
- 태그, 패키지, 결과 스키마의 버전이 일치한다.

릴리스는 태그로 자동 생성하고, 동일 커밋에서 빌드한 산출물만 배포한다. 릴리스 후 대표 설치와 실행을 한 번 확인한다. 문제가 있으면 이미 배포한 버전을 덮어쓰지 않고 수정 버전을 낸다.

## 9. 결함 처리

결함은 다음 우선순위로 처리한다.

1. 호스트 탈출, 비밀 노출, 임의 코드 실행 범위 확대
2. 잘못된 합격·불합격 또는 점수 계산
3. 동일 조건에서 결과가 달라지는 문제
4. 데이터 손실과 공개 인터페이스 회귀
5. 그 밖의 기능·성능 문제

1~3번 결함은 영향을 받는 릴리스와 평가 결과를 표시하고, 필요하면 해당 결과를 무효화한다. 수정 후에는 재현 테스트를 추가하고 같은 태스크 세트를 다시 실행한다.

## 10. 완료 기준

변경은 다음 조건을 모두 만족할 때 완료된다.

- 이슈의 완료 조건을 충족한다.
- 새 동작과 실패 경로를 자동 테스트가 검증한다.
- 로컬 `verify`와 필수 CI가 통과한다.
- 재현성·격리·점수에 미치는 영향을 확인했다.
- 사용자에게 보이는 변경은 문서와 변경 기록에 반영했다.
- 디버그 코드, 임시 파일, 비밀 정보가 남아 있지 않다.

## 11. 개발 시작 전 최소 설정

첫 기능을 구현하기 전에 다음만 준비한다.

- 기본 브랜치 보호와 PR 필수 검사
- 의존성 잠금 파일과 재현 가능한 실행 환경
- 단일 `verify` 명령과 CI 워크플로
- 단위·통합·소형 종단 테스트 디렉터리
- 결정적인 가짜 에이전트와 최소 평가 fixture
- 이슈 및 PR 템플릿
- 라이선스, 기여 가이드, 보안 취약점 비공개 신고 방법

이후 절차나 검사는 실제로 반복되는 결함이 있거나 위험을 줄인다는 근거가 있을 때만 추가한다.
