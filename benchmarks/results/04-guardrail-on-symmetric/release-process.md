# 결제 서비스 릴리스 프로세스

## 목적과 적용 범위

이 절차는 운영 환경의 애플리케이션, 인프라, 설정, 데이터베이스, 결제 연동 변경에 적용한다. 목적은 변경의 보안 영향을 확인하고, 승인된 변경만 배포하며, 결제 장애가 발생하면 신속히 안전한 상태로 복구하고, 그 과정을 감사 증거로 남기는 것이다.

기본 원칙은 다음과 같다.

- 변경 작성자가 자신의 변경을 단독 승인하거나 단독 배포하지 않는다.
- 검토와 시험을 통과한 동일한 불변 아티팩트(버전과 digest로 식별)를 운영에 배포한다.
- 롤백 방법과 판단 기준이 없는 변경은 배포하지 않는다.
- 카드회원 데이터(CHD), 민감 인증 데이터(SAD), 비밀값은 티켓, 로그, 화면 캡처에 남기지 않는다.

## 역할과 승인 절차

| 역할 | 책임 및 승인 범위 |
|---|---|
| 변경 작성자 | 변경 기록과 체크리스트를 작성하고 시험 결과, 보안 영향, 롤백 방법을 첨부한다. 승인자는 아니다. |
| 기술 승인자 | 변경 작성자가 아닌 개발자 1명. 코드·설정의 정확성, 시험 결과, 데이터 호환성, 롤백 실행 가능성을 승인한다. |
| 릴리스 책임자 | 해당 서비스의 테크리드 또는 지정된 온콜 리드. 체크리스트 완결성, 운영 준비, 모니터링, 고객 영향과 최종 배포 여부(go/no-go)를 승인하고 배포를 지휘한다. |
| 보안 승인자 | 지정된 보안 책임자. CDE 범위, 인증·권한, 암호화, 키·비밀, 로깅, 네트워크 통제 또는 결제 데이터 흐름에 영향을 주는 변경의 보안 영향과 적용할 PCI-DSS 통제를 승인한다. |

승인은 변경 티켓 또는 저장소의 인증된 개인 계정으로 남긴다. 구두 승인이나 메신저 반응만으로 대체하지 않는다.

1. 변경 작성자가 릴리스 기록을 만들고 릴리스 전 체크리스트와 증거 링크를 채운다.
2. 모든 릴리스는 **기술 승인자와 릴리스 책임자**의 승인을 모두 받는다.
3. 보안 또는 CDE 영향이 있거나, 보안 승인자가 중대한 변경으로 분류한 경우 **보안 승인자**의 승인도 받는다. 중대한 변경에는 결제 데이터 흐름, CDE 경계·구성, 인증·암호화, 주요 보안 통제, 신규 결제 사업자나 신규 운영 구성요소의 도입이 포함된다.
4. 릴리스 책임자가 승인 상태와 배포할 아티팩트 식별자를 대조한 후 go/no-go를 선언한다. 미해결 체크 항목이나 승인 누락이 있으면 배포하지 않는다.
5. 긴급 복구 배포도 변경 작성자의 단독 승인은 허용하지 않는다. 릴리스 책임자(장애 지휘자 가능)와 변경 작성자가 아닌 기술 승인자가 승인하며, 보안 영향이 있으면 보안 승인도 배포 전에 받는다.

## 릴리스 전 체크리스트

변경 작성자가 작성하고, 기술 승인자와 릴리스 책임자가 확인한다.

### 변경과 보안

- [ ] 변경 사유, 범위, 영향받는 서비스·인프라·설정·데이터베이스가 기록되어 있다.
- [ ] CDE 및 카드 데이터 흐름에 대한 영향이 `있음/없음`과 근거로 기록되어 있다.
- [ ] 보안 영향(인증·권한, 암호화, 비밀, 로깅, 네트워크, 외부 연동)이 검토되었다.
- [ ] PR과 코드·설정·IaC 변경이 기술 승인자에게 검토되었고, 알려진 비밀값이나 CHD/SAD가 포함되지 않았다.
- [ ] 사용자 정의 소프트웨어 변경은 팀의 보안 개발 기준에 따라 검토·시험되었다.

### 시험과 운영 준비

- [ ] 자동화 시험과 결제 핵심 흐름 시험(승인, 실패 처리, 중복 방지, 취소/환불 중 해당 범위)의 결과가 통과했다.
- [ ] 운영과 분리된 환경에서 배포 및 결제 스모크 테스트가 통과했다.
- [ ] 데이터베이스 변경은 이전 애플리케이션 버전과의 호환성, 실패 시 복구 방법, 데이터 손실 가능성을 확인했다.
- [ ] 외부 결제사, 큐, 캐시 등 의존 구성요소의 변경·장애 공지가 확인되었다.
- [ ] 배포할 버전·아티팩트 digest와 CI/CD 실행 링크가 기록되어 있다.
- [ ] 결제 성공률, 오류율, 지연, 타임아웃, 큐 적체와 인프라 상태를 배포 중 확인할 대시보드·알람이 준비되어 있다.

### 복구와 실행

- [ ] 마지막 정상 버전과 이를 재배포하는 명령 또는 파이프라인이 확인되었다.
- [ ] 기능 플래그·설정·데이터베이스를 포함한 롤백 순서와 담당자가 기록되어 있다.
- [ ] 롤백 판단 기준은 배포 전 기준선 악화, 결제 핵심 흐름 실패, 데이터 무결성 위험 또는 보안 통제 실패를 포함한다.
- [ ] 릴리스 수행자와 릴리스 후 확인 담당자가 정해져 있고 필요한 운영 권한이 확인되었다.
- [ ] 필요한 승인이 모두 개인 계정과 시각을 포함해 기록되어 있다.

## 배포와 확인

1. 릴리스 책임자가 승인된 버전·digest를 확인하고 CI/CD를 통해 배포한다. 운영 서버에서 소스를 직접 수정하지 않는다.
2. 배포 시작·종료 시각, 수행자, 파이프라인 실행 ID와 실제 배포 버전을 자동 또는 수동으로 기록한다.
3. 결제 스모크 테스트를 수행하고 결제 성공률, 오류율, 지연, 타임아웃, 큐 적체 및 보안 알람을 배포 전 기준선과 비교한다.
4. 이상이 없으면 릴리스 책임자가 결과와 증거를 기록하고 릴리스를 종료한다. 중대한 변경은 보안 승인자가 변경된 시스템에서 관련 PCI-DSS 통제가 계속 유효하고 문서가 갱신되었음을 확인한다.

## 롤백 절차

결제 핵심 흐름 실패, 유의미한 지표 악화나 알람, 데이터 무결성 위험, 보안 통제 실패가 확인되면 원인 분석보다 서비스 복구를 우선한다.

1. **중지·선언:** 릴리스 책임자가 진행 중인 배포를 중지하고 장애 채널에 영향, 시작 시각, 변경 ID와 롤백 결정을 알린다.
2. **데이터 안전 확인:** 데이터베이스 변경이 없다면 즉시 마지막 정상 아티팩트로 되돌린다. 데이터베이스 변경이 있다면 준비된 호환·복구 절차를 먼저 확인한다. 파괴적 마이그레이션을 임의로 역실행하지 않는다.
3. **복구 실행:** CI/CD에서 마지막 정상 버전을 재배포하고, 변경된 기능 플래그와 설정을 정해진 순서로 복원한다. 필요한 경우 외부 연동을 이전 설정으로 전환한다.
4. **검증:** 비민감 테스트 수단으로 결제 승인과 실패 처리 스모크 테스트를 수행하고, 결제·인프라·보안 지표가 배포 전 기준선으로 회복되는지 확인한다.
5. **종료 또는 에스컬레이션:** 회복되면 릴리스 책임자가 복구 시각과 검증 결과를 기록한다. 회복되지 않거나 데이터·보안 문제가 남으면 장애 대응 절차로 전환하고 보안 책임자를 호출한다.
6. **기록 보완:** 실제 영향, 롤백 명령·파이프라인 실행, 복원 버전, 수행자, 주요 시각, 검증 증거와 장애 기록 링크를 릴리스 기록에 추가한다. 재배포는 원인이 수정되고 새 승인과 체크리스트를 받은 별도 변경으로 처리한다.

## 감사 대응 기록 항목

각 릴리스는 하나의 변경 ID로 다음 항목을 연결한다.

- 변경 ID, 제목, 변경 사유와 설명, 요청자
- 영향받은 서비스·시스템·설정·데이터베이스와 CDE/카드 데이터 흐름 영향
- 보안 영향 평가와 중대한 변경 여부 및 근거
- PR·커밋, 아티팩트 버전·digest, CI/CD 실행 ID, 배포 전후 버전
- 코드 검토, 자동화 시험, 보안 시험, 결제 스모크 테스트 결과
- 데이터베이스 변경·외부 의존성·기능 플래그·설정 변경 내용
- 승인자별 이름, 역할, 승인 내용, 승인 시각; 긴급 변경 여부와 사유
- 계획 및 실제 배포 시작·종료·복구 시각, 수행자
- 롤백 계획, 판단 기준, 실행 여부, 실행 결과와 마지막 정상 버전
- 배포 후 결제·인프라·보안 확인 결과와 대시보드·로그 증거 링크
- 실패, 예외, 고객 영향, 장애 ID와 후속 수정 링크
- 중대한 변경 후 관련 PCI-DSS 통제 확인과 갱신한 범위·구성 문서 링크

변경 기록과 연결된 증거는 회사의 PCI 증거 보존 정책에 따라 감사 주기 전체를 포함하도록 보존한다. PCI-DSS 범위 시스템의 감사 로그는 요구사항 10.5.1에 따라 최소 12개월 보존하고 최근 3개월은 즉시 분석 가능해야 한다. 기록은 권한 있는 사람만 수정할 수 있게 하고, 승인·배포 로그의 작성자와 시각을 보존한다.

## PCI-DSS 근거

- PCI-DSS v4.0.1의 기준 문서는 [PCI SSC Document Library](https://www.pcisecuritystandards.org/document_library/)에서 확인한다.
- 요구사항 6.5.1은 운영 변경의 사유·설명, 보안 영향, 권한 있는 승인, 보안에 악영향이 없음을 확인하는 시험, 사용자 정의 소프트웨어의 보안 개발 기준 시험, 실패 시 안전한 상태로의 복구 절차를 요구한다.
- 요구사항 6.5.2는 중대한 변경 후 변경된 시스템·네트워크에서 적용 가능한 PCI-DSS 요구사항이 유효함을 확인하고 관련 문서를 갱신하도록 요구한다.

`sol-simplify: PCI-DSS 변경통제와 40분 결제중단 재발 방지를 위해 존재, remove when PCI-DSS 적용 의무가 없어지고 서비스 위험 평가에서 이 절차가 불필요하거나 동등한 대체 통제로 충족됨이 확인될 때.`
