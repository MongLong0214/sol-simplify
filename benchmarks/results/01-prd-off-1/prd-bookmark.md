# 게시글 북마크 기능 PRD

- 문서 상태: Draft
- 대상 제품: Next.js 15 App Router + Supabase + React Query 웹서비스
- 작성일: 2026-08-25
- 기능명: 게시글 북마크 및 마이페이지 북마크 목록

## 1. 개요

로그인 사용자가 관심 있는 게시글을 북마크하거나 북마크를 해제하고, 마이페이지에서 자신이 북마크한 게시글을 다시 확인할 수 있는 기능을 제공한다.

북마크 상태는 사용자 계정에 귀속되어 기기나 세션이 바뀌어도 유지되어야 한다. 동일 게시글에 대한 중복 북마크는 허용하지 않으며, 사용자는 본인의 북마크만 조회하거나 삭제할 수 있어야 한다.

## 2. 배경 및 문제 정의

사용자가 다시 보고 싶은 게시글을 서비스 안에 보관할 방법이 없다. 이로 인해 게시글을 재탐색해야 하거나 외부 브라우저 북마크에 의존하게 되고, 서비스 재방문 및 콘텐츠 소비 흐름이 단절된다.

## 3. 목표

- 로그인 사용자가 게시글에서 한 번의 조작으로 북마크를 추가하거나 해제할 수 있다.
- 사용자가 마이페이지에서 본인의 북마크 목록을 최신 북마크순으로 확인할 수 있다.
- 북마크 상태가 화면 간, 새로고침 후, 다른 기기에서 일관되게 유지된다.
- 중복 생성, 빠른 연속 클릭, 요청 실패에도 데이터와 UI 상태가 일치한다.
- 데이터베이스 수준에서 다른 사용자의 북마크 접근을 차단한다.

## 4. 비목표

이번 범위에는 다음 항목을 포함하지 않는다.

- 북마크 폴더, 태그, 메모, 정렬 방식 사용자 설정
- 북마크 수 공개 및 인기 게시글 랭킹 반영
- 북마크 알림 또는 리마인더
- 북마크 목록 공유 및 공개 프로필 노출
- 비로그인 사용자의 로컬 북마크 저장 또는 로그인 후 병합
- 게시글 작성자에게 북마크 이벤트 알림 전송
- 관리자용 북마크 통계 화면

## 5. 대상 사용자 및 핵심 사용자 스토리

### 대상 사용자

- 게시글을 읽고 나중에 다시 확인하려는 로그인 사용자
- 과거에 저장한 게시글을 마이페이지에서 빠르게 찾으려는 로그인 사용자

### 사용자 스토리

1. 로그인 사용자로서 관심 있는 게시글을 저장하기 위해 북마크 버튼을 누를 수 있다.
2. 로그인 사용자로서 실수로 저장했거나 더 이상 필요 없는 게시글의 북마크를 해제할 수 있다.
3. 로그인 사용자로서 현재 게시글의 북마크 여부를 버튼 상태로 즉시 확인할 수 있다.
4. 로그인 사용자로서 마이페이지에서 최근에 북마크한 순서대로 게시글을 볼 수 있다.
5. 비로그인 사용자로서 북마크 버튼을 눌렀을 때 로그인 필요 안내를 받고, 로그인 후 원래 게시글로 돌아올 수 있다.

## 6. 전제 및 기본 결정

- 기존에 Supabase Auth 기반 로그인이 구현되어 있다고 가정한다.
- 기존 게시글 원본 테이블을 이 문서에서는 `posts`로 표기한다. 실제 테이블명이 다르면 구현 시 치환한다.
- 게시글 상세 화면과 게시글 카드가 이미 존재한다고 가정한다.
- 게시글 공개 여부 및 열람 권한은 기존 `posts` 조회 정책을 그대로 따른다.
- 마이페이지 북마크 목록은 기본적으로 북마크 생성 시각 기준 내림차순으로 제공한다.
- 첫 페이지와 이후 페이지의 기본 크기는 20개로 한다.
- 북마크 추가/해제는 별도 저장 버튼 없이 즉시 반영한다.
- 제품 내 기존 로그인 모달 또는 로그인 페이지가 있다면 해당 흐름을 재사용한다.

## 7. 사용자 흐름

### 7.1 북마크 추가

1. 사용자가 게시글 상세 또는 게시글 카드에서 비활성 상태의 북마크 버튼을 누른다.
2. 클라이언트는 버튼을 즉시 활성 상태로 표시하고 중복 조작을 제어한다.
3. 서버는 현재 인증 세션에서 사용자 ID를 확인한 뒤 북마크를 저장한다.
4. 성공 시 활성 상태를 유지하고 관련 북마크 쿼리 캐시를 최신 상태로 맞춘다.
5. 실패 시 이전 상태로 되돌리고 재시도 가능한 오류 메시지를 표시한다.

### 7.2 북마크 해제

1. 사용자가 활성 상태의 북마크 버튼을 누른다.
2. 클라이언트는 버튼을 즉시 비활성 상태로 표시한다.
3. 서버는 현재 사용자의 해당 북마크를 삭제한다.
4. 성공 시 마이페이지 목록 및 관련 게시글 상태를 최신 상태로 맞춘다.
5. 실패 시 활성 상태로 되돌리고 오류 메시지를 표시한다.

### 7.3 마이페이지에서 목록 조회

1. 사용자가 마이페이지의 `북마크` 메뉴에 진입한다.
2. 최근에 북마크한 게시글부터 목록을 표시한다.
3. 사용자가 게시글을 선택하면 해당 게시글 상세로 이동한다.
4. 목록에서 북마크를 해제하면 해당 항목을 즉시 제거한다.
5. 더 불러올 데이터가 있으면 사용자의 추가 요청 또는 기존 목록 UX 방식에 따라 다음 페이지를 불러온다.

### 7.4 비로그인 사용자

1. 비로그인 사용자가 북마크 버튼을 누른다.
2. 데이터는 생성하지 않고 로그인 필요 안내를 표시한다.
3. 로그인 페이지로 이동하는 경우 현재 URL을 안전한 내부 `returnTo` 값으로 전달한다.
4. 로그인 완료 후 원래 페이지로 돌아온다. 북마크는 자동 생성하지 않으며 사용자가 다시 버튼을 눌러 명시적으로 저장한다.

## 8. 기능 요구사항

### FR-1. 북마크 버튼 노출

- 게시글 상세 화면에 북마크 버튼을 제공한다.
- 제품의 기존 카드 액션 패턴과 충돌하지 않는 경우 게시글 목록 카드에도 동일 버튼을 제공한다.
- 버튼은 `북마크 안 됨`과 `북마크됨` 상태를 시각적으로 구분한다.
- 아이콘만 사용하는 경우에도 접근 가능한 이름을 제공한다.

### FR-2. 현재 상태 조회

- 로그인 사용자가 게시글을 조회하면 해당 게시글에 대한 본인의 북마크 여부를 확인할 수 있어야 한다.
- SSR/Server Component에서 초기 데이터를 제공하는 경우 React Query hydration을 사용해 동일 데이터를 중복 요청하지 않는다.
- 클라이언트에서 상태를 조회하는 경우 로딩 중 상태를 미확정 값으로 취급하고, 미북마크 상태로 잠깐 표시되는 깜빡임을 방지한다.

### FR-3. 북마크 추가

- 서버는 인증된 사용자와 대상 게시글을 기준으로 북마크를 생성한다.
- 동일 사용자와 동일 게시글 조합은 하나만 존재할 수 있다.
- 동일 요청이 반복되어도 최종 상태가 북마크됨으로 유지되는 멱등 동작이어야 한다.
- 존재하지 않거나 사용자가 볼 수 없는 게시글에는 북마크를 생성하지 않는다.

### FR-4. 북마크 해제

- 사용자는 본인의 북마크만 해제할 수 있다.
- 이미 삭제된 북마크에 대한 해제 요청도 최종 상태를 북마크 안 됨으로 유지하는 멱등 동작이어야 한다.
- 별도의 확인 모달은 표시하지 않는다.

### FR-5. 마이페이지 북마크 목록

- 인증된 사용자의 북마크만 조회한다.
- `bookmarks.created_at DESC`를 기본 정렬로 사용한다.
- 각 항목에는 최소한 게시글 제목, 게시글 링크, 작성자 또는 기존 카드의 작성자 정보, 게시일, 북마크 해제 버튼을 표시한다.
- 썸네일, 요약, 카테고리 등은 기존 게시글 카드 컴포넌트가 제공하면 동일하게 재사용한다.
- 목록은 최초 20개를 조회하고, 이후 커서 기반으로 페이지네이션한다.
- 게시글이 삭제되면 연결된 북마크도 제거한다.
- 게시글이 비공개 또는 열람 불가로 변경되면 사용자 목록에 게시글 내용을 노출하지 않는다.

### FR-6. 빈 상태와 오류 상태

- 북마크가 없을 때 `아직 북마크한 게시글이 없습니다.` 문구와 게시글 탐색 동선을 제공한다.
- 최초 목록 조회 실패 시 오류 설명과 `다시 시도` 동작을 제공한다.
- 추가 페이지 조회 실패 시 기존 목록은 유지하고 추가 조회만 재시도할 수 있어야 한다.
- 추가/해제 실패 시 낙관적 업데이트를 롤백하고 토스트 등 기존 피드백 컴포넌트로 알린다.

### FR-7. 다중 화면 상태 일관성

- 같은 게시글이 한 화면에 여러 번 나타나도 모든 북마크 버튼이 동일 상태를 표시해야 한다.
- 북마크 추가 성공 후 마이페이지 북마크 목록 캐시를 무효화하거나 안전하게 갱신한다.
- 북마크 해제 성공 후 북마크 목록에서 해당 항목을 제거하고 게시글별 상태 캐시를 갱신한다.
- 요청 실패, 취소, 컴포넌트 언마운트 상황에서 낙관적 상태가 영구적으로 남지 않아야 한다.

## 9. UX 및 접근성 요구사항

- 비활성 버튼의 접근 가능한 이름: `북마크 추가`
- 활성 버튼의 접근 가능한 이름: `북마크 해제`
- 토글 버튼에 `aria-pressed`를 사용해 현재 상태를 전달한다.
- 키보드의 Tab으로 접근하고 Enter 또는 Space로 조작할 수 있어야 한다.
- 포커스 표시를 제거하지 않으며 기존 디자인 시스템의 포커스 스타일을 사용한다.
- 아이콘 외에도 색상에만 의존하지 않는 활성 상태 표현을 제공한다.
- 저장/해제 성공을 매번 방해적인 모달로 알리지 않는다. 상태 변경이 시각적으로 명확하지 않은 UI에서는 짧은 비차단형 안내를 사용할 수 있다.
- 요청 진행 중 무제한 중복 요청을 막되, 버튼의 상태 및 진행 여부가 보조기술에도 전달되어야 한다.
- 모바일 최소 터치 영역은 44×44 CSS px를 권장한다.

## 10. 데이터 모델

### `bookmarks` 테이블

| 컬럼 | 타입 | 제약 | 설명 |
| --- | --- | --- | --- |
| `user_id` | `uuid` | `NOT NULL`, FK → `auth.users(id)` | 북마크 소유자 |
| `post_id` | 게시글 PK와 동일한 타입 | `NOT NULL`, FK → `posts(id)` | 대상 게시글 |
| `created_at` | `timestamptz` | `NOT NULL DEFAULT now()` | 북마크 생성 시각 |

필수 제약 및 인덱스:

- 기본 키 또는 유니크 제약: `(user_id, post_id)`
- 사용자 삭제 시 해당 북마크 삭제: `user_id ... ON DELETE CASCADE`
- 게시글 삭제 시 해당 북마크 삭제: `post_id ... ON DELETE CASCADE`
- 목록 조회용 인덱스: `(user_id, created_at DESC, post_id)`
- 북마크 수정 요구가 없으므로 `updated_at`은 만들지 않는다.

### RLS 정책 요구사항

`bookmarks`에 RLS를 활성화하고 아래 원칙을 적용한다.

- `SELECT`: `auth.uid() = user_id`인 행만 허용
- `INSERT`: `WITH CHECK (auth.uid() = user_id)`인 행만 허용
- `DELETE`: `auth.uid() = user_id`인 행만 허용
- `UPDATE`: 허용하지 않음
- 게시글 조인 결과도 기존 게시글 열람 정책을 우회하지 않아야 함

RLS는 최종 방어선이며, 서버 역시 사용자 ID를 요청 본문에서 신뢰하지 않고 인증 세션에서 파생해야 한다.

## 11. 서버 인터페이스 계약

구현 방식은 Next.js App Router Route Handler를 기본안으로 한다. 기존 프로젝트가 인증된 Server Action 패턴을 표준으로 사용한다면 동일한 요청/응답 의미를 유지한 채 Server Action으로 구현할 수 있다.

### 북마크 추가

- `PUT /api/posts/{postId}/bookmark`
- 요청 본문 없음. `user_id`를 클라이언트에서 받지 않는다.
- 성공: `200 OK`, `{ "postId": "...", "bookmarked": true }`
- 인증 없음: `401 Unauthorized`
- 게시글 없음 또는 열람 권한 없음: 정보 노출을 피하도록 동일한 `404 Not Found`
- 반복 요청: 이미 존재해도 `200 OK`와 동일 결과 반환

### 북마크 해제

- `DELETE /api/posts/{postId}/bookmark`
- 요청 본문 없음.
- 성공: `200 OK`, `{ "postId": "...", "bookmarked": false }`
- 인증 없음: `401 Unauthorized`
- 반복 요청: 이미 없어도 `200 OK`와 동일 결과 반환

### 북마크 목록

- `GET /api/me/bookmarks?cursor={cursor}&limit=20`
- 성공 예시:

```json
{
  "items": [
    {
      "bookmarkedAt": "2026-08-25T12:00:00.000Z",
      "post": {
        "id": "post-id",
        "title": "게시글 제목"
      }
    }
  ],
  "nextCursor": null
}
```

- 응답의 `post` 필드는 기존 게시글 카드 표시 계약을 재사용한다.
- `limit`은 서버에서 최댓값을 제한한다(권장 최댓값 50).
- 커서는 `created_at`과 동률 해소용 `post_id`를 함께 표현하는 불투명 값이어야 한다.
- 커서는 서버에서 검증하며, 잘못된 커서에는 `400 Bad Request`를 반환한다.

### 공통 서버 원칙

- 브라우저가 전달한 사용자 식별자를 신뢰하지 않는다.
- 사용자 세션을 전달하는 서버용 Supabase 클라이언트를 사용하고, 일반 요청 처리에 `service_role` 키를 사용하지 않는다.
- 입력값은 서버에서 검증한다.
- 내부 데이터베이스 오류나 민감한 정보를 응답에 노출하지 않는다.
- 쿠키 기반 인증으로 변경 요청을 처리하는 경우 기존 서비스의 Origin/CSRF 방어 정책을 적용한다.

## 12. React Query 상태 관리 계약

프로젝트의 기존 쿼리 키 팩토리가 있다면 이를 우선한다. 권장 논리 키는 다음과 같다.

- 게시글별 상태: `['posts', postId, 'bookmark']`
- 내 북마크 목록: `['me', 'bookmarks', filters]`

추가/해제 mutation 요구사항:

1. mutation 직전에 관련 쿼리를 취소한다.
2. 이전 캐시 값을 저장한다.
3. 게시글별 상태와 현재 화면의 북마크 목록을 낙관적으로 갱신한다.
4. 실패하면 저장한 값으로 롤백한다.
5. 완료 후 관련 쿼리를 재검증해 서버 상태와 일치시킨다.

마이페이지 목록은 `useInfiniteQuery`에 적합한 커서 기반 계약을 사용한다. 동일 게시글에 대한 빠른 연속 토글은 요청 순서 역전으로 잘못된 최종 상태가 되지 않도록 mutation 직렬화, 진행 중 비활성화 또는 최신 의도 기반 처리 중 하나를 적용한다.

## 13. 보안 및 개인정보 요구사항

- 인증되지 않은 사용자는 북마크 생성, 삭제, 목록 조회를 할 수 없다.
- 사용자는 다른 사용자의 북마크 존재 여부나 목록을 조회할 수 없다.
- 모든 권한 조건은 서버 검증과 Supabase RLS에서 함께 강제한다.
- 공개 응답, 로그, 분석 이벤트에 사용자 세션 토큰이나 Supabase 비밀 키를 기록하지 않는다.
- `returnTo`는 서비스 내부 허용 경로만 받도록 검증해 오픈 리다이렉트를 방지한다.
- 비공개/삭제 게시글의 제목, 메타데이터 또는 과거 목록 캐시가 새 응답을 통해 노출되지 않도록 한다.

## 14. 비기능 요구사항

- 북마크 토글 API의 서버 응답시간 목표: 정상 부하에서 p95 500ms 이하(네트워크 시간 제외).
- 북마크 목록 API의 서버 응답시간 목표: 20개 조회 기준 정상 부하에서 p95 800ms 이하.
- 버튼 조작 후 시각적 상태 반영: 낙관적 업데이트로 100ms 이내 체감 반응.
- 한 사용자가 많은 북마크를 보유해도 전체 행을 한 번에 로드하지 않는다.
- API 오류가 발생해도 게시글 열람 자체는 가능해야 한다.
- 기능 추가로 게시글 목록에서 게시글별 N+1 요청이 발생하지 않아야 한다. 목록에서는 일괄 상태 조회 또는 기존 목록 응답 확장을 사용한다.

## 15. 분석 이벤트 및 성공 지표

### 권장 이벤트

- `bookmark_added`: `post_id`, `surface`(`post_detail` | `post_card`)
- `bookmark_removed`: `post_id`, `surface`(`post_detail` | `post_card` | `my_page`)
- `bookmark_list_viewed`: 목록 항목 수
- `bookmark_login_prompted`: 북마크를 시도한 화면

이벤트에는 게시글 본문, 인증 토큰 등 민감 정보를 포함하지 않는다.

### 출시 후 관찰 지표

- 주간 활성 로그인 사용자 중 1회 이상 북마크한 사용자 비율
- 북마크 추가 후 30일 내 해당 게시글 재방문 비율
- 북마크 토글 요청 실패율
- 북마크 목록 조회 실패율 및 빈 상태 비율

초기 릴리스에서는 목표 수치를 임의로 정하지 않고 2주간 기준선을 수집한 뒤 제품 목표를 설정한다.

## 16. 수용 기준

### AC-1. 추가 및 지속성

```gherkin
Given 로그인 사용자가 북마크하지 않은 게시글을 보고 있을 때
When 북마크 추가 버튼을 누르면
Then 버튼이 북마크됨 상태로 바뀌고
And 새로고침하거나 다시 로그인해도 북마크 상태가 유지된다
And 마이페이지 북마크 목록에 해당 게시글이 표시된다
```

### AC-2. 해제

```gherkin
Given 로그인 사용자가 북마크한 게시글을 보고 있을 때
When 북마크 해제 버튼을 누르면
Then 버튼이 북마크 안 됨 상태로 바뀌고
And 마이페이지 북마크 목록에서 해당 게시글이 제거된다
```

### AC-3. 중복 방지

```gherkin
Given 로그인 사용자가 동일 게시글에 대해 북마크 추가 요청을 반복할 때
When 서버가 요청을 처리하면
Then 해당 사용자와 게시글 조합의 북마크 행은 하나만 존재한다
And 최종 응답은 북마크됨 상태를 반환한다
```

### AC-4. 인증 요구

```gherkin
Given 비로그인 사용자가 게시글을 보고 있을 때
When 북마크 버튼을 누르면
Then 북마크 데이터는 생성되지 않고 로그인 안내가 표시된다
And 로그인 완료 후 원래 게시글로 돌아올 수 있다
```

### AC-5. 사용자 데이터 격리

```gherkin
Given 사용자 A와 사용자 B가 각각 로그인했을 때
When 각 사용자가 북마크 목록을 조회하거나 북마크를 삭제하려 하면
Then 각 사용자는 본인의 북마크만 조회 및 삭제할 수 있다
```

### AC-6. 실패 롤백

```gherkin
Given 로그인 사용자가 게시글의 북마크 상태를 변경할 때
When 네트워크 또는 서버 오류가 발생하면
Then 낙관적으로 변경된 UI는 이전 상태로 돌아가고
And 사용자는 오류와 재시도 가능 여부를 알 수 있다
```

### AC-7. 목록 페이지네이션

```gherkin
Given 로그인 사용자에게 20개를 초과하는 북마크가 있을 때
When 마이페이지 북마크 목록에서 다음 페이지를 요청하면
Then 기존 항목을 유지한 채 다음 항목이 중복이나 누락 없이 추가된다
And 모든 항목은 북마크 생성 시각 내림차순으로 정렬된다
```

### AC-8. 접근성

```gherkin
Given 키보드 또는 스크린 리더 사용자가 북마크 버튼에 접근했을 때
When 버튼을 확인하고 조작하면
Then 현재 선택 상태와 가능한 동작을 인지할 수 있고
And 키보드만으로 북마크 추가 및 해제를 완료할 수 있다
```

## 17. 테스트 범위

### 데이터베이스 및 보안

- `(user_id, post_id)` 중복 삽입 방지
- 사용자/게시글 삭제 시 cascade 동작
- RLS 기반 본인 조회, 생성, 삭제 허용
- 타 사용자 조회, 생성 위조, 삭제 차단
- 비공개 게시글 조인 시 기존 게시글 권한 유지

### 서버

- 인증 성공/실패
- 추가 및 해제의 멱등성
- 존재하지 않거나 열람 불가인 게시글 처리
- 잘못된 게시글 ID, 커서, limit 검증
- 페이지 경계에서 중복과 누락 없는 커서 페이지네이션
- 동률 `created_at`에서 안정적인 정렬

### 클라이언트

- 초기 북마크 상태 표시
- 낙관적 추가/해제 및 실패 롤백
- 연속 클릭과 응답 순서 역전 방지
- 상세, 카드, 마이페이지 간 캐시 동기화
- 로딩, 빈 상태, 최초 오류, 다음 페이지 오류 UI
- 로그인 유도 및 안전한 원위치 복귀

### 접근성 및 E2E

- 버튼 이름, `aria-pressed`, 포커스, 키보드 조작
- 로그인 → 북마크 추가 → 마이페이지 확인 → 해제 전체 흐름
- 새로고침 및 재로그인 후 상태 유지
- 서로 다른 두 사용자 간 데이터 격리

## 18. 출시 계획

1. 데이터베이스 마이그레이션과 RLS 정책을 적용하고 스테이징에서 권한 테스트를 완료한다.
2. 서버 인터페이스와 자동화 테스트를 배포한다.
3. 북마크 버튼과 마이페이지 목록을 연결한다.
4. 내부 또는 제한된 사용자 대상으로 오류율과 캐시 일관성을 확인한다.
5. 전체 사용자에게 공개하고 최소 2주간 지표와 오류 로그를 모니터링한다.

롤백 시 UI 진입점과 API를 비활성화하되, 사용자 북마크 데이터는 삭제하지 않는다. 데이터 삭제가 필요한 별도 결정 전까지 테이블을 보존한다.

## 19. 완료 정의

- 모든 기능 및 수용 기준을 충족한다.
- 데이터베이스 마이그레이션, RLS 정책, 롤백 계획이 코드로 관리된다.
- 단위/통합/E2E 테스트가 CI에서 통과한다.
- 모바일과 데스크톱에서 주요 브라우저 동작을 확인한다.
- 키보드 및 스크린 리더 기준의 핵심 접근성 검증을 완료한다.
- 스테이징에서 두 개의 실제 테스트 계정으로 데이터 격리를 검증한다.
- 분석 이벤트와 운영 오류 관찰 수단이 준비된다.
- 관련 사용자 도움말 또는 릴리스 노트를 갱신한다.

## 20. 오픈 이슈

구현 전에 아래 항목을 제품 및 개발 담당자가 확정한다.

1. 북마크 버튼을 게시글 상세에만 둘지, 모든 게시글 카드에도 둘지
2. 마이페이지 기존 정보 구조에서 북마크를 탭, 메뉴, 독립 페이지 중 어디에 배치할지
3. 목록의 추가 조회 방식을 무한 스크롤과 `더 보기` 중 무엇으로 할지
4. 기존 게시글 카드 응답에 로그인 사용자의 `bookmarked` 값을 일괄 포함할 수 있는지
5. 게시글이 비공개로 전환될 때 북마크 행을 보존할지 삭제할지
6. 제품의 기존 인증 구현에 맞춰 Route Handler와 Server Action 중 어느 방식을 표준으로 사용할지
