# 개발 프로세스와 검증 체계

## 전제와 목표

이 프로젝트는 고정된 과제와 작업공간에서 AI 코딩 에이전트를 실행하고 결과를 채점하는 로컬 CLI 또는 라이브러리라고 가정한다.

품질의 기준은 기능 수가 아니라 다음 네 가지다.

- **정확성:** 같은 결과를 올바르게 채점하고, 실패를 성공으로 판정하지 않는다.
- **재현성:** 같은 입력·설정·에이전트 결과에는 같은 채점 결과가 나온다.
- **격리와 안전성:** 에이전트가 평가 데이터, 호스트 파일, 비밀 값에 의도치 않게 접근하지 못한다.
- **진단 가능성:** 실패 원인을 로그와 실행 산출물만으로 다시 조사할 수 있다.

에이전트 자체의 확률적 출력과 평가 도구의 결정성은 구분한다. 도구는 동일한 패치나 실행 기록을 다시 채점할 때 결정적이어야 한다.

## 개발 흐름

각 변경은 한 가지 관찰 가능한 동작을 대상으로 한다.

1. 구현 전에 성공 예시와 대표 실패 예시를 짧게 적는다. 별도 명세 문서는 만들지 않고 테스트 이름이나 PR 설명에 둔다.
2. 채점 로직은 단위 테스트로, 프로세스 실행과 작업공간 처리는 통합 테스트로 먼저 표현한다. 버그 수정에는 그 버그를 재현하는 테스트를 포함한다.
3. 구현 후 로컬에서 관련 테스트를 실행하고, 전체 검증은 CI의 단일 명령으로 실행한다.
4. 코드·평가 과제·의존성 변경은 짧은 브랜치에서 진행한다. PR은 변경 내용을 한 번 읽고 CI를 통과시키는 장소로만 사용하며 별도 승인, 체크리스트, 티켓 연결은 요구하지 않는다.
5. 서로 무관한 리팩터링은 같은 변경에 섞지 않는다. 테스트가 실제 동작을 설명하고 CI가 통과하면 병합한다.

`sol-simplify: PR 흐름은 병합 전 실제 동작 검증을 위해 존재한다. 같은 보호를 더 단순하게 제공하는 방식이 생기거나 PR이 제품 결함과 무관한 병목이 되면 제거한다.`

## 검증 체계

### 1. 단위 테스트: 채점의 의미

- 점수 계산, 성공/실패 판정, 집계, 설정 기본값과 잘못된 입력을 검증한다.
- 손으로 만든 **정답 결과는 통과**하고 **그럴듯하지만 틀린 결과는 실패**하는 쌍을 둔다. 채점기 변경 시 이 쌍을 먼저 확장한다.
- 점수 범위, 순서 독립성처럼 항상 성립해야 하는 성질은 예제 몇 개보다 속성 테스트가 명확할 때만 속성 테스트로 둔다.
- 경로, 시간, 출력 순서처럼 환경에 따라 달라지는 값은 채점 전에 명시적으로 정규화한다.

### 2. 통합 테스트: 실행 하네스

실제 네트워크 모델 대신 출력과 종료 동작을 제어할 수 있는 가짜 에이전트를 사용한다. 작은 고정 저장소에서 다음 동작을 검증한다.

- 새 임시 작업공간 생성, 명령 실행, 변경 수집, 채점, 정리의 전체 흐름
- 정상 종료, 비정상 종료, 시간 초과, 취소, 잘못된 출력, 큰 출력
- 하위 프로세스 전체 종료와 부분 실행 결과 보존
- 작업공간 밖 경로 접근, 심볼릭 링크 탈출, 평가 전용 파일 수정 시도 차단
- stdout/stderr, 종료 코드, 실행 시간, 설정, 도구 버전, seed와 diff가 재현 산출물에 남는지 확인

테스트는 호스트의 사용자 설정이나 설치된 도구에 의존하지 않는다. 임시 디렉터리와 고정 fixture를 사용하며, fixture 변경은 이를 사용하는 테스트와 같은 변경에서 한다.

### 3. 설치 산출물 스모크 테스트

소스 트리가 아니라 실제 패키징된 산출물을 설치해 `도움말 → 예제 실행 → 결과 파일 읽기` 한 경로를 실행한다. 패키지 누락, 잘못된 엔트리포인트, 런타임 의존성 누락을 잡는 것이 목적이다.

`sol-simplify: 수동 릴리스 스모크는 배포물에서만 발생하는 결함을 잡기 위해 존재한다. CI가 동일한 배포물을 끝까지 검증하게 되면 수동 단계는 제거한다.`

### 4. 실제 모델 연동 테스트

외부 API를 호출하는 테스트는 필수 CI에 넣지 않는다. 비용, 네트워크, 모델 변동 때문에 제품 결함과 무관하게 실패할 수 있기 때문이다. 어댑터는 저장된 최소 응답 fixture로 계약을 테스트하고, 실제 호출은 릴리스 후보에서 필요할 때만 수동으로 확인한다. API 키나 호스트 비밀 값은 에이전트 프로세스에 전달하지 않는다.

## CI와 병합 기준

CI는 하나의 진입 명령으로 다음을 순서와 무관하게 실행한다.

- 빌드 및 패키징
- 결함을 찾는 정적 분석과 타입 검사
- 단위 테스트와 통합 테스트
- 설치 산출물 스모크 테스트

지원한다고 문서화한 운영체제와 런타임에서만 실행한다. 새 환경은 실제 지원을 약속할 때 추가한다. 코드 커버리지는 빠진 영역을 찾는 참고 자료로만 보고, 임의의 퍼센트를 병합 조건으로 삼지 않는다. 포맷팅은 자동화하되 제품 동작과 무관한 별도 검증 체계는 만들지 않는다.

필수 테스트가 불안정하면 재시도 횟수를 늘려 숨기지 않는다. 원인을 고치거나, 외부 변동에 의존한 테스트라면 필수 CI에서 분리한다. 실제 동작 회귀를 잡는 테스트는 삭제하지 않는다.

## 실행 안전성

에이전트가 임의 코드를 실행하므로 격리는 제품 요구사항이다. 샌드박스를 제공하기 전까지는 "호스트 사용자와 같은 권한으로 코드를 실행한다"는 사실을 CLI와 문서에 명확히 표시하고, 안전한 격리를 제공한다고 표현하지 않는다.

평가 전용 테스트와 정답 데이터는 에이전트의 쓰기 가능한 작업공간 밖에 둔다. 입력 경계에서 설정, 경로, 결과 형식을 검증하고 로그 크기와 실행 시간을 제한한다. 실패해도 원본 fixture는 바뀌지 않아야 하며 다음 실행은 깨끗한 복사본에서 시작해야 한다.

## 릴리스와 결함 대응

릴리스는 CI를 통과한 커밋에서 재현 가능하게 만든 패키지만 태그한다. 배포 전 설치 산출물의 스모크 경로를 확인하고, 사용자에게 영향을 주는 변경만 릴리스 노트에 적는다.

결함이 발견되면 먼저 최소 재현을 테스트로 고정하고 수정한다. 한 번의 실수를 이유로 새 승인 단계나 문서를 추가하지 않는다. 새 검사는 그 검사가 실제 사용자 결함을 잡았을 것이고 안정적으로 자동화할 수 있을 때만 추가한다. 제품이 정상인데 실패하는 검사나 유지비가 더 큰 검사는 수정하거나 제거한다.

`sol-simplify: 이 규칙은 검증 도구가 제품보다 커지는 것을 막기 위해 존재한다. 프로젝트에 여러 메인테이너가 생겨 실제 조정 문제가 확인되면 그 문제에 필요한 최소 절차로 교체한다.`
