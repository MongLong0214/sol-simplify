# 개발 프로세스와 검증 체계

## 목표와 원칙

이 프로젝트에서 품질은 단순히 "테스트가 통과함"이 아니라 다음을 뜻한다.

- 같은 입력, 설정, 버전에는 같은 평가 결과를 낸다.
- 점수와 판정의 근거를 재현하고 설명할 수 있다.
- 에이전트가 생성한 비신뢰 코드는 호스트와 다른 평가 실행에 영향을 주지 못한다.
- 실패, 시간 초과, 잘못된 출력도 정상적인 평가 결과로 처리한다.
- 한 명의 메인테이너가 지속할 수 있을 만큼 절차가 단순하다.

정확성과 재현성을 속도보다 우선한다. 모든 필수 검증은 자동화하고, 사람의 기억에 의존하는 체크리스트는 최소화한다.

## 변경 흐름

모든 코드 변경은 다음 순서로 진행한다.

1. **작업 정의**: 이슈에 문제, 범위 밖인 것, 관찰 가능한 완료 조건, 주요 위험을 짧게 적는다. 작은 변경은 이 네 항목만 있는 한 단락이면 충분하다.
2. **작은 브랜치**: 한 브랜치와 PR은 한 가지 동작 변경만 담는다. 생성 코드나 대규모 포맷 변경은 기능 변경과 분리한다.
3. **검증 먼저 정의**: 새 동작에는 완료 조건을 증명할 테스트를, 버그 수정에는 실패를 재현하는 회귀 테스트를 추가한다.
4. **구현**: 완료 조건을 만족하는 가장 작은 변경만 한다. 공개 동작이나 평가 형식이 달라지면 문서도 같은 PR에서 고친다.
5. **로컬 검증**: 포맷, 정적 분석, 단위·통합 테스트를 모두 실행한다.
6. **자기 리뷰**: PR diff를 처음부터 읽으며 불필요한 변경, 테스트 누락, 비밀정보, 비결정적 동작, 하위 호환성 영향을 확인한다.
7. **CI 후 병합**: 필수 검사가 모두 통과한 PR만 `main`에 squash merge한다. 실패한 검사를 우회하거나 불안정한 테스트를 단순 재실행해 통과시키지 않는다.

긴급 수정도 같은 흐름을 따른다. 보안상 공개 전에 수정해야 하는 경우에만 비공개 브랜치에서 진행하고, 배포 후 회귀 테스트와 설명을 보완한다.

## 완료의 정의

변경은 다음 조건을 모두 만족할 때만 완료다.

- 이슈의 완료 조건을 충족한다.
- 정상 경로와 관련 실패 경로가 자동 테스트로 검증된다.
- 포맷, 린트, 타입 검사(사용 언어가 지원하는 경우), 테스트가 통과한다.
- 점수, 실행기, 입출력 형식 변경에는 고정 fixture를 사용한 통합 테스트가 있다.
- 사용자에게 보이는 동작, 설정 또는 호환성 변화가 문서와 changelog에 기록됐다.
- 새 의존성은 꼭 필요한 최소 범위이며 라이선스와 알려진 취약점을 확인했다.
- CI가 깨끗한 환경에서 같은 결과를 냈다.

## 테스트 구조

### 단위 테스트

파서, 설정 검증, 점수 계산, 결과 집계처럼 결정적인 핵심 로직을 빠르게 검증한다. 특히 점수 계산은 경계값, 빈 결과, 부분 실패, 중복 결과, 순서 변경을 포함한다. 시간, 난수, 파일 경로처럼 결과에 영향을 주는 값은 명시적으로 주입하거나 고정한다.

### 통합 테스트

작은 고정 저장소와 실제 평가 실행 흐름을 연결한다. 실제 모델 대신 성공, 잘못된 출력, 충돌, 무응답, 시간 초과를 재현하는 고정된 가짜 에이전트를 사용한다. 최소한 다음을 검증한다.

- 입력 준비 → 에이전트 실행 → 테스트 실행 → 점수 산출 → 결과 저장의 전체 흐름
- 종료 코드, 신호, 시간 초과와 자원 초과의 분류
- 깨진 출력과 누락된 파일에 대한 일관된 판정
- 같은 fixture를 반복 실행했을 때 동일한 정규화 결과와 점수
- 한 실행의 파일과 프로세스가 다음 실행에 남지 않음

Fixture에는 입력 저장소 스냅샷, 과제, 평가 설정, 기대 판정과 점수를 함께 버전 관리한다. 기대값 갱신은 테스트를 통과시키기 위한 자동 덮어쓰기를 금지하고, 변경 이유와 전후 diff를 PR에서 확인한다. 타임스탬프나 임시 경로처럼 의미 없는 값은 기대값에서 제외한다.

### 종단 간 및 호환성 테스트

패키지 설치, CLI 실행, 결과 파일 생성, 문서의 대표 예제를 깨끗한 환경에서 검증한다. 외부 AI API를 쓰는 검증은 비용과 비결정성 때문에 PR의 필수 게이트로 삼지 않는다. 대신 고정 모델·프롬프트·파라미터로 정기 실행하고, 원시 응답과 실행 메타데이터를 보관해 이전 기준선과 비교한다.

## 평가 도구 전용 품질 규칙

### 재현성과 추적성

각 평가 결과에는 최소한 도구 버전, 평가/점수 규칙 버전, 입력 커밋 또는 콘텐츠 해시, 에이전트와 모델 식별자, 프롬프트/설정, 의존 환경, 난수 시드, 시작·종료 시각을 남긴다. 원시 출력과 로그는 점수와 분리해 보존한다. 같은 저장 결과에서 점수를 다시 계산할 수 있어야 하며, 재계산 결과는 원래 점수와 일치해야 한다.

### 격리와 보안

에이전트가 생성한 코드는 비신뢰 입력으로 취급해 일회용 샌드박스에서 실행한다. 샌드박스는 기본적으로 네트워크를 끄고, 읽기·쓰기 범위, CPU, 메모리, 프로세스 수, 디스크와 실행 시간을 제한한다. 호스트 자격 증명과 CI 비밀정보를 전달하지 않으며 평가 테스트와 정답 데이터는 에이전트가 수정할 수 없는 위치에 둔다. 로그에 토큰이나 환경 변수 값이 남지 않는지 테스트한다.

### 점수와 벤치마크 무결성

점수 규칙은 버전이 있는 공개 명세로 관리한다. 규칙 변경은 기존 fixture 전체의 점수 차이를 보여 주고, 의도한 차이만 있는지 확인한 뒤 새 버전으로 배포한다. 평가 순서, 병렬 실행 여부, 로케일, 시간대에 따라 점수가 달라지지 않아야 한다. 공개 예제와 실제 비교용 benchmark를 구분하고, 에이전트가 평가 테스트나 기대 답을 입력으로 읽지 못하는지 통합 테스트로 검증한다.

## 자동화 게이트

`main` 브랜치는 직접 변경하지 않고 PR의 필수 검사를 요구한다. 도구 체계를 정한 뒤 로컬과 CI가 호출하는 단일 검증 명령을 제공하며, 다음 게이트를 둔다.

| 시점 | 필수 검증 | 실패 시 처리 |
| --- | --- | --- |
| 모든 PR | 포맷 확인, 린트, 타입 검사, 단위 테스트, 빠른 통합 테스트, 의존성 취약점 검사 | 병합 금지 |
| 실행기·샌드박스 변경 PR | 시간/자원 제한, 네트워크·파일 격리, 비밀정보 비노출 테스트 | 병합 금지 |
| 점수·결과 형식 변경 PR | 전체 fixture 회귀, 재계산 일치, 이전 버전과의 결과 diff | 의도하지 않은 차이가 있으면 병합 금지 |
| 주기 실행 | 전체 통합 테스트, 지원 환경 조합, 실제 외부 에이전트 smoke test | 이슈 생성 후 원인 분류; 제품 회귀면 릴리스 중지 |
| 릴리스 후보 | 깨끗한 설치, 전체 테스트, CLI smoke test, 문서 예제, 패키지 내용 확인 | 배포 금지 |

코드 커버리지는 누락을 찾는 보조 지표로 보고 숫자만 맞추는 테스트는 만들지 않는다. 대신 점수 계산, 결과 판정, 샌드박스 수명 주기의 모든 분기와 확인된 모든 버그에 테스트가 있어야 한다. 불안정한 테스트는 발견 즉시 수정하거나 필수 게이트에서 제거하지 않은 채 해당 기능의 병합을 멈춘다.

## 릴리스와 회귀 대응

릴리스는 Semantic Versioning을 따르고 태그와 changelog를 남긴다. 평가 결과가 달라질 수 있는 규칙 변경은 최소 minor 버전으로 명시하고, 결과 형식의 호환되지 않는 변경은 major 버전으로 취급한다. 배포 산출물은 CI가 태그에서 만들며 로컬에서 수동 생성하지 않는다.

회귀가 발견되면 먼저 재현 가능한 최소 fixture를 추가해 현재 버전에서 실패함을 확인한다. 수정과 함께 전체 fixture의 점수 diff를 검토하고, 영향받은 릴리스와 우회 방법을 이슈에 기록한다. 데이터 손상, 샌드박스 탈출, 자격 증명 노출 가능성이 있으면 새 릴리스를 중지하고 보안 수정으로 우선 처리한다.

## 첫 구현 전 체크리스트

기능 개발을 시작하기 전에 다음 기반만 먼저 만든다.

- 지원 플랫폼과 런타임 버전을 정하고 고정한다.
- 포맷, 린트, 타입 검사, 테스트를 실행하는 로컬 명령을 정한다.
- 같은 명령을 실행하는 CI와 `main` 보호 규칙을 설정한다.
- 성공·실패·시간 초과를 내는 최소 가짜 에이전트와 fixture 하나를 만든다.
- 결과 형식과 점수 규칙의 첫 버전을 문서화한다.
- 라이선스, 기여 안내, 보안 취약점 제보 경로를 추가한다.

이 기반이 통과한 뒤 세로로 완결된 가장 작은 기능부터 구현한다. 새 도구나 별도 환경은 실제로 반복되는 문제를 해결할 때만 추가한다.
