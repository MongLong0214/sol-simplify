# PR 리뷰 프로세스

3명인 팀이 변경 내용을 공유하고 실수를 줄이기 위한 최소 규칙이다.

## 기본 규칙

- 공유 브랜치에 반영할 변경은 PR로 올린다.
- 작성자를 제외한 팀원 1명의 승인을 받으면 병합할 수 있다.
- 테스트와 자동 검사가 실패한 상태에서는 병합하지 않는다.
- 작성자는 리뷰를 받았더라도 변경 결과에 대한 책임을 가진다.

## 진행 순서

### 1. PR 작성

작성자는 리뷰 전에 스스로 변경 내용을 확인하고 PR 본문에 다음을 적는다.

- 변경한 이유와 주요 내용
- 리뷰어가 특히 봐야 할 부분
- 실행한 테스트 또는 테스트하지 못한 이유

PR은 한 가지 목적에 집중한다. 관련 없는 변경이 섞였다면 가능한 범위에서 분리한다.

### 2. 리뷰 요청

작성자는 다른 팀원 1명을 리뷰어로 지정한다. 특정 영역을 잘 아는 사람이 있다면 우선 요청하되, 그 사람이 아니어도 리뷰할 수 있다. 업무가 급하면 요청할 때 그 사실을 함께 알린다.

### 3. 리뷰

리뷰어는 다음을 중심으로 확인한다.

- 의도한 동작을 구현했는지
- 오류, 보안 문제, 데이터 손실 가능성이 있는지
- 필요한 테스트가 있는지
- 이후 팀원이 이해하고 수정할 수 있는지

반드시 수정해야 하는 의견은 이유와 원하는 결과를 분명히 적는다. 선택 사항은 `제안:`으로 시작하며, 취향 차이만으로 병합을 막지 않는다. 문제가 없으면 승인한다.

### 4. 의견 반영

작성자는 각 의견에 수정 내용이나 답변을 남긴다. 차단 의견이 남아 있으면 리뷰어의 재확인을 받는다.

두 사람이 합의하지 못하면 남은 팀원에게 맥락과 선택지를 보여 주고 의견을 구한다. 세 사람의 논의 후에는 가장 안전하고 단순한 선택을 적용하고, 이유는 PR 대화에 남긴다.

### 5. 병합

다음 조건을 만족하면 작성자가 PR을 병합한다.

- 차단 의견이 모두 해결됨
- 테스트와 자동 검사가 통과함
- 작성자 외 팀원 1명이 승인함

병합 뒤 문제가 발견되면 먼저 영향을 줄이거나 되돌리고, 필요한 수정은 새 PR로 진행한다.

> sol-simplify: 리뷰 누락과 의견 교착을 막기 위한 최소 절차다. 팀 규모가 바뀌거나 이 절차가 개발 속도만 늦추면 해당 규칙을 삭제하거나 조정한다.
