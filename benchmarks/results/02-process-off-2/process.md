# 개발 프로세스 및 검증 체계

## 1. 목적과 적용 범위

이 문서는 AI 코딩 에이전트 평가 도구의 개발, 검증, 배포, 유지보수 방식을 정의한다. 목표는 결함이 절대 없다고 주장하는 것이 아니라, 모든 변경과 평가 결과에 대해 **재현 가능하고 추적 가능한 품질 근거**를 남기는 것이다.

현재 전제는 다음과 같다.

- 프로젝트는 코드가 없는 초기 단계다.
- 메인테이너는 1명이며, 프로세스는 혼자서 지속할 수 있어야 한다.
- 평가 대상 에이전트의 코드와 출력은 신뢰할 수 없는 입력으로 취급한다.
- 언어, 실행 환경, CI 서비스는 아직 결정되지 않았다. 이 문서의 원칙과 게이트는 기술 스택과 무관하게 적용한다.

초기에는 자동화된 검증과 변경 추적에 집중한다. 회의, 수동 승인, 장황한 문서처럼 1인 프로젝트에 실효성이 낮은 절차는 두지 않는다.

## 2. 품질 목표

우선순위는 다음과 같다.

| 우선순위 | 품질 속성 | 통과 기준 |
|---|---|---|
| 1 | 정확성 | 점수 계산과 성공/실패 판정이 명세 및 독립된 테스트 오라클과 일치한다. |
| 2 | 재현성 | 동일한 버전, 입력, 설정, 환경에서 결정적 구성 요소는 같은 결과를 낸다. 비결정적 결과는 분포와 불확실성으로 보고한다. |
| 3 | 격리와 안전 | 평가 대상 코드가 호스트, 자격 증명, 다른 실행 또는 결과 저장소를 침해하지 못한다. |
| 4 | 추적성 | 모든 결과에서 도구, 벤치마크, 데이터, 설정, 환경, 입력의 정확한 버전을 역추적할 수 있다. |
| 5 | 호환성과 사용성 | 지원한다고 명시한 환경에서 설치·실행·결과 해석이 가능하며 오류가 행동 가능한 메시지를 제공한다. |
| 6 | 성능 | 정한 시간·메모리·비용 한도 안에서 평가가 완료되고 성능 퇴행을 탐지한다. |

다음 불변 조건은 기능보다 우선한다.

1. 공개된 벤치마크 버전의 의미를 소급 변경하지 않는다.
2. 서로 다른 벤치마크 버전의 점수를 같은 척도처럼 비교하지 않는다.
3. 실행 실패, 인프라 실패, 에이전트 실패, 채점 실패를 서로 다른 상태로 기록한다.
4. 평가 대상의 텍스트, 패치, 파일, 로그는 모두 신뢰할 수 없는 입력으로 처리한다.
5. 결과 하나만으로 비결정적 시스템의 우열이나 퇴행을 단정하지 않는다.
6. 실패를 숨기기 위한 자동 재시도나 테스트 제외를 허용하지 않는다.

## 3. 변경 흐름

모든 제품 코드 변경은 다음 흐름을 따른다.

```text
이슈/요구사항 → 위험 분류 → 설계 또는 수용 기준 → 작업 브랜치
→ 구현과 테스트 → 로컬 검증 → PR 기반 자기 검토 → CI 통과 → 병합
→ 필요 시 릴리스 → 배포 후 확인
```

### 3.1 이슈와 수용 기준

버그, 기능, 벤치마크 변경은 구현 전에 이슈나 PR 설명으로 다음을 기록한다.

- 해결할 문제와 해결하지 않을 범위
- 관찰 가능한 수용 기준
- 정상, 경계, 실패 사례
- 결과 형식이나 공개 API의 변경 여부
- 재현성, 보안, 성능에 미치는 영향
- 검증 방법

작업 도중 요구사항이 달라지면 설명을 먼저 갱신한다. 작은 오탈자와 내부 문서 수정은 별도 이슈 없이 PR 설명만으로 충분하다.

### 3.2 위험 등급

| 등급 | 예시 | 추가 요구사항 |
|---|---|---|
| 낮음 | 문구, 주석, 비동작 문서, 내부 리팩터링 | 관련 자동 검사와 자기 검토 |
| 중간 | CLI, 어댑터, 결과 포맷, 일반 기능 | 수용 기준, 회귀 테스트, 통합 테스트, 호환성 검토 |
| 높음 | 채점기, 집계식, 벤치마크 데이터·스키마, 샌드박스, 권한, 비밀정보 처리, 공개 결과에 영향을 주는 기본값 | 짧은 설계 기록, 독립된 오라클 또는 이중 구현 검증, 전체 평가 스모크 테스트, 다음 작업 세션에서 2차 자기 검토 |

높은 위험 변경에 외부 검토자를 구할 수 없다면 자동화된 독립 검증을 반드시 추가한다. 그마저 불가능하면 안정 릴리스에 포함하지 않고 실험 기능 또는 프리릴리스로 배포한다.

### 3.3 설계 기록

다음 결정은 `docs/adr/`에 짧은 ADR(Architecture Decision Record)로 남긴다.

- 실행 격리 방식
- 벤치마크 및 결과 스키마
- 점수 계산과 집계 방식
- 플러그인 또는 에이전트 어댑터 경계
- 호환성을 깨는 공개 API 변경
- 개인정보, 원격 실행, 텔레메트리 정책

ADR에는 맥락, 결정, 대안, 결과만 기록한다. 이미 코드와 테스트로 명확한 세부 구현은 반복해서 문서화하지 않는다.

### 3.4 브랜치와 PR

- `main`은 항상 릴리스 가능한 상태로 유지한다.
- 제품 코드는 짧게 유지되는 작업 브랜치와 PR을 통해 병합한다.
- PR은 하나의 목적만 가지며 리팩터링과 동작 변경을 가능한 한 분리한다.
- 필수 CI가 실패한 상태에서는 병합하지 않는다.
- 혼자 작업하더라도 PR 화면에서 최종 diff, 생성 파일, 설정 변경을 검토한다.
- 높은 위험 변경은 최초 구현 직후가 아닌 다음 작업 세션에 다시 읽는다.
- 긴급 수정도 같은 검증을 거친다. 생략한 검증이 있다면 이슈로 남기고 다음 패치 전에 완료한다.

커밋 메시지는 변경의 이유를 설명한다. 히스토리를 이해하기 어렵게 만드는 의미 없는 커밋은 병합 전에 정리한다.

## 4. 아키텍처상의 검증 경계

구현은 최소한 다음 책임을 분리한다.

- **벤치마크 정의:** 과제, 입력, 기대 조건, 라이선스, 버전
- **실행기:** 작업 공간 준비, 에이전트 실행, 제한 적용, 산출물 회수
- **에이전트 어댑터:** 각 에이전트의 호출 규약을 공통 인터페이스로 변환
- **검증기/채점기:** 산출물을 판정하고 근거를 생성
- **집계기:** 여러 과제와 반복 실행의 통계를 계산
- **결과 저장 및 보고:** 기계 판독 결과와 사람이 읽는 요약 생성

각 경계는 버전이 있는 명시적 스키마를 사용한다. 실행기가 점수를 계산하거나, 어댑터가 결과를 임의로 보정하거나, 리포터가 원시 판정을 다시 해석하지 않게 한다. 이를 통해 각 계층을 독립적으로 테스트할 수 있다.

핵심 로직은 가능한 한 순수 함수로 만들고 시간, 난수, 파일 시스템, 네트워크, 프로세스 실행은 주입 가능한 경계 뒤에 둔다. 결정적 핵심과 비결정적 외부 시스템을 분리하는 것이 재현성의 기본이다.

## 5. 테스트 전략

테스트는 실제 위험을 기준으로 구성한다. 커버리지 숫자만 높이기 위한 테스트는 작성하지 않는다.

### 5.1 테스트 계층

| 계층 | 검증 대상 | 실행 시점 |
|---|---|---|
| 단위 테스트 | 파서, 상태 전이, 점수식, 집계, 제한 계산, 오류 매핑 | 모든 PR |
| 스키마/계약 테스트 | 벤치마크, 어댑터, 결과 포맷의 입력·출력 계약과 이전 버전 fixture | 모든 PR |
| 통합 테스트 | 실행기-어댑터-채점기 연결, 작업 공간 수명주기, 타임아웃과 정리 | 모든 PR의 소형 fixture |
| 종단 간 스모크 테스트 | 가짜 에이전트가 포함된 최소 평가 전체 흐름 | 모든 PR |
| 골든/회귀 테스트 | 알려진 입력의 판정 근거 및 결과 구조 | 모든 PR |
| 속성/퍼즈 테스트 | 파서, 경로, 스키마, 집계의 불변 조건과 악성 입력 | 야간, 핵심 사례는 PR |
| 보안 테스트 | 격리 탈출 시도, 경로 순회, 심볼릭 링크, 로그/HTML 주입, 비밀정보 노출 | 관련 PR 및 야간 |
| 성능 테스트 | 실행 오버헤드, 메모리, 대규모 결과 처리, 비용 예산 | 야간 및 릴리스 |
| 실제 에이전트 호환성 | 지원하는 에이전트/모델의 최소 실제 실행 | 정기 실행 및 릴리스 후보 |

### 5.2 채점 정확성

채점기와 집계기는 프로젝트에서 가장 엄격하게 검증한다.

- 사람이 직접 계산할 수 있는 작은 fixture와 예상 점수를 둔다.
- 성공, 부분 성공, 실패, 타임아웃, 누락, 중복, 잘못된 형식을 모두 테스트한다.
- 평균, 가중치, 반올림, 결측값, 동점 처리의 의미를 명세하고 경계값을 테스트한다.
- 가능한 경우 프로덕션 코드와 구현을 공유하지 않는 단순한 참조 오라클로 결과를 교차 검증한다.
- 과제 순서 변경이 총점에 영향을 주지 않는지 등 메타모픽 속성을 검증한다.
- 골든 파일은 전체 로그가 아니라 안정적인 의미 데이터만 포함한다. 변경 시 diff를 사람이 확인하며 무조건 재생성하지 않는다.

### 5.3 테스트 데이터

- 기본 테스트에는 작고 합성된 데이터를 사용한다.
- 외부 데이터에는 출처, 버전, 라이선스, 수집일, 해시를 기록한다.
- 개인정보, 자격 증명, 고객 코드, 라이선스가 불명확한 코드를 저장소에 넣지 않는다.
- 학습 데이터 오염이나 벤치마크 누출 위험을 문서화한다.
- 개발용, 검증용, 비공개 홀드아웃이 필요하다면 접근과 공개 정책을 구분한다.
- 공개 후 바뀐 데이터는 기존 버전을 덮어쓰지 않고 새 벤치마크 버전으로 추가한다.

### 5.4 결정성과 비결정성

결정적 테스트는 시간대, 로케일, 파일 순서, 실제 시계, 전역 난수에 의존하지 않는다. 테스트에서 시간과 난수 시드를 고정하고 네트워크는 기본적으로 차단한다.

모델이나 에이전트처럼 비결정적인 대상을 비교할 때는 다음을 적용한다.

- 단일 실행이 아니라 사전에 정한 반복 횟수를 사용한다.
- 같은 과제에 대한 paired run을 우선한다.
- 평균만이 아니라 표본 수, 성공률, 분산 또는 신뢰구간을 함께 보고한다.
- 회귀 판정 전에 실질적 허용 한계와 통계적 기준을 정한다.
- 재시도는 원래 실패를 지우지 않고 별도 attempt로 기록한다.
- 비용 때문에 반복 횟수를 줄였다면 결과의 불확실성을 표시한다.

초기 기본값은 PR 스모크 테스트 1회, 정기 비교 실행은 과제별 최소 5회로 한다. 표본 수와 판정 기준은 실제 분산을 수집한 후 ADR로 조정한다.

### 5.5 실패와 flaky 테스트

- 새 결함은 가능하면 먼저 실패하는 최소 재현 테스트로 고정한 뒤 수정한다.
- flaky 테스트는 재실행 성공으로 통과 처리하지 않는다.
- 환경 문제와 제품 결함을 구분할 수 있도록 오류 상태와 로그를 구조화한다.
- 격리 조치는 다른 개발을 실제로 막는 경우에만 허용하고, 담당 이슈와 만료일(최대 7일)을 둔다.
- 실패 원인이 제거되기 전에는 같은 영역의 안정 릴리스를 만들지 않는다.

## 6. AI 에이전트 평가에 특화된 검증

### 6.1 실행 격리

평가 대상 코드와 명령은 적대적일 수 있다고 가정한다.

- 매 실행은 폐기 가능한 별도 작업 공간과 프로세스 경계를 사용한다.
- 네트워크는 기본 차단하고, 필요한 호스트만 명시적으로 허용한다.
- CPU, 메모리, 디스크, 실행 시간, 프로세스 수, 출력 크기에 제한을 둔다.
- 호스트 자격 증명, SSH 에이전트, 클라우드 메타데이터, 사용자 홈을 노출하지 않는다.
- 작업 디렉터리 밖 경로, 심볼릭 링크, 경로 순회, 남은 자식 프로세스를 검증한다.
- 실행 후 프로세스와 임시 자원을 정리하고 다른 실행과 캐시를 공유하지 않는 모드를 제공한다.
- 격리 실패는 과제 실패가 아니라 인프라/보안 실패로 기록하고 해당 결과를 무효화한다.

컨테이너만 사용했다고 안전하다고 간주하지 않는다. 첫 안정 릴리스 전에 `docs/threat-model.md`에 자산, 신뢰 경계, 공격자 능력, 완화책, 잔여 위험을 기록한다.

### 6.2 결과와 로그의 안전

- 터미널 제어 문자, HTML/Markdown, 파일명과 링크를 표시 전에 이스케이프하거나 정제한다.
- 로그에 토큰, 환경 변수, 인증 헤더, 사용자 경로가 포함되지 않게 구조적 마스킹을 적용한다.
- 출력이 제한을 넘으면 잘렸다는 사실과 원본 크기를 기록한다.
- 보고서는 원시 에이전트 문구와 도구가 생성한 판정을 명확히 구분한다.
- 외부 PR에서 실행되는 CI에는 배포 비밀정보를 제공하지 않는다.

### 6.3 실행 provenance

모든 평가 결과에는 가능한 범위에서 다음 메타데이터를 포함한다.

- 도구 버전과 소스 커밋
- 벤치마크 이름, 버전, manifest 해시
- 과제 ID와 데이터 해시
- 에이전트/어댑터 이름과 버전
- 모델 제공자, 정확한 모델 식별자, 노출되는 모델 리비전
- 프롬프트/정책/도구 설정의 해시
- temperature, seed 등 생성 설정
- OS, 아키텍처, 런타임과 격리 이미지 digest
- 시작·종료 시각, 제한, 종료 사유, 재시도 번호
- 토큰, 시간, 비용 등 사용량
- 채점기 버전, 원시 판정, 집계 결과

비밀정보와 불필요한 개인정보는 provenance에 포함하지 않는다. 재현에 필요한 값과 보관하면 안 되는 값을 스키마에서 구분한다.

### 6.4 벤치마크 버전

- 릴리스된 벤치마크 bundle은 불변이다.
- 과제, fixture, 실행 조건, 채점기, 집계식, 기본 제한 중 점수 의미에 영향을 주는 변경은 새 벤치마크 버전을 만든다.
- 문구나 메타데이터만 바뀌어 점수 의미가 같을 때만 패치 버전을 사용한다.
- 도구 버전과 벤치마크 버전을 별도로 기록한다.
- 결과 비교는 같은 벤치마크 버전과 호환 환경에서만 기본 허용한다. 다른 경우 명시적인 경고를 표시한다.
- 새 버전에는 변경 이유, 예상 영향, 이전 버전과의 비교 가능 여부를 기록한다.

## 7. 자동 품질 게이트

로컬과 CI가 같은 명령을 사용하도록 저장소 루트에 안정적인 작업 진입점을 제공한다. 실제 도구는 기술 스택을 정할 때 선택하되 다음 의미는 유지한다.

| 명령 역할 | 내용 |
|---|---|
| `bootstrap` | 고정된 의존성으로 개발 환경 준비 |
| `format` / `format-check` | 자동 포맷 적용 / 차이 검사 |
| `lint` | 정적 분석과 금지 패턴 검사 |
| `typecheck` | 지원 언어의 엄격 타입 검사 |
| `test` | 단위·계약 테스트 |
| `test-integration` | 격리된 통합 테스트 |
| `test-e2e-smoke` | 가짜 에이전트 기반 전체 흐름 |
| `verify` | PR에서 요구하는 모든 빠른 검사 |
| `benchmark-smoke` | 소형 벤치마크와 결과 스키마 검증 |

### 7.1 모든 PR의 필수 검사

목표 실행 시간은 10분 이내, 상한은 15분으로 한다.

1. 포맷 검사
2. 린트와 엄격 타입 검사
3. 단위 및 계약 테스트
4. 소형 통합 및 종단 간 스모크 테스트
5. 결과/벤치마크 스키마 검증과 하위 호환 fixture
6. 문서의 코드 예제와 링크 검사
7. 비밀정보 및 알려진 고위험 의존성 검사
8. 라이선스 정책 검사
9. 변경된 핵심 로직의 커버리지 검사

초기 커버리지 기준은 전체 line coverage 80% 이상, 채점·집계·스키마·보안 경계의 branch coverage 90% 이상으로 한다. 기존 수치를 낮추는 변경은 허용하지 않는다. 단, 숫자 충족보다 수용 기준과 실패 경로 검증이 우선이며, 제외할 코드는 근거를 주석 또는 설정에 남긴다.

### 7.2 야간 또는 정기 검사

- 지원 OS·런타임 조합 전체 테스트
- 실제 에이전트 최소 호환성 테스트
- 퍼즈/속성 테스트와 격리 공격 fixture
- 반복 실행을 통한 결정성 확인
- 성능·메모리·비용 기준선 비교
- 전체 의존성 및 컨테이너 취약점 검사
- 깨진 링크와 설치 문서의 깨끗한 환경 검증

정기 검사가 실패하면 자동으로 이슈를 만들거나 눈에 띄는 상태로 남긴다. 알림만 발생하고 장기간 방치되는 검사는 제거하거나 고친다.

### 7.3 릴리스 후보 검사

- 깨끗한 환경에서 설치 및 제거
- 지원 환경 전체 매트릭스
- 전체 벤치마크 스모크와 이전 안정 버전 비교
- 패키지 내용에 비밀, 로컬 경로, 불필요한 대형 파일이 없는지 확인
- 산출물 checksum, SBOM, provenance 생성
- 사용자 문서의 빠른 시작을 그대로 실행

## 8. 자기 검토 체크리스트

PR을 병합하기 전에 다음 질문에 답한다.

- 수용 기준을 모두 충족하며 범위 밖 변경은 없는가?
- 잘못된 입력, 부분 실패, 타임아웃, 취소, 정리 실패를 처리하는가?
- 점수나 공개 결과가 달라진다면 의도와 버전 변경이 명시됐는가?
- 결정성, 실행 순서, 로케일, 시간대, 동시성에 숨은 의존성이 없는가?
- 신뢰할 수 없는 데이터가 셸, 경로, 로그, HTML, 쿼리에 안전하게 전달되는가?
- 로그와 결과에 비밀정보가 노출되지 않는가?
- 새 동작과 회귀를 증명하는 테스트가 있는가?
- 사용자가 알아야 할 CLI/API/설정 변경이 문서와 changelog에 반영됐는가?
- 실패 메시지가 원인과 다음 행동을 알려주는가?
- 전체 diff에 디버그 코드, 임시 우회, 생성물, 무관한 파일이 없는가?

## 9. 완료의 정의(Definition of Done)

변경은 다음 조건을 모두 충족해야 완료다.

- 수용 기준을 충족한다.
- 필요한 자동 테스트가 추가되고 로컬 `verify`가 통과한다.
- 필수 CI가 모두 통과한다.
- 위험 등급에 필요한 추가 검증이 완료됐다.
- 사용자 동작, 공개 API, 설정 또는 결과 의미가 바뀌었다면 문서가 갱신됐다.
- 호환성 또는 마이그레이션 영향이 기록됐다.
- 보안, 개인정보, 라이선스 영향이 검토됐다.
- 임시 코드와 알려진 후속 작업은 숨기지 않고 이슈로 연결됐다.
- PR 자기 검토가 끝났다.

## 10. 릴리스 정책

### 10.1 버전과 변경 기록

- 도구는 Semantic Versioning을 따른다. `1.0.0` 전에도 호환성을 깨는 변경은 명확히 기록한다.
- 사용자에게 보이는 변경은 `CHANGELOG.md`의 Added, Changed, Fixed, Security, Deprecated, Removed 범주에 기록한다.
- 릴리스 태그는 서명하고, 생성된 패키지와 컨테이너는 가능한 한 재현 가능한 방식으로 빌드한다.
- 안정 릴리스는 변경 불가능한 태그와 artifact digest를 가진다.
- 공개 API 제거에는 최소 한 번의 minor 릴리스에 걸친 폐기 경고와 대체 방법을 제공한다. 보안상 즉시 제거가 필요하면 예외와 이유를 기록한다.

### 10.2 릴리스 절차

1. 릴리스 범위와 버전을 결정하고 changelog를 정리한다.
2. 릴리스 후보에서 전체 검증을 실행한다.
3. 결과 스키마와 벤치마크 버전의 호환성을 확인한다.
4. 패키지, checksum, SBOM, provenance를 생성한다.
5. 서명된 태그와 릴리스 노트를 게시한다.
6. 깨끗한 환경에서 게시된 artifact를 다시 설치하고 스모크 테스트한다.
7. 실패 시 같은 버전을 덮어쓰지 않고 수정 버전을 낸다.

초기에는 기능을 모아 큰 릴리스를 만들기보다 작고 되돌리기 쉬운 릴리스를 선호한다.

## 11. 버그, 보안 문제, 회귀 대응

버그 보고에는 가능한 한 도구/벤치마크 버전, 환경, 명령, 기대 결과, 실제 결과, 최소 재현 자료를 받는다.

- 정확한 점수에 영향을 주는 버그는 어떤 결과 버전이 영향받았는지 조사하고 릴리스 노트에 명시한다.
- 잘못된 공개 결과가 생겼다면 조용히 덮어쓰지 않고 무효 또는 수정 상태를 표시한다.
- 보안 취약점은 공개 이슈가 아닌 `SECURITY.md`의 비공개 채널로 접수한다.
- 심각도, 악용 가능성, 데이터/격리 영향으로 우선순위를 정한다.
- 수정에는 회귀 테스트를 포함하되 공개가 실제 공격을 돕는 경우 패치 배포 후 공개한다.
- 중대한 장애나 잘못된 채점은 짧은 사후 분석을 남긴다: 영향, 탐지, 원인, 수정, 재발 방지.

## 12. 의존성과 공급망

- 단일 패키지 관리자와 lockfile을 사용하고 CI에서 고정 설치를 강제한다.
- 새 의존성은 필요성, 유지보수 상태, 라이선스, 크기, 권한, 대안을 확인한다.
- 런타임 의존성은 최소화한다. 특히 평가 실행 경계의 의존성을 엄격히 제한한다.
- 자동 의존성 PR은 CI를 통과한 뒤 병합하며 major 업데이트는 수동으로 변경 내용을 검토한다.
- CI 액션과 빌드 이미지는 변경 불가능한 commit 또는 digest로 고정한다.
- 릴리스에는 SBOM을 첨부하고 알려진 고위험 취약점이 있는 artifact는 배포하지 않는다. 예외에는 영향 분석과 만료일을 둔다.

## 13. 오픈소스 운영

첫 공개 전에 다음 파일을 준비한다.

- `README.md`: 목적, 비목표, 빠른 시작, 결과 해석, 현재 한계
- `LICENSE`: 선택한 오픈소스 라이선스
- `CONTRIBUTING.md`: 개발 환경, 검증 명령, PR 규칙
- `CODE_OF_CONDUCT.md`: 참여 행동 기준
- `SECURITY.md`: 지원 버전과 비공개 신고 방법
- `CHANGELOG.md`: 사용자 관점의 변경 기록
- `docs/architecture.md`: 구성 요소와 데이터 흐름
- `docs/threat-model.md`: 신뢰 경계와 잔여 위험

외부 기여는 작은 PR을 권장하고, 행동 변경에는 테스트를 요구한다. 메인테이너가 최종 기술 결정을 하되 거절 사유와 프로젝트 범위를 설명한다. 자동 생성된 기여도 동일한 기준을 적용하며, 제출자가 동작과 라이선스에 책임을 진다.

사용자 코드나 실행 정보를 수집하는 텔레메트리는 기본 비활성화한다. 도입한다면 opt-in, 수집 항목, 보존 기간, 삭제 방법을 먼저 문서화한다.

## 14. 프로세스 자체의 상태 지표

월 1회 또는 릴리스 후 다음 지표를 가볍게 확인한다.

- PR 필수 CI의 중앙 실행 시간과 실패율
- flaky 테스트 수와 평균 해결 시간
- 릴리스 후 발견된 회귀 수
- 같은 실행의 결정적 결과 불일치율
- 실제 에이전트 호환성 실패율
- 평가 1회당 시간, 메모리, 외부 API 비용
- 열린 보안/고위험 결함의 기간

지표는 목표가 아니라 문제를 찾는 신호다. 커버리지를 높이기 위해 의미 없는 테스트를 만들거나 CI 시간을 줄이기 위해 핵심 검증을 제거하지 않는다. 이 문서는 초기에는 매달, 안정화 후에는 분기마다 검토하며 변경 이유를 PR에 남긴다.

## 15. 단계별 도입 순서

### 0단계: 첫 기능 코드 전

1. Git 저장소, 라이선스, README, CONTRIBUTING, SECURITY를 만든다.
2. 언어와 패키지 관리자를 정하고 버전 및 의존성을 고정한다.
3. 포맷터, 린터, 타입 검사, 테스트 러너를 연결한다.
4. `verify` 단일 진입점과 PR CI를 만든다.
5. 아키텍처 개요와 초기 위협 모델을 작성한다.
6. 벤치마크와 결과 스키마의 최초 버전을 정의한다.

### 1단계: 최소 실행 가능한 평가기

1. 가짜 에이전트와 합성 과제로 전체 흐름을 먼저 검증한다.
2. 실행 상태와 오류 분류를 계약 테스트로 고정한다.
3. 참조 오라클로 채점과 집계를 교차 검증한다.
4. 임시 작업 공간, 제한, 로그 정제, provenance를 구현한다.
5. 실제 에이전트 어댑터는 하나만 추가해 경계를 검증한다.

### 2단계: 첫 공개 릴리스 전

1. 지원 환경 매트릭스와 성능 예산을 확정한다.
2. 격리 공격 fixture와 공급망 검사를 추가한다.
3. 깨끗한 환경의 설치·빠른 시작 테스트를 자동화한다.
4. 벤치마크 데이터의 출처·라이선스·해시를 감사한다.
5. 프리릴리스 사용 결과를 바탕으로 오류 메시지와 문서를 보완한다.
6. 전체 릴리스 후보 체크리스트를 통과한다.

### 3단계: 사용자가 생긴 뒤

실제 결함과 비용 데이터를 보고 테스트 매트릭스와 반복 횟수를 조정한다. 플러그인, 분산 실행, 대시보드 같은 확장은 핵심 평가 결과의 정확성·재현성·격리를 훼손하지 않는 범위에서만 추가한다.

이 프로세스의 핵심은 세 가지다. **점수의 의미를 버전으로 고정하고, 모든 결과의 provenance를 남기며, 신뢰할 수 없는 실행을 격리한다.** 새 절차는 이 셋의 증거를 강화하거나 실제 반복 작업을 줄일 때만 추가한다.
