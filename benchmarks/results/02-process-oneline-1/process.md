# 개발 프로세스와 검증 체계

이 문서는 AI 코딩 에이전트 평가 도구의 품질 기준과 변경 절차를 정의한다. 1인 메인테이너가 지속할 수 있도록, 짧은 피드백 루프와 자동화된 필수 게이트를 우선한다.

## 1. 품질 원칙

모든 설계와 변경은 다음 불변 조건을 지켜야 한다.

1. **재현 가능성**: 같은 도구·평가 데이터·설정·실행 환경·시드를 사용한 실행은 같은 결과를 내야 한다. 모델처럼 비결정적인 대상은 반복 횟수와 분산을 함께 보고한다.
2. **평가의 타당성**: 점수는 문서화된 능력만 측정해야 한다. 실행 성공, 정답성, 효율, 비용 등 서로 다른 지표를 근거 없이 하나로 합치지 않는다.
3. **추적 가능성**: 모든 결과에서 소스 커밋, 도구 버전, 평가 데이터 버전, 평가기 버전, 모델/에이전트 식별자, 설정, 시드, 실행 환경을 확인할 수 있어야 한다.
4. **격리와 최소 권한**: 에이전트가 생성하거나 실행하는 코드는 신뢰하지 않는다. 호스트 파일, 자격 증명, 프로세스, 네트워크에 기본적으로 접근할 수 없어야 하며 시간·CPU·메모리·디스크 제한을 둔다.
5. **원자료 보존**: 실행 로그와 산출물을 먼저 보존하고 점수 계산은 별도 단계에서 수행한다. 평가 오류가 발견되면 원자료를 다시 채점할 수 있어야 한다.
6. **명시적 실패**: 결과 누락, 타임아웃, 인프라 오류, 평가 실패를 에이전트의 오답과 구분한다. 불완전한 실행을 성공처럼 집계하지 않는다.

## 2. 변경 절차

모든 변경은 이 순서를 따른다.

1. **작업 정의**: 이슈에 문제, 기대 결과, 범위 밖 항목, 검증 가능한 인수 조건을 적는다. 보안 경계, 점수 의미, 데이터 형식 또는 결과 호환성을 바꾸면 `고위험`으로 표시한다.
2. **작은 변경 작성**: 한 브랜치와 한 PR에는 한 가지 목적만 둔다. 버그 수정에는 실패를 재현하는 테스트를 먼저 추가한다.
3. **로컬 검증**: 포맷, 정적 검사, 단위 테스트, 관련 통합 테스트를 실행한다. 생성 파일과 비밀정보가 포함되지 않았는지 diff를 확인한다.
4. **PR 자체 리뷰**: 혼자 개발하더라도 PR을 만들고 인수 조건별 증거와 사용자 영향, 호환성 영향을 기록한다. CI가 모두 통과한 뒤 diff를 처음부터 다시 읽는다.
5. **병합**: 필수 게이트가 실패하거나 불안정한 상태에서는 병합하지 않는다. 고위험 변경은 CI 통과 후 최소 하루 뒤 재검토하고, 가능하면 사전 릴리스에서 먼저 검증한다.
6. **릴리스 확인**: 배포 후 깨끗한 환경에서 설치와 대표 평가 1건을 실행한다. 실패하면 새 수정 릴리스를 내고 영향받은 결과를 명시한다.

## 3. 변경 위험도와 필수 증거

| 등급 | 예시 | 추가 필수 검증 |
| --- | --- | --- |
| 낮음 | 문서, 오류 메시지, 내부 정리 | 관련 테스트와 문서 확인 |
| 보통 | CLI/API 동작, 저장 형식, 실행 흐름 | 통합 테스트, 이전 동작과의 비교 |
| 고위험 | 샌드박스, 평가기, 점수식, 데이터셋, 결과 호환성 | 공격/실패 사례, 전체 회귀 평가, 이전 버전과 차이 분석, 마이그레이션 또는 명시적 호환성 중단 |

위험도가 애매하면 더 높은 등급을 적용한다.

## 4. 검증 계층

테스트는 빠르고 결정적인 것부터 넓은 범위로 구성한다.

- **단위 테스트**: 파서, 상태 전이, 점수 계산, 타임아웃/오류 분류를 외부 서비스 없이 검증한다.
- **계약 테스트**: 에이전트 어댑터, 실행기, 결과 스키마의 입력·출력과 버전 호환성을 검증한다.
- **통합 테스트**: 고정된 가짜 에이전트와 작은 fixture 저장소로 준비→실행→수집→채점 전체 흐름을 검증한다.
- **격리 테스트**: 파일 탈출, 자격 증명 접근, 자식 프로세스 잔존, 네트워크 접근, 자원 고갈 시도를 검증한다.
- **종단 간 스모크 테스트**: 깨끗한 환경에서 설치 후 대표 성공·오답·타임아웃·인프라 실패 사례를 실행한다.
- **회귀 평가**: 고정 평가 세트로 결과 스키마와 점수 변화를 이전 기준선과 비교한다.

테스트는 실행 순서, 실제 시간, 외부 네트워크에 의존하지 않아야 한다. 불가피한 난수는 시드를 고정한다. 외부 모델을 호출하는 테스트는 비용과 변동성 때문에 PR 필수 게이트와 분리하고, 예약 실행 또는 릴리스 검증으로 수행한다.

불안정한 테스트는 재시도로 숨기지 않는다. 원인을 고치기 전 격리가 필요하면 담당 이슈와 해제 조건을 남기며, 핵심 경로 테스트는 격리할 수 없다.

## 5. 평가기와 평가 데이터 검증

평가 도구 자체가 틀린 점수를 만들지 않도록 다음을 적용한다.

- 각 평가기는 사람이 결과를 확인한 `정답`, `부분 성공`, `오답`, `실행 실패` fixture를 가져야 한다.
- 같은 의미의 코드 변형에는 같은 판정을, 핵심 요구사항을 깨뜨린 변형에는 실패 판정을 내리는 변형 기반 테스트를 둔다.
- 경로 조작, 테스트 변조, 출력 위조, 캐시 오염처럼 점수를 속일 수 있는 사례를 포함한다.
- 평가기 또는 점수식 변경 시 같은 원자료를 구버전과 신버전으로 채점하여 달라진 항목을 전부 검토한다. 의미가 바뀌면 평가기 버전을 올리고 서로 다른 버전의 점수를 직접 비교하지 않는다.
- 정답 fixture와 기대 점수는 구현 코드와 분리해 리뷰 가능하게 보관한다. 기대값을 현재 출력으로 무심코 덮어쓰지 않는다.

평가 데이터의 각 항목에는 고유 ID, 버전, 출처와 라이선스, 요구사항, 채점 기준, 실행 제한, 알려진 오염 위험을 기록한다. 공개 개발 세트와 릴리스 비교 세트를 구분하며, 릴리스 비교 결과를 본 뒤 해당 릴리스의 기준이나 점수식을 조정하지 않는다. 항목이나 채점 기준이 바뀌면 데이터 버전을 올리고 변경 내역을 남긴다.

비결정적인 에이전트를 비교할 때는 동일한 예산과 환경을 사용하고 사전에 정한 반복 횟수로 실행한다. 성공률과 표본 수를 기본으로 보고하며, 평균만 제시하지 말고 분산 또는 신뢰구간과 실패 유형도 함께 공개한다. 결과를 본 뒤 유리한 실행만 선택하지 않는다.

## 6. 자동화 게이트

프로젝트가 실행 가능한 시점부터 다음 명령을 하나의 표준 작업 실행기(예: `make`, `just`, 또는 선택한 언어의 작업 도구)로 제공한다. 구체적인 이름은 기술 스택을 정할 때 고정한다.

### 모든 PR

1. 포맷 검사
2. 린트와 타입/정적 검사
3. 단위 및 계약 테스트
4. 가짜 에이전트를 사용한 통합 테스트
5. 샌드박스 격리 테스트
6. 소형 회귀 평가
7. 의존성 취약점 및 비밀정보 검사

### 기본 브랜치 예약 실행

1. 지원 환경 전체의 종단 간 테스트
2. 전체 회귀 평가와 기준선 비교
3. 외부 모델 연동 테스트(명시된 비용 한도 내)

### 릴리스

1. 위 검증 전체 통과
2. 깨끗한 환경의 설치 및 스모크 테스트
3. 버전, 변경 기록, 데이터/평가기 호환성 표기 확인
4. 배포 산출물 체크섬과 의존성 목록 생성

커버리지는 누락 탐지용 지표로 관찰하되 숫자만을 품질 게이트로 삼지 않는다. 핵심 점수 계산, 실패 분류, 격리 경계에는 모든 의미 있는 분기의 테스트를 요구한다.

## 7. 보안 검토

최초 실행기 구현 전에 신뢰 경계와 공격 경로를 간단한 위협 모델로 기록한다. 이후 권한, 네트워크, 파일 마운트, 비밀정보, 의존성 또는 산출물 처리 방식이 바뀔 때 갱신한다.

- CI와 평가 실행에 장기 자격 증명을 넣지 않고 권한과 수명을 최소화한다.
- 의존성과 실행 이미지는 버전 또는 digest로 고정하고 자동 변경 PR도 동일한 검증을 거친다.
- 외부 기여 코드의 CI에는 릴리스 비밀정보를 제공하지 않는다.
- 보안 문제는 공개 이슈가 아닌 별도 신고 경로로 받고, 확인 전까지 악용 세부사항을 공개하지 않는다.

## 8. 릴리스와 결과 호환성

도구는 의미적 버전 규칙을 사용한다. CLI/API, 결과 스키마, 평가 데이터, 평가기 버전을 결과에 각각 기록한다. 점수의 의미나 비교 가능성이 바뀌는 변경은 변경 기록에서 눈에 띄게 알리고, 필요하면 주요 버전을 올린다.

릴리스 전에는 알려진 제한, 새 기능, 수정, 호환성 중단을 작성한다. 릴리스 후 평가 오류가 발견되면 영향받은 버전과 결과를 표시하고, 재채점 가능 여부와 수정 버전을 안내한다. 이미 공개한 결과를 설명 없이 교체하지 않는다.

## 9. 완료 기준

변경은 다음 조건을 모두 만족해야 완료다.

- 인수 조건을 충족하는 자동 테스트가 있다.
- 필수 CI가 통과한다.
- 사용자 동작, 결과 형식 또는 점수 의미가 바뀌면 문서와 변경 기록이 갱신됐다.
- 새 의존성·권한·데이터에는 출처, 라이선스, 보안 영향을 확인했다.
- 결과를 재현하는 데 필요한 버전과 설정이 기록된다.
- PR 자체 리뷰에서 범위 밖 변경과 디버그 코드가 없음을 확인했다.

## 10. 프로젝트 시작 순서

1. 지원 환경, 결과 스키마, 버전 정책, 위협 모델을 짧게 문서화한다.
2. 포맷·정적 검사·테스트를 실행하는 단일 명령과 PR CI를 만든다.
3. 고정된 가짜 에이전트와 성공·오답·타임아웃·인프라 실패 fixture를 만든다.
4. 최소 종단 간 경로를 구현하고 원자료 보존과 실행 메타데이터를 검증한다.
5. 샌드박스 경계를 구현하고 격리 테스트를 필수 게이트로 만든다.
6. 첫 평가기를 golden fixture로 검증한 뒤에만 실제 모델 비교를 시작한다.

프로세스 자체가 반복적으로 개발을 막거나 결함을 놓치면 회고 후 이 문서를 수정한다. 게이트를 완화할 때는 이유와 대체 검증을 PR에 남긴다.
