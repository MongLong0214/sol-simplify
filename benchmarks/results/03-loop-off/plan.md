# 티켓 착수 게이트 정상화 계획

## 1. 결론

현재 문제는 검증 코드의 절대적인 줄 수보다 **변경 가능한 레포 규모를 정확한 숫자로 고정한 설계**, **정책 판정과 시스템 오류가 섞인 리졸버**, **구현 세부사항까지 고정하는 과도한 계약 테스트**에 있다.

다음 순서로 해결한다.

1. 오늘 안에 게이트 장애를 복구하고, 막힌 4개 티켓을 감사 가능한 임시 절차로 재판정한다.
2. 정확한 파일·티켓 개수를 요구하는 census pin을 차단 조건에서 제거한다.
3. 5,745줄 리졸버의 현재 동작을 규칙 목록과 골든 케이스로 먼저 고정한 뒤, 선언적 정책과 작은 순수 판정 코어로 점진 교체한다.
4. 8,683줄 계약 테스트를 규칙 테이블, 불변조건 테스트, 소수의 경계 통합 테스트로 대체한다.
5. 새 판정기를 shadow mode로 검증하고 단계적으로 전환한다. 한 번에 다시 쓰지 않는다.

`census pin` 재측정은 복구책으로 사용하지 않는다. 숫자를 다시 맞추면 다음 머지에서 같은 장애가 반복된다.

## 2. 목표와 성공 기준

### 운영 목표

- 유효한 티켓 판정 요청의 99.9% 이상이 `ALLOW` 또는 근거가 있는 `DENY`로 끝난다.
- 파싱 실패, 의존 서비스 실패, 규칙 충돌은 `DENY`가 아니라 `ERROR`로 분류하고 즉시 알린다.
- 항상 통과해야 하는 합성 canary 티켓과 항상 거절되어야 하는 canary 티켓을 매 실행에서 검증한다.
- 게이트 장애 시 30분 안에 탐지하고, 2시간 안에 복구하거나 제한된 수동 판정 절차를 가동한다.

### 변경성 목표

- 정확한 파일 수 또는 티켓 수의 일치를 머지 조건으로 사용하는 검사를 0개로 만든다.
- 서로 다른 두 브랜치가 파일이나 티켓을 각각 추가해도 pin 수정 없이 함께 머지된다.
- 전환 후 4주 동안 census 재측정 전용 커밋이 0건이어야 한다.
- 모든 판정 결과에 규칙 ID, 이유 코드, 정책 버전이 포함된다.

### 단순성 목표

- 모든 현행 규칙에 목적, 소유자, 입력, 우선순위, 기대 결과, 근거 테스트가 하나씩 연결된다.
- 중복·사문화 규칙을 제거하고, 리졸버의 분기 복잡도와 테스트 실행 시간을 기준선 대비 최소 50% 줄인다.
- 검증 코드 LOC는 단독 합격 기준으로 쓰지 않는다. 다만 전환 기간에는 장애 회귀 테스트를 제외한 검증 코드의 순증을 금지하고, 최종적으로 검증 기계가 제품 소스보다 커진 현재 상태를 해소한다.

## 3. 비목표와 원칙

- 모든 검증을 없애거나 게이트를 영구적으로 fail-open으로 만들지 않는다.
- 기존 테스트를 먼저 대량 삭제하지 않는다. 새 판정기와 대체 테스트가 동작한 뒤 대응되는 옛 코드와 테스트를 함께 제거한다.
- 5,745줄 파일을 단순히 여러 파일로 나누는 것을 완료로 보지 않는다. 규칙 수와 분기 수, 외부 상태 의존성을 실제로 줄여야 한다.
- 관측용 통계와 머지 차단용 정확성 검사를 분리한다. 파일·티켓 수는 대시보드 지표일 수는 있어도 저장소의 정답은 아니다.
- 정책 변경과 엔진 변경을 같은 PR에 섞지 않는다. 의도된 판정 변화는 별도 결정 기록과 승인으로 추적한다.

## 4. 단계별 실행 계획

### 0단계 — 장애 수습과 작업 재개 (오늘, P0)

담당: 게이트 온콜 또는 저장소 관리자 1명, 티켓 정책 소유자 1명

1. 어제 실패 실행의 입력 스냅샷, 정책 버전, 로그, 종료 코드를 보존한다.
2. 결과를 `ALLOW`, `DENY`, `ERROR`로 다시 분류한다. 예외나 데이터 로딩 실패가 빈 `ALLOW` 목록 또는 전부 `DENY`로 변환되는 경로를 우선 확인한다.
3. 알려진 합격 티켓 1개와 불합격 티켓 1개를 최소 회귀 테스트로 추가한다. 합격 canary가 통과하지 못하면 게이트 전체를 비정상으로 간주한다.
4. census 불일치가 원인이면 해당 검사만 즉시 **차단에서 경고로 강등**한다. 숫자를 새로 측정해 pin을 갱신하지 않는다.
5. 막힌 구현 티켓 4개는 같은 정책을 사람이 재평가한다. 두 명의 승인, 판정 이유, 적용 정책 버전을 기록한 임시 override로 진행시키고 7일 이내 자동 만료시킨다. 제품 안전·보안 규칙 자체를 우회하지 않는다.
6. 복구 후 사건 기록에 영향 범위, 직접 원인, 탐지 실패, 재발 방지 항목을 남긴다. 개인이 아니라 시스템 조건을 기록한다.

완료 조건:

- 4개 티켓 각각이 `ALLOW`, 근거가 명시된 `DENY`, 또는 별도 조치가 필요한 `ERROR` 중 하나로 판정된다.
- 합격/불합격 canary가 CI에서 매번 실행된다.
- 예외가 빈 결과로 숨겨지지 않는다.

### 1단계 — census pin 제거 (1주차, P0)

담당: 저장소 관리자 + CI 소유자

정확한 개수 비교를 다음의 의미 있는 불변조건으로 교체한다.

- 티켓 문서가 스키마를 만족한다.
- 티켓 ID가 유일하다.
- 참조한 티켓·정책·파일이 실제로 존재한다.
- 티켓 의존 그래프에 금지된 순환이나 dangling reference가 없다.
- 상태 전이가 허용된 방향이다.
- 생성물이 필요하다면 전체 개수가 아니라 원본 입력에서 재생성한 내용과 일치한다.

파일 수와 티켓 수 자체가 필요하면 CI 결과나 모니터링 저장소에 시계열로 기록하되, 그 값 또는 생성된 pin 파일을 Git에 커밋하지 않는다. 비싼 검사는 변경된 티켓과 그 의존 항목을 우선 검사하고, 전체 검사는 야간 작업으로 분리한다.

반드시 추가할 병합 회귀 테스트:

1. 기준 브랜치에서 A와 B를 만든다.
2. A는 파일/티켓 하나를 추가하고 B도 서로 다른 파일/티켓 하나를 추가한다.
3. A를 반영한 뒤 B를 반영한다.
4. 어느 쪽도 카운트 갱신이나 재측정 없이 검증을 통과해야 한다.

완료 조건:

- 저장소 전체에서 exact-count assertion, pin 파일, pin 갱신 스크립트, 관련 문서를 검색해 제거하거나 관측 전용으로 전환했다.
- 위 병합 회귀 테스트가 통과한다.
- pin-only PR을 만드는 자동화가 비활성화됐다.

### 2단계 — 현행 판정 계약 추출 (1~2주차, P1)

담당: 티켓 정책 소유자 + 리졸버 유지보수자

리졸버를 수정하기 전에 코드와 8,683줄 테스트에서 실제 규칙을 다음 표로 추출한다.

| 필드 | 설명 |
|---|---|
| 규칙 ID | 변경되지 않는 식별자 |
| 목적/근거 | 이 규칙이 막는 실제 위험 |
| 입력 | 티켓 필드와 외부 상태 |
| 결과 | `ALLOW`, `DENY`, `ERROR` 및 이유 코드 |
| 우선순위 | 다른 규칙과 충돌할 때의 순서 |
| 소유자 | 정책 변경을 승인할 역할 |
| 예제 | 최소 합격 1개와 불합격 1개 |
| 상태 | 유지, 통합, 폐기 후보 |

최근 실제 티켓과 경계 사례로 작은 골든 코퍼스를 만든다. 개인정보나 비밀 값은 제거한다. 기존 리졸버의 결과를 무조건 정답으로 취급하지 말고 다음을 별도 표시한다.

- 같은 목적을 중복 구현한 규칙
- 현재 입력에서는 도달할 수 없는 분기
- 테스트만 존재하고 정책 근거가 없는 동작
- 순서에 따라 결과가 달라지는 규칙
- 외부 실패를 `DENY`로 바꾸는 경로

이 단계에서 각 규칙을 `유지`, `통합`, `폐기`, `정책 결정 필요`로 분류하고 정책 소유자의 승인을 받는다.

완료 조건:

- 운영 중인 모든 판정 경로가 규칙 목록 또는 명시적인 오류 처리에 대응된다.
- 소유자나 근거가 없는 규칙은 새 엔진으로 이관되지 않고 결정 대기 목록에 있다.
- 골든 코퍼스가 어제의 장애와 막힌 4개 티켓을 포함한다.

### 3단계 — 작은 판정 코어 구축 (2~4주차, P1)

담당: 리졸버 유지보수자

새 판정기는 다음 세 층으로 제한한다.

1. **입력 어댑터**: 티켓과 필요한 저장소 상태를 한 번 읽어 정규화된 입력으로 만든다.
2. **순수 판정 코어**: 외부 I/O나 숨은 전역 상태 없이 선언된 규칙을 평가한다.
3. **출력 어댑터**: 결과, 이유 코드, 정책 버전, 진단 정보를 CI와 사용자에게 전달한다.

결과 계약 예시:

```text
Decision {
  outcome: ALLOW | DENY | ERROR
  reason_codes: string[]
  policy_version: string
  evaluated_rules: string[]
}
```

설계 규칙:

- 잘못된 입력, I/O 실패, 규칙 충돌은 `ERROR`다. 정책상 조건 불충족만 `DENY`다.
- 현재 시간, 브랜치 순서, 디렉터리 열거 순서 같은 암묵 입력을 없앤다. 시간이 필요하면 명시적 입력으로 전달한다.
- 여러 거절 이유를 안정된 순서로 반환해 첫 실패 지점에 따라 결과가 흔들리지 않게 한다.
- 정책은 데이터 또는 작고 이름 붙은 predicate로 표현하고, 거대한 조건문과 테스트 전용 분기를 금지한다.
- 모든 새 규칙에는 규칙 ID, 소유자, 이유 코드, 최소 예제, 만료 또는 재검토 조건이 필요하다.

기존 리졸버 앞에 호환 인터페이스를 두고 규칙 묶음별로 옮긴다. 옮긴 묶음은 새 코어가 담당하고, 대응되는 옛 분기와 중복 테스트를 같은 PR에서 삭제한다.

완료 조건:

- 정규화된 동일 입력은 실행 위치나 열거 순서와 무관하게 동일 결정을 만든다.
- 모든 실패가 `DENY` 또는 `ERROR`로 의도적으로 분류된다.
- 활성 규칙의 100%가 이유 코드와 소유자를 갖는다.
- 리졸버의 단일 거대 실행 경로가 제거되고, 기준선 대비 분기 복잡도가 최소 50% 감소한다.

### 4단계 — 테스트 포트폴리오 재구성 (2~5주차, P1)

담당: 리졸버 유지보수자 + 테스트 인프라 소유자

테스트를 다음 피라미드로 바꾼다.

- **규칙 테이블 테스트**: 규칙별 최소 합격·불합격·경계 사례를 데이터 행으로 표현한다.
- **불변조건/속성 테스트**: 입력 순서가 결과에 영향을 주지 않음, 관련 없는 파일 추가가 판정을 바꾸지 않음, 정보가 더 완전해져도 무관한 거절이 생기지 않음 등을 검증한다.
- **오류 계약 테스트**: 파싱, 누락 참조, I/O, 충돌이 `ERROR`로 노출되는지 검증한다.
- **소수의 통합 테스트**: 실제 파일 읽기, CI 입출력, 종료 코드 같은 경계만 검증한다.
- **병합 회귀 테스트**: 두 독립 브랜치의 추가가 서로를 무효화하지 않는지 검증한다.

기존의 긴 fixture 복제, 내부 호출 순서 assertion, 전체 출력 문자열 snapshot은 제거한다. snapshot이 필요하면 안정된 구조화 결과만 작은 크기로 비교한다. 테스트 삭제 PR에는 대체 테스트 또는 해당 규칙의 폐기 승인을 연결한다.

완료 조건:

- 규칙 목록의 각 유지 규칙이 테이블 테스트 행과 연결된다.
- 장애 사례와 병렬 머지 사례가 회귀 테스트로 고정된다.
- 테스트 실행 시간과 테스트 코드량이 기준선 대비 최소 50% 감소하되, 규칙·오류·경계 커버리지는 빠지지 않는다.
- flaky test 재실행으로 통과시키는 경로가 없다.

### 5단계 — shadow 검증과 전환 (4~6주차, P0/P1)

담당: 게이트 온콜 + 티켓 정책 소유자

1. 모든 판정 요청에 기존 엔진과 새 엔진을 함께 실행하되 기존 결과만 적용한다.
2. `outcome`과 이유 코드의 차이를 저장하고 규칙 ID별로 집계한다.
3. 골든 코퍼스 100%, 최근 실제 티켓, 신규 티켓을 비교한다.
4. 차이를 `새 엔진 버그`, `기존 엔진 버그`, `의도된 정책 변경`, `모호한 정책`으로 분류한다.
5. 미해결 차이가 0이고 7일 연속 canary 및 운영 SLO를 만족하면 새 엔진을 기본으로 전환한다.
6. 첫 1주는 기능 플래그로 즉시 기존 엔진으로 되돌릴 수 있게 유지한다. 이후 옛 리졸버와 대응 테스트를 삭제한다.

전환을 막아야 하는 조건:

- `ERROR`가 `DENY`로 축약되는 사례가 하나라도 있음
- 이유 코드 없는 판정이 있음
- 정책 소유자가 승인하지 않은 결과 차이가 있음
- 병렬 머지 회귀 테스트 또는 합격 canary가 실패함

## 6. 관측과 운영 가드레일

매 실행에서 다음을 수집한다.

- `ALLOW`, `DENY`, `ERROR` 수와 비율
- 규칙 ID별 거절 수와 전주 대비 급변
- 판정 지연 시간과 timeout 수
- 합격/불합격 canary 결과
- 기존/새 엔진의 결과 불일치 수
- override 사용 횟수, 사유, 만료 여부
- pin-only 커밋 수(목표 0)
- 검증 코드 변경량, 분기 복잡도, 테스트 실행 시간

`ALLOW=0`만으로 항상 장애라고 단정하지는 않지만, 합격 canary 실패 또는 평소 범위를 벗어난 `ALLOW=0`은 page 대상이다. override는 좁은 티켓 집합, 짧은 만료 시간, 두 명 승인, 감사 로그를 필수로 하며 정상 경로가 되어서는 안 된다.

## 7. PR 운영 방식

- PR 하나는 한 가지 정책/구조 변경만 담고, 자동 생성된 대규모 diff와 손수 작성한 로직 변경을 섞지 않는다.
- 각 PR 설명에 제거한 규칙/코드, 새 이유 코드, 판정 변화 유무, rollback 방법을 적는다.
- 의도된 정책 변화가 없는 PR은 골든 코퍼스 diff가 0이어야 한다.
- 의도된 변화가 있는 PR은 정책 소유자의 승인과 영향을 받는 티켓 목록을 첨부한다.
- census pin 갱신을 요구하는 CI가 남아 있으면 임시로 값을 맞추지 말고 CENSUS-01의 제거 대상으로 등록한다.

## 8. 최종 종료 조건

다음을 모두 만족하면 정상화 작업을 종료한다.

- 4주 연속 census 재측정 커밋과 pin 충돌이 0건이다.
- 새 엔진이 2주 연속 운영 SLO와 canary를 만족한다.
- 기존 5,745줄 리졸버와 대응되는 중복 계약 테스트가 삭제됐다.
- 검증 시스템이 제품 코드보다 큰 상태가 해소됐고, 추가 규칙의 소유·근거·만료 정책이 문서화됐다.
- 최근 장애를 재현한 테스트, 병렬 머지 테스트, 오류 분류 테스트가 모두 통과한다.
- 임시 override가 모두 만료 또는 폐기됐으며 상시 우회 경로가 남아 있지 않다.
