# 결제 서비스 릴리스 프로세스

## 1. 목적과 적용 범위

이 문서는 프로덕션 변경으로 인한 결제 중단과 보안 통제 약화를 방지하고, PCI-DSS
감사에서 변경의 요청·검토·승인·실행·검증 과정을 재현할 수 있게 하는 최소 절차다.

다음 변경에 적용한다.

- 카드회원데이터 환경(CDE)의 애플리케이션, 인프라, 네트워크, 데이터베이스, 설정
- CDE의 보안에 영향을 줄 수 있는 CI/CD, 인증, 비밀 관리, 로깅·모니터링 시스템
- 결제 승인, 취소, 환불, 웹훅, 정산 또는 결제사업자 연동에 영향을 주는 변경

모든 릴리스는 하나의 변경 기록(티켓 또는 동등한 기록)을 기준으로 관리한다. 기록에는
카드번호 전체, CVV/CVC, 비밀키, 비밀번호 등 민감정보를 남기지 않는다.

## 2. 역할과 승인 절차

역할은 매 릴리스 기록에 실명 계정으로 지정한다. 한 사람이 여러 역할을 맡을 수 있지만,
**변경 작성자는 자신의 변경을 승인할 수 없다.** 일반 릴리스는 최소한 작성자와 독립
승인자 두 사람이 참여한다.

| 역할 | 책임과 승인 대상 |
| --- | --- |
| 변경 작성자 | 변경 사유·범위·보안 영향·테스트 결과·중단 조건·롤백 절차를 작성하고 배포 후보 아티팩트를 지정한다. 승인이 아니라 제출 책임을 진다. |
| 기술 검토자 | 코드/설정의 정확성, 테스트 범위, 데이터 마이그레이션 호환성, 카드 데이터 비노출, 롤백 가능성을 검토하고 기술 승인을 남긴다. 작성자와 다른 사람이어야 한다. |
| 보안 책임자 또는 지정 대리자 | 아래의 `중대한 변경`에 한해 CDE 범위, 인증·권한, 암호화, 로깅, 취약점 및 PCI-DSS 통제 영향을 승인한다. |
| 릴리스 관리자 | 체크리스트, 필수 승인, 배포 담당자·온콜 가용성, 모니터링 화면, 중단 조건과 롤백 준비가 완결됐는지 확인하고 최종 Go/No-Go를 승인한다. 작성자 본인은 맡을 수 없다. |
| 배포 담당자 | 승인된 아티팩트와 절차만 프로덕션에 적용하고, 시작·종료 시각과 실제 결과를 기록한다. 이상 시 즉시 중단 또는 롤백한다. |
| 온콜/인시던트 지휘자 | 배포 중 서비스 상태를 감시한다. 중단 조건 발생 시 추가 승인 없이 배포 중단과 사전 승인된 롤백을 지시할 수 있다. |

`중대한 변경`은 최소한 다음을 포함한다: CDE 장비·소프트웨어·네트워크의 신규 도입이나
대규모 교체, 계정 데이터의 저장 또는 흐름 변경, CDE 경계·PCI 범위 변경, 인증·시간
동기화·로깅·모니터링 등 기반 통제 변경, CDE를 지원하는 외부 서비스 제공자 변경.

승인은 다음 순서로 진행한다.

1. 변경 작성자가 변경 기록과 배포 후보를 제출한다.
2. 기술 검토자가 PR과 증적을 검토하고 승인 또는 보완 요청을 남긴다.
3. 중대한 변경이면 보안 책임자가 보안 영향과 적용 통제를 별도로 승인한다.
4. 릴리스 관리자가 모든 항목을 확인해 최종 Go/No-Go를 기록한다.
5. 배포 담당자는 최종 승인 뒤 지정된 아티팩트만 배포한다.

승인은 변경 기록 또는 연결된 PR에서 인증된 계정, 승인 내용, 시각이 보이게 남긴다.
구두 승인이나 메신저 반응만으로는 승인 증적을 대체할 수 없다. 승인 후 코드, 설정,
아티팩트 또는 롤백 절차가 바뀌면 영향받는 승인을 다시 받아야 한다.

### 긴급 릴리스

진행 중인 장애나 즉시 악용 가능한 취약점을 복구하기 위한 변경은 긴급 릴리스로 표시한다.
인시던트 지휘자와 작성자가 아닌 승인자 한 명의 승인을 받은 뒤 실행하며, 생략한 테스트와
그 사유를 기록한다. 복구 후 생략한 검증을 완료하고 인시던트 기록과 연결한다. 긴급이라는
이유로 자기 승인, 변경 기록 또는 보안 영향 기록을 생략할 수 없다.

## 3. 릴리스 전 체크리스트

릴리스 관리자는 다음 항목이 충족된 경우에만 Go를 승인한다. 해당하지 않는 항목은
`N/A`와 사유를 기록한다.

### 변경과 위험

- [ ] 고유 변경 ID, 변경 사유, 사용자 영향, 대상 서비스·인프라·설정이 기록됐다.
- [ ] CDE 및 PCI-DSS 통제에 미치는 보안 영향과 `중대한 변경` 여부·근거가 기록됐다.
- [ ] 커밋, PR, 버전, 컨테이너 이미지 digest 또는 아티팩트 checksum이 고정됐다.
- [ ] 의존 서비스, 결제사업자, 기능 플래그, 설정, 비밀, DB 스키마 영향이 확인됐다.
- [ ] 배포 중단 조건을 기존 서비스 기준에 맞춰 정량적으로 기록했다.

### 검토와 테스트

- [ ] 작성자가 아닌 기술 검토자가 승인했다.
- [ ] 빌드, 단위·통합 테스트와 보안 검사가 성공했고 결과 링크가 있다.
- [ ] 변경된 맞춤형 소프트웨어가 입력 검증, 인증·권한, 세션, 암호화, 오류 처리 등
      적용 가능한 보안 요구사항을 충족하는지 시험했다.
- [ ] 프로덕션과 분리된 사전 환경에서 승인·거절·타임아웃·재시도·웹훅·멱등성 등
      변경과 관련된 결제 경로를 테스트했다.
- [ ] 실제 카드 데이터나 프로덕션 비밀을 사전 환경 또는 테스트 증적에 사용하지 않았다.
- [ ] 로그, 오류 메시지, 추적 데이터에 PAN 전체와 민감 인증 데이터가 노출되지 않는다.
- [ ] DB 변경은 이전 애플리케이션 버전과의 호환성, 재실행 안전성, 복구 방법을 검증했다.

### 배포와 복구 준비

- [ ] 배포 순서, 명령/자동화 링크, 담당자, 예정 시각이 기록됐다.
- [ ] 현재 프로덕션 버전과 설정을 식별했고 직전 정상 아티팩트를 다시 배포할 수 있다.
- [ ] 롤백 트리거, 책임자, 명령, 데이터 처리 방법과 검증 절차를 사전 환경에서 확인했다.
- [ ] 필요한 백업이 완료됐고 복원 가능 여부가 확인됐다. 백업에 카드 데이터가 있으면
      기존 암호화·접근 통제를 그대로 적용한다.
- [ ] 결제 승인 성공/실패, 오류율, 응답시간, 웹훅·큐 지연, 외부 결제사업자 상태,
      DB 상태를 볼 수 있는 대시보드와 알림이 준비됐다.
- [ ] 배포 담당자와 온콜이 배포 및 관찰 시간 동안 즉시 대응 가능하다.

## 4. 배포와 완료 판정

1. 배포 담당자는 승인된 버전과 현재 프로덕션 버전을 다시 대조하고 시작 시각을 기록한다.
2. 승인된 절차로만 배포하며, 수동 변경이 필요하면 실행자·명령의 목적·결과를 기록한다.
3. 배포 직후 비실카드 테스트 수단으로 영향받은 결제 경로를 스모크 테스트한다.
4. 온콜은 사전에 기록된 중단 조건과 배포 전 상태를 기준으로 결제 및 시스템 지표를 확인한다.
5. 정상임을 확인하면 릴리스 관리자가 완료를 기록한다. 중대한 변경은 적용 가능한
   PCI-DSS 통제가 유지되는지 확인하고 관련 CDE 범위·구성 문서를 갱신한다.

## 5. 롤백 절차

결제 스모크 테스트 실패, 승인 성공률 또는 오류·지연의 중단 조건 위반, 중복 승인·누락,
웹훅/정산 불일치, 보안 통제 실패, 예상하지 못한 CDE 노출이 확인되면 롤백한다. 원인 분석을
기다리느라 복구를 늦추지 않는다.

1. **중단:** 배포 담당자 또는 온콜이 추가 배포를 멈추고 인시던트 지휘자를 지정한다.
2. **고정:** 변경 ID, 배포 버전, 시작 시각, 최초 증상과 지표를 보존한다. 로그에 민감한
   카드 데이터를 복사하지 않는다.
3. **복구 방식 선택:** 사전 승인된 순서에 따라 기능 플래그 비활성화, 이전 설정 복원,
   이전 아티팩트 재배포 또는 정상 환경으로 트래픽 전환 중 가장 안전한 방법을 실행한다.
4. **데이터 보호:** DB 변경은 임의로 역방향 실행하지 않는다. 검증된 하위 호환 경로,
   사전 작성된 복구 변경 또는 백업 복원을 사용한다. 파괴적 복원은 인시던트 지휘자와
   DB 책임자가 대상·시점을 확인한 뒤 실행한다.
5. **검증:** 비실카드 수단으로 승인과 영향받은 경로를 재시험하고, 중복/유실 거래,
   미처리 큐·웹훅, DB 및 외부 결제사업자 상태, 보안 통제와 로그 마스킹을 확인한다.
6. **종료:** 정상 버전, 복구 시각, 고객 영향, 실행자, 명령/파이프라인, 검증 결과와 남은
   후속 조치를 변경 기록에 남긴다. 장애가 선언됐다면 인시던트 기록과 연결한다.

사전 승인된 롤백은 서비스 복구를 위해 별도 Go 승인을 기다리지 않는다. 계획에 없던
프로덕션 변경이 필요하면 인시던트 지휘자와 작성자가 아닌 기술 또는 보안 승인자가 범위와
위험을 확인하고 긴급 릴리스로 기록한다.

## 6. 감사 대응을 위한 기록 항목

팀이 이미 사용하는 변경 티켓, Git/PR, CI/CD 및 중앙 로그 저장소를 증적 원본으로 사용하고,
고유 변경 ID로 서로 연결한다. 별도 수기 대장을 중복 작성하지 않는다.

각 릴리스에는 다음을 보존한다.

| 구분 | 필수 기록 |
| --- | --- |
| 식별 | 변경 ID, 제목, 사유·설명, 요청자, 생성·배포·완료 시각과 시간대 |
| 범위 | 영향받은 서비스·CDE 구성요소·데이터 흐름·외부 제공자, 중대한 변경 여부와 근거 |
| 보안 영향 | 인증·권한·암호화·카드 데이터·비밀·네트워크·로깅·모니터링 영향과 적용 통제 |
| 변경물 | PR/커밋, 소스 버전, 아티팩트 버전·digest/checksum, 스키마·설정 변경 식별자 |
| 검증 | 코드 리뷰, 빌드, 기능·결제 경로·보안 테스트, 취약점 검사 결과와 실패 조치 |
| 승인 | 작성자, 기술 검토자, 조건부 보안 책임자, 릴리스 관리자 각각의 결정·시각·계정 |
| 실행 | 배포 담당자, 실제 시작·종료 시각, 배포 전후 버전, 파이프라인 실행 또는 수동 작업 결과 |
| 관찰 | 배포 전 기준, 중단 조건, 배포 후 주요 결제·시스템 지표, 스모크 테스트 결과 |
| 복구 | 롤백 필요 여부, 결정자·사유·시각, 실행 단계와 결과, 복구 버전, 거래 무결성 검증 |
| 예외 | N/A 사유, 긴급 변경 사유, 생략한 테스트·보완 결과, 연결된 장애·후속 조치 |

증적은 읽기 권한을 업무상 필요한 인원으로 제한하고, 삭제·변조로부터 보호하며, 시스템
시간을 동기화해 동일한 사건의 시각을 대조할 수 있게 한다. 프로덕션 접근·배포 등 PCI-DSS
범위의 감사 로그는 최소 12개월 보존하고 최근 3개월은 즉시 분석 가능하게 유지한다.
그 밖의 변경·승인·테스트 증적은 회사의 증적 보존 정책에 따라 해당 감사 대상 기간 전체를
조회할 수 있게 보존한다.

## 7. PCI-DSS 기준 연결

- PCI DSS v4.0.1 6.5.1: 변경 사유·설명, 보안 영향, 권한 있는 승인, 보안 테스트,
  실패 시 안전한 상태로의 복구 절차
- PCI DSS v4.0.1 6.5.2: 중대한 변경 후 적용 가능한 통제와 문서의 재확인
- PCI DSS v4.0.1 10.2.2, 10.3, 10.5.1, 10.6.1: 감사 이벤트의 식별 정보,
  로그 보호·보존 및 시간 동기화

[PCI SSC의 중대한 변경 설명](https://www.pcisecuritystandards.org/faqs/1317/)
