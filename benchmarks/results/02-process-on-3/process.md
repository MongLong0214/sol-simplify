# AI 코딩 에이전트 평가 도구: 개발 프로세스와 검증 체계

## 전제와 품질 기준

이 문서는 평가 도구가 에이전트와 에이전트가 만든 코드를 격리된 환경에서 실행하고, 그 결과를 구조화된 점수로 만드는 도구라고 가정한다. 정적 분석만 수행하는 제품으로 범위가 좁아지면 실행 격리 항목은 제외한다.

프로세스만으로 품질을 보장할 수는 없다. 대신 다음 속성을 실행 가능한 증거로 확인한다.

- **정확성:** 같은 원시 실행 증거에 같은 판정을 내린다.
- **재현성:** 결과에 사용한 코드, 태스크, 환경, 설정을 다시 구성할 수 있다.
- **타당성:** 통과해야 할 구현은 통과하고, 의도적으로 깨진 구현은 올바른 이유로 실패한다.
- **안전성:** 에이전트와 생성 코드를 신뢰하지 않아도 호스트와 비밀정보가 보호된다.
- **설명 가능성:** 총점뿐 아니라 태스크별 판정, 실패 이유, 원시 증거를 확인할 수 있다.

인프라 장애, 평가기 버그, 에이전트 실패는 서로 다른 상태다. 실행 오류를 임의로 0점 처리하지 않는다.

## 최소 제품 경계

처음부터 다음 네 경계를 분리한다.

1. **태스크:** 입력, 제약, 성공 조건과 테스트 픽스처
2. **러너:** 격리 환경 생성, 에이전트 실행, 자원 제한과 증거 수집
3. **평가기:** 수집한 증거를 판정과 점수로 변환하는 순수 로직
4. **리포터:** 결과 레코드를 저장하고 사람이 읽을 수 있게 출력

러너의 로그를 파싱하면서 동시에 점수를 계산하거나, 리포터가 점수를 다시 추론하지 않는다. 이 경계가 있어야 실행 문제와 채점 문제를 독립적으로 재현할 수 있다.

태스크 스키마, 결과 스키마, 평가 프로토콜은 각각 버전을 가진다. 점수 의미가 바뀌는 태스크·오라클·가중치 변경은 새 평가 프로토콜 버전으로 남기며, 기존 결과를 새 의미로 덮어쓰지 않는다.

## 일상 개발 흐름

한 명의 메인테이너에게 별도 승인 단계는 두지 않는다. `main`을 항상 실행 가능한 상태로 유지하며 다음 순서로 작게 변경한다.

1. 사용자에게 보이는 동작 하나 또는 재현 가능한 실패 하나를 정한다.
2. 해당 동작을 증명할 가장 낮은 수준의 테스트를 먼저 추가해 실패를 확인한다.
3. 테스트를 통과시키는 최소 구현을 작성한다.
4. 포매터, 정적 검사, 타입 검사, 테스트와 작은 종단 간 평가를 로컬에서 실행한다.
5. 변경 diff를 다시 읽어 신뢰 경계, 오류 분류, 결과 스키마와 하위 호환 영향을 확인한다.
6. 깨끗한 환경의 CI에서 같은 검증을 통과한 뒤 `main`에 반영한다.

초기에는 전체 테스트가 작으므로 모든 push와 외부 PR에서 전부 실행한다. 실제 실행 비용이 커진 뒤에만 빠른 검증과 전체 검증을 분리한다. 이슈, PR, ADR은 변경 자체를 이해하는 데 필요할 때만 사용하며 혼자 하는 모든 변경에 의무화하지 않는다.

## 변경별 필수 증거

| 변경 대상 | 반드시 확인할 동작 |
|---|---|
| 파서·평가기·점수 집계 | 경계값과 잘못된 입력의 단위 테스트, 스키마 계약 테스트, 사람이 계산 가능한 골든 케이스 |
| 러너·프로세스 제어 | 성공, 비정상 종료, 타임아웃, 출력 과다, 자식 프로세스 잔존을 다루는 통합 테스트 |
| 태스크·벤치마크 | 알려진 정상 구현의 통과와 의도적으로 깨진 구현들의 예상 사유 실패 |
| 격리·파일·네트워크 | 경로 탈출, 심볼릭 링크, 비밀정보 접근, 자원 고갈, 허용되지 않은 네트워크 요청의 적대적 테스트 |
| CLI·API·결과 형식 | 깨끗한 임시 디렉터리에서 설치부터 결과 파일 생성까지 수행하는 종단 간 테스트 |
| 배포·의존성 | 지원한다고 명시한 환경에서 깨끗한 설치와 번들된 소형 평가의 스모크 테스트 |

코드 커버리지는 누락 지점을 찾는 참고 자료로만 사용한다. 근거 없는 목표 수치를 합격 조건으로 삼지 않는다.

## 검증 설계

### 평가기

- 점수 계산은 원시 증거를 입력받는 결정적 함수로 만든다.
- 정상, 빈 값, 부분 결과, 손상된 결과, 중복 결과와 경계값을 테스트한다.
- 골든 테스트는 총점만 고정하지 않고 기준별 판정과 그 근거를 함께 확인한다.
- 가능한 불변식을 속성 테스트로 확인한다. 예를 들어 입력 순서가 의미 없는 집계라면 순서를 바꿔도 결과가 같아야 한다.
- 원시 증거 보존값과 리포터가 표시한 값에서 점수를 독립적으로 다시 계산할 수 있어야 한다.

LLM을 판정자로 사용한다면 모델 식별자, 프롬프트, 루브릭, 샘플링 설정을 평가 프로토콜에 포함한다. 에이전트 이름을 가린 손으로 판정한 소형 사례 모음과 비교하고 반복 실행의 분산을 기록한다. 판정자 호출 실패나 형식 오류는 에이전트 실패가 아니라 평가 인프라 오류다.

### 태스크와 벤치마크

각 태스크에는 최소한 하나의 정상 구현과, 해당 태스크가 잡으려는 결함을 하나씩 담은 깨진 구현들을 둔다. 정상 구현이 실패하거나 깨진 구현이 엉뚱한 이유로 실패하면 태스크 결함으로 취급한다.

오라클과 비공개 테스트는 에이전트 작업 디렉터리에서 읽을 수 없게 한다. 공개 벤치마크는 학습 데이터 오염과 사전 노출을 완전히 막을 수 없으므로 결과를 일반 지능의 절대 척도로 표현하지 않는다. 서로 다른 결과를 비교할 때는 같은 태스크 버전, 평가 프로토콜, 실행 환경, 자원 정책과 반복 정책을 사용한다.

동일한 고정 입력과 환경에서 판정이 흔들리는 태스크는 집계에서 제외하고 원인을 고친다. 재시도로 우연히 통과시켜 불안정성을 숨기지 않는다. 에이전트 자체의 확률적 변동을 측정할 때는 개별 실행 결과, 집계 방법과 분산을 함께 공개한다.

### 러너와 보안

에이전트와 생성 코드는 악의적일 수 있다고 가정한다.

- 실행마다 폐기 가능한 격리 환경과 별도 작업 디렉터리를 사용한다.
- 호스트 자격증명과 사용자 파일을 주입하지 않고 최소 권한으로 실행한다.
- CPU, 메모리, 디스크, 실행 시간과 프로세스 수를 제한한다.
- 입력은 읽기 전용으로 제공하고 결과 경로는 정규화해 상위 경로 및 심볼릭 링크 탈출을 막는다.
- 네트워크는 태스크가 명시적으로 필요로 할 때만 목적지와 정책을 기록해 허용한다.
- 타임아웃이나 종료 시 전체 프로세스 트리를 정리한다.
- 로그와 결과에서 비밀정보를 가리고, 보존할 출력과 최대 크기를 제한한다.

위 항목은 문서 확인이 아니라 실제 탈출 시도와 자원 고갈 픽스처로 검증한다. 완전한 샌드박스를 구현하기 전에는 외부 에이전트나 신뢰하지 않는 코드를 호스트에서 직접 실행하지 않는다.

### 종단 간 기준 시나리오

작고 빠른 가짜 태스크와 가짜 에이전트로 다음 결과를 끝까지 검증한다.

- 정상 해결 및 예상 점수
- 빌드 실패와 테스트 실패
- 에이전트 충돌과 형식이 잘못된 출력
- 타임아웃과 종료되지 않는 자식 프로세스
- 평가기 또는 인프라 자체의 실패
- 허용 범위 밖 파일·네트워크 접근

각 시나리오는 러너 상태, 평가 상태, 종료 코드, 태스크별 판정과 결과 파일을 확인한다. 실제 외부 모델 호출은 핵심 CI의 필수 조건으로 두지 않고, 별도 수동 스모크에서 공급자 연결만 확인한다. 핵심 정확성 테스트는 기록된 응답이나 가짜 에이전트로 결정적으로 실행한다.

## 결과 재현성과 보고

모든 결과 레코드에는 다음을 포함한다.

- 도구 버전과 소스 커밋
- 태스크 묶음과 평가 프로토콜 버전
- 에이전트, 모델·공급자 버전, 실행 설정과 허용 도구
- 환경 이미지 또는 운영체제, 런타임과 잠금된 의존성 정보
- 입력, 시드, 자원·네트워크 정책과 반복 식별자
- 원시 이벤트, 로그, 산출물 또는 변경 diff의 참조와 무결성 해시
- 태스크별 판정 근거, 총점, 실행 오류 및 인프라 오류

한 번의 실행을 에이전트의 안정적인 능력으로 과장하지 않는다. 서로 다른 프로토콜의 결과는 비슷한 숫자여도 직접 순위 비교하지 않으며, 리포트에 비교 불가 사유를 표시한다.

## 릴리스

릴리스 후보는 깨끗한 체크아웃에서 설치하고, 전체 테스트와 번들된 소형 평가를 실행해 실제 결과 레코드를 생성한다. 성공한 소스 커밋에 버전을 태그하고, 평가 프로토콜 및 태스크 버전과 함께 배포한다. 점수 의미, 결과 스키마 또는 호환성을 바꾸는 내용은 릴리스 설명에 명시한다.

실사용에서 발견된 결함은 먼저 최소 재현 테스트로 고정한 뒤 수정한다. 한 번의 사고를 이유로 새 승인 단계나 포괄적 규칙을 추가하지 않는다. 실제 사용자 결함을 잡지 못하거나 더 단순한 테스트와 중복되는 검증은 제거한다.
