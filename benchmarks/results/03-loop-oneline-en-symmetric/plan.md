# 티켓 착수 게이트 단순화 계획

> 목표: 변동하는 레포·티켓 개수를 고정값으로 검증하는 `census pin`을 없애고, 현재 외부 계약을 유지한 채 리졸버를 “발견된 각 티켓에 기존 착수 조건을 한 번 적용한다”는 단일 흐름으로 축소한다. 게이트를 끄거나 우회하지 않는다.

| 현재 기준 | 수치 |
|---|---:|
| 리졸버 + 계약 테스트 | 14,428줄 |
| 전체 검증 / 제품 소스 | 20,280줄 / 17,964줄 |
| 지난달 pin 재측정 커밋 | 25건 |
| 어제 멈춘 구현 작업 | 4건 |

## 판단

지금 문제는 pin 값이 틀린 것이 아니라 **변동하는 개수를 불변 계약으로 취급한 설계**다. 재측정 자동화나 충돌 해결 절차를 추가해도 두 브랜치가 서로의 pin을 무효화하는 구조는 남는다. 따라서 pin을 다시 맞추는 대신 정확한 개수 비교 자체를 삭제해야 한다.

동시에 5,745줄 리졸버와 8,683줄 계약 테스트를 별도 구조로 재설계하지 않는다. 공개 입출력과 실제 착수 조건만 남기고, 같은 스크립트 안에서 한 번의 순회로 판정하도록 만든 뒤 그 계약만 작은 표 기반 테스트로 고정한다. 결과는 코드 추가가 아니라 대규모 순삭제여야 한다.

## 변경 경계

실제 제품 레포가 이 작업 디렉터리에 제공되지 않아 파일명은 확정하지 않는다. 구현 시 아래 네 대상만 찾아 수정한다.

1. 티켓 착수 여부를 반환하는 현재 리졸버 스크립트
2. 그 리졸버의 계약 테스트
3. 파일 수·티켓 수의 기대값을 저장하는 pin 파일 또는 상수
4. pin을 생성·재측정하거나 CI에서 비교하는 호출부

CLI 인자, 입력 티켓 형식, 허용/거부 결과 형식, 실제 게이트 조건은 유지한다. 새 서비스, 설정, 추상화 계층, 호환 경로, 이중 실행, feature flag는 만들지 않는다.

## 목표 흐름

```text
canonical ticket source
        |
        v
discover current tickets  ----  no expected total
        |
        v
for each ticket: apply the existing eligibility predicate once
        |
        +---- eligible   -> existing allow result
        |
        `---- ineligible -> existing deny result + existing reason
```

검증은 “티켓이 정확히 N개인가?”가 아니라 **현재 발견된 티켓마다 판정 결과가 있는가, 그리고 판정이 착수 조건과 일치하는가**만 확인한다. 기존에 이미 수행 중인 티켓 내용 검증은 유지하되 총개수 비교만 제거한다.

## 실행 순서

### 1. 외부 계약과 어제 장애를 최소 테스트로 고정

- 리졸버의 실제 호출부에서 공개 입력, 출력, 종료 코드를 확인해 유지할 계약을 적는다.
- 어제 통과해야 했지만 거부된 티켓 하나를 최소 fixture로 만들고 `조건 충족 -> 허용` 회귀 테스트를 먼저 추가한다.
- 표에는 모든 조건을 만족하는 허용 행 하나와, 각 조건을 하나씩만 깨뜨린 거부 행 하나씩만 둔다. 조건 조합의 전수열거·스냅샷·생성 테스트는 만들지 않는다.
- 기존 테스트가 문서화된 착수 조건과 충돌하면 거대한 테스트의 현재 출력이 아니라 공개 계약과 실제 게이트 규칙을 기준으로 기대값을 정한다.

### 2. 리졸버를 현재 파일 안의 단일 판정 루프로 축소

- 티켓 원본을 한 번 읽고, 발견된 각 티켓에 기존 착수 predicate를 정확히 한 번 적용한다.
- 조건을 만족하면 기존 allow 결과를, 만족하지 않으면 기존 deny 결과와 사유를 반환한다. 어제의 all-deny 원인을 만든 반전 조건, 조기 종료, 집계 의존성은 이 흐름으로 교체한다.
- census 값, 전체 티켓 수, 전체 파일 수가 개별 티켓의 착수 여부에 영향을 주는 분기를 삭제한다.
- 단일 순회와 같은 결정을 중복 수행하는 기존 분기와 그 전용 코드를 삭제한다. 단, 실제 착수 조건 자체는 바꾸지 않는다.

### 3. census pin을 끝까지 제거

- 저장된 파일 수·티켓 수, pin 생성기/재측정 명령, CI의 정확한 개수 비교, pin 갱신 전용 테스트를 삭제한다.
- 티켓 발견과 기존 내용 검증은 그대로 실행한다. 새 파일이나 새 티켓이 추가되면 별도 기준값 갱신 없이 같은 검증 대상에 자동 포함되게 한다.
- README, 기여 문서, CI 메시지에서 pin 갱신 절차만 제거한다. 대체 운영 절차는 추가하지 않는다.

### 4. 계약 테스트를 행위 중심 표로 교체하고 구 구현 삭제

- 테스트는 다음 네 행위만 남긴다: 조건을 모두 만족한 티켓 허용, 각 조건 위반의 거부 사유, 현재 발견된 모든 티켓에 정확히 한 결과, 파일·티켓 추가가 기존 결과를 무효화하지 않음.
- 서로 다른 두 변경이 각각 유효 티켓을 하나씩 추가한 뒤 합쳐진 상태를 fixture로 검증한다. pin 수정 없이 두 티켓 모두 발견·판정되면 충분하다.
- 새 테스트가 통과하면 기존 8,683줄 계약 테스트 중 같은 결과를 반복하거나 census 숫자를 고정하는 부분과 축소 전 리졸버 코드를 같은 변경에서 삭제한다.

## 검증 및 완료 조건

- 어제 장애를 재현한 적격 fixture가 허용되고, 조건 하나를 위반한 fixture들은 기존 사유로 거부된다.
- 리졸버의 기존 CLI/API 소비자가 수정 없이 같은 형식의 결과를 받는다.
- 레포에 관련 없는 파일 하나를 추가해도 검증 결과가 변하지 않는다.
- 유효 티켓 두 개를 독립적으로 추가한 변경을 합친 상태에서 pin 재측정 없이 둘 다 통과한다.
- 저장된 census 값, 정확한 총개수 assertion, pin 생성·갱신 명령 및 문서가 더 이상 남아 있지 않다.
- 전체 테스트와 CI 게이트가 통과하며, 리졸버와 계약 테스트의 합계는 기준 14,428줄보다 순감소한다. 별도 줄 수 목표를 위해 코드를 재배치하지 않는다.
- 이후 일반적인 파일·티켓 추가 PR에는 census 갱신 diff가 생기지 않는다.

## 위험과 제어

| 위험 | 제어 |
|---|---|
| 숨은 소비자가 리졸버의 내부 산출물에 의존 | 실제 호출부를 검색해 공개 입출력·종료 코드만 먼저 고정하고 그대로 유지한다. |
| pin 제거로 티켓 누락을 못 찾음 | 고정 총개수 대신 canonical source에서 현재 발견된 모든 티켓이 한 번씩 판정되는 테스트로 확인한다. |
| 단순화 과정에서 착수 의미가 변함 | 어제의 적격 사례와 조건별 양방향 표를 먼저 만들고, 구현 전후 동일 계약을 실행한다. |

## 명시적 비목표

- 게이트 비활성화 또는 fail-open
- census pin 자동 갱신 봇이나 충돌 해결 도구
- 범용 규칙 엔진, 플러그인 시스템, 새 검증 프레임워크
- 제품 코드 리팩터링
- 리졸버 공개 계약 변경
